## 定位

- **本 skill 管"怎么拆、怎么治理"**，是重构的方法论。
- **拆完的代码质量由 `coding-standards` 保证**——重构过程中写的每一行代码都要符合编码规范。
- 不做需求变更，不改业务语义（除非明确要求）。

## 何时触发

- 用户说"这个方法太长了，拆一下""这个文件太大了，治理一下""把职责分离出来"。
- 用户说"这块老代码要整理一下""这个模块要重构"。
- code-review 发现 P2（可维护性差）问题后，需要落地改造。
- 文件超 1000 行或方法超 150 行，需要拆分。

## 重构边界

**开始前必须写清楚：**

| 维度 | 默认约束 |
|------|---------|
| 接口契约 | 不改（除非明确要求） |
| 业务语义 | 不改（除非明确要求） |
| 设计模式 | 不引入新模式（除非明确要求） |
| 编码规范 | 遵守 `coding-standards`（全维度） |
| 目标阈值 | 文件 ≤ 1000 行，方法 ≤ 150 行 |

## 重构类型

### 类型 A：结构拆分

**目标**：把大文件/大方法拆成合理粒度，提升可读性和可维护性。

适用场景：
- 单个文件超过 1000 行
- 单个方法超过 150 行
- 一个类承担了太多职责（上帝类）

### 类型 B：老代码治理

**目标**：在不改业务的前提下，提升老代码的可读性、可维护性和可观测性。

适用场景：
- 代码年久失修，可读性差
- 缺少日志，出问题无法排查
- 命名混乱，新人看不懂
- 重复代码多，改一处漏一处

### 类型 C：模块化重组

**目标**：把散落在各处的相关逻辑归拢到合理的模块/包结构中。

适用场景：
- 相关逻辑散落在多个不相关的类中
- 包结构不清晰，找代码靠搜索
- 循环依赖、层次混乱

## 结构拆分流程

### 1. 画出主流程

先理清当前代码的主链路：

```
validate → build → call → parse → persist → respond
```

用 5-10 行或一张 Mermaid 图描述清楚。

### 2. 标出"可切的缝"（seams）

找到可以独立出去的职责块：

- 校验逻辑
- DTO/DO/VO 转换
- 外部调用（HTTP/RPC/DB）
- 持久化操作
- 规则计算
- 异常映射
- 日志封装

### 3. 抽方法（局部收敛）

把每个职责块抽成独立方法：

- 方法名必须能说明"做了什么"
- 一个方法只做一件事
- 参数尽量少，语义清晰

### 4. 拆类（职责聚合）

把同一类职责的方法聚到一个类里：

- 原入口类只做**编排**（调用各职责类的方法，控制流程）
- 每个拆出的类聚焦一个清晰的职责

### 5. 重命名

- 类名/方法名要能一眼看懂
- 避免泛化命名滥用：`Manager`、`Processor`、`Handler`、`Executor`
- 用业务语义命名：`OrderValidator`、`PointCalculator`、`WeatherClient`

### 6. 行为等价自查

拆完后必须验证：
- 关键分支是否一致
- 默认值/边界是否一致
- 异常行为是否一致
- 返回值语义是否一致

## 老代码治理流程

### 1. 读懂现有逻辑

- 先通读一遍，理解主流程和关键分支。
- 不懂的地方看 `git log -p` / `git blame` 了解历史。
- 标记出"历史逻辑/技术债/已知坑"。

### 2. 补注释

- 按 `coding-standards` 的注释规范，给类/方法/关键常量补注释。
- 重点补：核心入口方法、非直觉行为、历史兼容逻辑。

### 3. 补日志

- 按 `coding-standards` 的可观测性规范，补关键路径日志。
- 重点补：入口/出口、外部调用、异常处理、耗时。

### 4. 提取重复代码

- 发现重复代码抽取共用方法，但要保证行为一致。
- 不要过度抽象——两处重复可以先不动，三处以上再抽。

### 5. 规范化

- 命名不规范的改掉（但注意对外接口/字段不要随便改）。
- 配置硬编码的改成配置中心。
- 缺少校验的补上。

### 6. 按结构拆分流程处理超大文件/方法

如果文件/方法超标，走上面的结构拆分流程。

## 职责组件清单

按场景选，不要硬凑全家桶：

| 组件 | 职责 | 示例 |
|------|------|------|
| `XxxValidator` | 入参/业务前置校验 | `OrderValidator` |
| `XxxConverter` / `XxxAssembler` | DTO/DO/VO 互转 | `OrderConverter` |
| `XxxClient` / `XxxBoundService` | 外部系统调用封装 | `WeatherBoundService` |
| `XxxRepository` | DB 访问与复杂查询 | `OrderRepository` |
| `XxxDomainService` / `XxxRule` | 核心规则与状态流转 | `PointRule` |
| `XxxSupportService` | 支撑逻辑 | `NotifySupportService` |

## 验收清单

- [ ] 主流程入口方法可在 **10 分钟内读懂**（步骤清晰、命名明确）
- [ ] 文件/方法尺寸明显下降，职责边界更清楚
- [ ] 没有"为了拆分而拆分"的空壳抽象
- [ ] 关键异常与返回语义保持一致
- [ ] 重构过程中写的代码符合 `coding-standards`
- [ ] 日志覆盖关键路径（如果之前缺的话趁机补上）
- [ ] 有 code-review 验证改动没有引入新问题

## 与其他 Skill 的关系

| Skill | 关系 |
|-------|------|
| `coding-standards` | 约束：重构过程和结果都要符合编码规范 |
| `code-review` | 上游：review 发现问题后触发重构；重构完后再 review 验收 |
| `table-design` | 协作：涉及表结构调整时参考 |
| `code-write-doc` | 协作：重构后文档可能需要同步更新 |
| `md-optimizer` | 约束：重构涉及的文档更新遵循其 Markdown 规范 |
