## 定位与边界

本 skill 在迭代流程中的位置：

```
需求进来 → requirement-analysis → system-design → 【plan-work】→ 编码 → review → 提测
            产出：需求文档          产出：技术方案+工时    产出：编码实施计划
```

**只管"按什么顺序写代码 + 每步怎么验证"，不管：**
- 需求是什么（交给 `requirement-analysis`）
- 怎么实现、用什么方案（交给 `system-design`）
- 代码怎么写（交给 `coding-standards` 等）
- 代码怎么审（交给 `code-review`）

## 何时使用本 Skill

- 技术方案和工时评估已完成，准备进入编码阶段。
- 用户说"帮我拆一下实施步骤""这个需求先做什么后做什么""排一下编码计划"。
- 多人协作开发，需要明确谁先做什么、谁等谁。
- 改动涉及多个应用/模块，需要确定编码顺序和联调节奏。

**不需要用的场景：** 单人单接口的小需求，直接看技术方案开干。

## 输入要求

1. **技术方案/** 目录（必须有）— 系统设计阶段的产出，包含 README.md、整体架构设计、模块设计、接口清单、表设计等子文档。
2. **评估方案_DOC.md**（必须有）— 从需求拆解 + 技术方案提取的评估标准，编码完成后由 evaluator 验证。
3. **工时评估_DOC.md**（必须有）— 到接口/字段级的工时明细、责任人、里程碑。
4. **当前代码库** — 需要读代码确认实际情况，而非只看文档。

## 输出交付物

归档到迭代目录（与前序文档同目录）：

```
yyyyMMdd_迭代主题/
├── README.md                       ← requirement-analysis 产出（迭代看板）
├── 01-原始需求_DOC.md              ← requirement-analysis 产出
├── 02-需求拆解_DOC.md              ← requirement-analysis 产出
├── 04-技术方案/                    ← system-design 产出
├── 05-评估方案_DOC.md              ← system-design 产出
├── 06-工时评估_DOC.md              ← system-design 产出
└── 07-编码实施计划_DOC.md          ← 本 skill 产出
```

> 编号即 SOP 阶段流转顺序，缺位跳号不补位。详见 `code-write-doc` skill 的"命名规范"。

> 模板：`references/编码实施计划_DOC_模板.md`

## 自动化原则

**默认自动执行，有问题才告警让人介入。**

```
┌─────────────────────────────────────────────────────────────┐
│  编码规划完成后：                                            │
│  ─────────────────────────────────────────────────────────  │
│  1. 自动检查：结构完整性、步骤拆分粒度、验证点、依赖关系    │
│  2. 无问题 → 自动进入编码阶段                               │
│  3. 有问题 → 告警，等待人处理                                │
└─────────────────────────────────────────────────────────────┘
```

### 自动检查清单

| 检查项 | 通过条件 | 不通过处理 |
|--------|---------|-----------|
| 实施计划结构完整 | 所有章节已填写 | 🚨 告警：补全缺失章节 |
| 步骤拆分到文件/方法级 | 每个步骤有具体文件 | 🚨 告警：细化步骤 |
| 依赖关系无冲突 | 无循环依赖 | 🚨 告警：修复依赖 |
| 验证点覆盖核心链路 | MVP 场景有验证节点 | 🚨 告警：补充验证点 |

### 告警规则

只有以下情况才需要人介入：

1. **🚨 技术方案有待确认项** — 需要回 system-design 确认
2. **🚨 依赖关系冲突** — A 等 B，B 等 A
3. **🚨 工时评估与方案不匹配** — 任务遗漏或工时偏差大

### 自动进入下一阶段

以上检查全部通过后，**自动进入编码阶段**，不需要人确认。

```
检查通过 → 自动进入编码阶段（按实施计划执行）
检查不通过 → 告警，等待人处理 → 处理后自动进入下一阶段
```

## 工作流程

### 1) 读技术方案，梳理依赖关系

- 读 `技术方案/` 目录下的所有设计文档，理清各场景之间的依赖（哪个场景的接口是其他场景的前置）。
- 读 `工时评估_DOC.md`，确认每项任务的责任人和工时。
- 读 `评估方案_DOC.md`，确认编码完成后需要验证的评估项。
- **读实际代码**，确认技术方案中描述的现状是否准确（方案可能写完后代码有变动）。

### 2) 确定编码顺序

按以下原则排序：

1. **基础设施先行** — 建库建表、申请资源、配置中心等必须最先完成。
2. **被依赖的先做** — 如果 B 接口依赖 A 接口，A 先做。
3. **核心链路优先** — P0 场景的核心链路先做，保证 MVP 可跑通。
4. **同一人的任务连续排** — 减少上下文切换。
5. **可并行的标出来** — 不同人负责的无依赖任务可以并行。

### 3) 拆分为编码步骤

每个步骤需要明确：

| 要素 | 说明 |
|------|------|
| **步骤编号** | 全局顺序编号（Step 1、Step 2...） |
| **所属场景** | 对应技术方案中的哪个场景 |
| **开发内容** | 具体做什么（新建表/写接口/加缓存...） |
| **涉及文件** | 预计改动或新建哪些文件/类 |
| **责任人** | 谁来做 |
| **预计工时** | 从工时评估中带过来 |
| **前置依赖** | 依赖哪个步骤完成后才能开始 |
| **验证方式** | 这一步做完怎么验证（自测接口/跑单测/数据验证...） |
| **产出物** | 完成后交付什么（接口可调用/表已建好/配置已生效...） |

### 4) 定义验证节点

在关键步骤后设置验证节点（checkpoint）：

- **基础设施验证** — 库表建好、资源申请到位、配置生效。
- **核心链路验证** — MVP 场景从头到尾跑通。
- **联调验证** — 前后端/跨服务联调通过。
- **全链路验证** — 所有场景跑通，准备提测。

### 5) 标注风险与应对

从技术方案和工时评估中的风险项，映射到具体步骤：
- 哪些步骤可能卡住（等资源、等对方接口、技术难点）。
- 卡住了怎么办（先用 Mock、先做其他步骤、找谁协调）。

### 6) 问答闸门（有不确定就问）

在输出实施计划前，如果发现：
- 技术方案中有待确认项还没解决。
- 工时评估中有未指定责任人的任务。
- 依赖关系有冲突（A 等 B，B 等 A）。
- 资源申请/业务方对接还没完成。

**先提出来，问清楚再排计划。**

## 实施计划拆分原则

### 步骤粒度

- **最小粒度**：一个接口 / 一张表 / 一个缓存 key 的实现。
- **最大粒度**：不超过 4 小时工作量。超过的要继续拆。
- **原则**：每个步骤做完后，应该有一个可验证的产出。

### 并行标注

```
Step 1: 建表（张三）          ──┐
Step 2: 申请 Redis（张三）     ──┤── 基础设施阶段
Step 3: 配置中心初始化（张三）  ──┘

Step 4: 接口 A 开发（张三）    ──┐── 可并行
Step 5: 前端页面 A 开发（李四） ──┘

Step 6: 前后端联调 A（张三+李四）── 依赖 Step 4 + Step 5
```

### 编码规范提醒

每个步骤在编码时需遵守：
- `coding-standards` — 编码规范（命名/日志/外部调用/性能/安全，全维度覆盖）
- `table-design` — 建表规范（如涉及）

## Checkpoint 检查

编码规划完成后，**自动运行检查点验证产出物质量**：

### 检查项清单

| 检查 ID | 描述 | 类型 | on_fail | 说明 |
|---------|------|------|---------|------|
| P01 | 实施计划结构完整 | structure | warn | 实施步骤 + 验证点 |
| P02 | 包含文件/类/方法级别任务拆解 | ai_check | warn | AI 验证步骤粒度 |
| P03 | 每个步骤有明确的完成标准 | content | warn | 检查验证方式 |
| P04 | 包含依赖关系说明 | structure | warn | 依赖关系章节 |
| P05 | 风险识别和应对措施 | content | warn | 风险/注意事项 |
| P06 | 包含责任人分配 | structure | warn | 多人协作时必须 |
| P07 | 步骤有优先级或顺序标识 | content | warn | 编号/优先级/顺序 |

### 执行检查

```bash
# 运行检查点
scripts/checkpoint/run-checkpoint.sh plan-work doc/需求迭代/{迭代目录}

# 查看检查结果
cat doc/需求迭代/{迭代目录}/.claude/checkpoint-result.json
```

### 检查结果处理

| 结果 | 处理方式 |
|------|---------|
| 全部通过 | 自动进入编码阶段 |
| 有警告 (warn) | 记录到问题池，继续执行 |
| 有阻塞 (block) | 必须修复后才能继续 |

## PROCESS.md 状态更新

> PROCESS.md 由 requirement-analysis 阶段创建，位置：`.claude/processes/{迭代目录名}/PROCESS.md`

### 更新规则

1. **阶段开始**：更新 plan-work 状态为 `in_progress`，记录开始时间
2. **产出物完成**：更新编码实施计划_DOC.md 状态
3. **Checkpoint 检查**：记录检测轮次和结果
4. **发现问题**：添加到 Issue Pool
5. **问题修复**：更新 Issue Pool 状态
6. **阶段完成**：更新状态为 `done`，记录完成时间

### 状态示例

```markdown
| 阶段 | 状态 | 开始时间 | 完成时间 | 检查轮次 |
|------|------|---------|---------|---------|
| requirement-analysis | done | 2026-04-10 10:00 | 2026-04-10 12:00 | 1 |
| system-design | done | 2026-04-10 14:00 | 2026-04-10 16:00 | 1 |
| plan-work | done | 2026-04-10 16:30 | 2026-04-10 17:00 | 1 |
```

### Hook 触发条件

设置 `need_hook = true` 时，会话结束会触发 hook：
- 自动打开新 tmux pane 继续
- 读取 PROCESS.md 恢复状态
- 继续执行未完成的检查

## 编码阶段协作约定

### 进度同步

- 每完成一个步骤，在实施计划中标注状态（待开始 / 进行中 / 已完成 / 阻塞）。
- 遇到阻塞及时标注原因和预计解除时间。

### 方案偏差处理

编码过程中发现和技术方案不一致的情况：
- **小偏差**（字段名调整、参数顺序变化）：直接改，编码完成后同步更新技术方案。
- **中偏差**（接口拆合、缓存策略变更）：先在实施计划中记录偏差原因，继续编码，完成后统一更新技术方案。
- **大偏差**（架构调整、方案推翻）：**停下来**，回到 system-design 重新评估，更新技术方案后再继续。

### 联调节奏

- 后端先行，接口开发完成后提供 Mock 或测试环境供前端对接。
- 跨服务联调需要提前约好时间窗口，避免双方空等。
- 联调问题及时记录，不要口头解决后忘记。

## 与其他 Skill 的关系

| Skill | 关系 |
|-------|------|
| `system-design` | 上游：技术方案和工时评估是本 skill 的输入 |
| `requirement-analysis` | 上上游：需求文档是整个流程的起点 |
| `work-spec` | 约束：编码时遵守全局规范 |
| `coding-standards` | 约束：编码规范（含 Java 专项、外部调用、可观测性等） |
| `table-design` | 约束：建表遵守其规范 |
| `md-optimizer` | 约束：产出的 `编码实施计划_DOC.md` 必须符合其 Markdown 规范 |
| `code-review` | 下游：编码完成后进入 review |
| `git-commit` | 下游：代码提交遵守其规范 |

> 产出风格遵循 `work-spec`：大白话说明白、结构清晰、必要时用 Mermaid，一图胜千言。
