## 定位

**检查依据就是 `coding-standards` 和 `constitution`**。本 skill 管的是 review 的**流程和输出格式**，不重复写编码规则。

**核心原则：两阶段审查，自动执行，有问题才告警。**

```
┌─────────────────────────────────────────────────────────────┐
│                     自动化 Review 流程                       │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   第一阶段：规范合规审查（自动）                             │
│   ────────────────────────────────────────                  │
│   • 对照技术方案自动检查                                     │
│   • 无问题 → 自动进入第二阶段                                │
│   • 有问题 → 🚨 告警，等待人处理                            │
│                                                             │
│   第二阶段：代码质量审查（自动）                             │
│   ────────────────────────────────────                      │
│   • 按 coding-standards 自动检查                            │
│   • 无 P0/P1 → 自动通过，允许合并                           │
│   • 有 P0/P1 → 🚨 告警，等待人处理                          │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

**人只处理告警，不参与正常流程。**

## 何时触发

- 用户说"帮我 review 一下""给个结论和改动建议""这段代码靠谱么"。
- 用户说"检查一下代码质量""上生产前过一遍"。
- 需要输出结构化的 review 报告时。

## 输入要求

开始 review 前先确认：

- **目标**：这次 review 要解决什么（可读性/稳定性/性能/安全/排障能力）。
- **范围**：具体到目录/文件/类/接口，避免全仓库乱扫。
- **行为约束**：是否允许改接口契约/业务语义（默认不允许）。
- **技术方案**：是否有对应的技术方案文档（用于规范合规审查）。

缺了就先问。

### 告警规则

只有以下情况才告警让人介入：

| 级别 | 问题类型 | 处理方式 |
|------|---------|---------|
| 🚨 P0 | 安全漏洞、数据错误、核心链路不可用 | 阻塞，必须人处理 |
| 🚨 P1 | 边界不清、异常吞掉、耦合严重 | 阻塞，必须人处理 |
| ⚠️ P2 | 可维护性差、命名差 | 自动记录，不阻塞 |
| ⚠️ P3 | 风格问题 | 自动记录，不阻塞 |

### 自动通过条件

```
第一阶段无问题 + 第二阶段无 P0/P1 = 自动通过
```

### 自动进入下一阶段

审查通过且 checkpoint 验证通过后，**自动进入 dev-handoff 阶段**（生成提测交付文档），不需要人确认。

```
审查通过 + checkpoint 通过 → 自动进入 dev-handoff
有 P0/P1 → 告警，回到编码阶段修复
```

## 第一阶段：规范合规审查（Spec Compliance）

### 目的

确保"实现的是正确的东西"，而不是"正确地实现了错误的东西"。

### 检查清单

#### 1. 技术方案对照

| 检查项 | 是否符合 | 说明 |
|--------|---------|------|
| 接口路径是否与技术方案一致？ | ✅ / ❌ | |
| 请求参数是否与技术方案一致？ | ✅ / ❌ | |
| 响应结构是否与技术方案一致？ | ✅ / ❌ | |
| 错误码是否与技术方案一致？ | ✅ / ❌ | |

#### 2. 范围边界检查

| 检查项 | 是否符合 | 说明 |
|--------|---------|------|
| 是否实现了技术方案中不存在的功能？ | ✅ / ❌ | 超出范围 = 过设计 |
| 是否遗漏了技术方案中的功能？ | ✅ / ❌ | 遗漏 = 欠设计 |
| 是否有"顺便"加的功能？ | ✅ / ❌ | 未经审批的加塞 |

#### 3. Constitution 合规

| 检查项 | 是否符合 | 说明 |
|--------|---------|------|
| 服务边界是否正确？ | ✅ / ❌ | 参考 constitution Article I |
| 接口版本是否正确？ | ✅ / ❌ | 参考 constitution Article II |
| 是否有未声明的 constitution 违反？ | ✅ / ❌ | |

### 第一阶段输出

```markdown
## 第一阶段：规范合规审查

### 技术方案对照

| 项目 | 技术方案 | 实际实现 | 是否一致 |
|------|---------|---------|---------|
| 接口路径 | /api/v1/xxx | /api/v1/xxx | ✅ |
| 参数 A | 必填 | 必填 | ✅ |
| 参数 B | 可选 | ❌ 缺失 | ❌ |

### 范围边界

| 类型 | 内容 | 处理建议 |
|------|------|---------|
| 遗漏 | {遗漏的功能点} | 需补充 |
| 超出 | {多余的功能点} | 需删除或追加方案 |

### Constitution 合规

- 服务边界：{符合 / 不符合，原因}
- 接口版本：{符合 / 不符合，原因}

### 第一阶段结论

- [ ] ✅ 通过，进入第二阶段
- [ ] ❌ 不通过，需修改后重新审查

**不通过原因**：{}
```

## 第二阶段：代码质量审查（Code Quality）

### 前置条件

**第一阶段必须通过**。如果第一阶段有问题，先修完再来。

### 检查维度

对照 `coding-standards` 的编码自检清单，逐维度过：

| 维度 | 检查重点 |
|------|---------|
| 通用编码 | 命名/结构/注释/文件方法粒度 |
| 外部调用 | 封装/超时/耗时日志/降级 |
| 数据层 | N+1/索引/事务/缓存一致性/消息幂等 |
| 可观测性 | 新增/修改业务分支可辨识、decision/result、reason、关键依据、业务标识、traceId、耗时 |
| 异常处理 | 吞异常/错误码/降级/重试 |
| 性能并发 | 线程池/锁/批处理/资源释放 |
| 安全 | 输入校验/鉴权/注入防护 |

### 第二阶段输出

```markdown
## 第二阶段：代码质量审查

### 问题清单

| # | 等级 | 问题 | 影响 | 位置（文件:行号） |
|---|------|------|------|------------------|
| 1 | P0 | {现象} | {影响} | `XxxService.java:120` |
| 2 | P1 | {现象} | {影响} | `YyyController.java:45` |

### 改动建议

按落地顺序排列：

1. {建议 1}（到类/方法粒度）
2. {建议 2}

### 第二阶段结论

- [ ] ✅ 通过，允许合并
- [ ] ❌ 不通过，需修改后重新审查
```

---

## 问题分级

| 等级 | 含义 | 示例 |
|------|------|------|
| **P0** | 会出事故 | 安全漏洞、数据错误、核心链路不可用、无法排障 |
| **P1** | 高概率埋雷 | 边界不清、异常吞掉、耦合导致改一处崩一片 |
| **P2** | 可维护性差 | 大方法、命名差、重复多、阅读成本高 |
| **P3** | 风格与一致性 | 格式、轻微命名、小优化 |

**规范合规问题统一为 P0 或 P1**：遗漏核心功能 = P0，多余功能 = P1。

## 测试检查

review 时对测试的检查要求：

### 必备用例类型

- **正常流程**（happy path）
- **参数校验**：必填/格式/边界值/空值
- **异常流程**：外部系统失败/超时/返回非法数据
- **幂等**：重复请求/重复消息（如适用）
- **并发**：同资源并发更新/重复消费（如适用）
- **兼容性**：字段缺省、默认值、老版本请求（如适用）

### 测试策略

- 优先**接口级测试**：模拟真实请求，验证返回与副作用。
- 只在必要时补单测：复杂规则、分支爆炸、纯函数型计算。
- 给出用例清单和建议命令，默认不在不确定环境里强跑。

## Checkpoint 检查

代码评审完成后，**自动运行检查点验证审查质量**：

### 检查项清单

| 检查 ID | 描述 | 类型 | on_fail | 说明 |
|---------|------|------|---------|------|
| CR01 | 第一阶段：规范合规审查通过 | ai_check | block | 对照技术方案无偏差 |
| CR02 | 第二阶段：代码质量审查无 P0/P1 | ai_check | block | coding-standards 合规 |
| CR03 | 代码符合 coding-standards | ai_check | block | 按 8 维度逐项检查；缺少部署后分支可观测性时禁止通过 |
| CR04 | 代码符合 constitution | ai_check | block | 项目宪法合规 |

#### CR03 详细检查维度

CR03 对照 `coding-standards` 的 **8 个规范维度**逐项验证：

| # | 维度 | AI 检查要点 | 必须通过 |
|---|------|------------|---------|
| 1 | 通用编码 | 命名语义清晰、文件 ≤1000 行、方法 ≤150 行、分层正确、接口注入 | 是 |
| 2 | 外部调用 | HTTP/RPC 有超时配置、耗时日志、失败降级 | 涉及时 |
| 3 | 数据层 | 无 N+1、有索引、缓存一致性、消息幂等 | 涉及时 |
| 4 | 可观测性 | 新增/修改业务分支可通过 INFO 及以上日志识别 decision/result、reason 和关键依据，traceId 透传，E2E 已核对日志 | 是 |
| 5 | 异常处理 | 无吞异常、错误码合理、有兜底逻辑 | 是 |
| 6 | 性能并发 | 无大循环 IO、线程池配置合理、连接池正确 | 涉及时 |
| 7 | 安全编码 | 输入校验、权限校验、无注入风险 | 是 |
| 8 | 测试 | 核心链路有接口级测试、修改的接口有对应测试 | 是 |

> **"涉及时"** 的维度：如果改动不涉及 HTTP/DB/MQ/并发等，该维度自动跳过。

### 执行检查

```bash
# 运行检查点
scripts/checkpoint/run-checkpoint.sh code-review doc/需求迭代/{迭代目录}

# 查看检查结果
cat doc/需求迭代/{迭代目录}/.claude/checkpoint-result.json
```

### 检查结果处理

| 结果 | 处理方式 |
|------|---------|
| 全部通过 | 自动进入 dev-handoff 阶段（提测交付文档） |
| 有警告 (warn) | 记录到问题池，继续执行 |
| 有阻塞 (block) | 必须修复后才能继续，回到编码阶段 |

## PROCESS.md 状态更新

> PROCESS.md 由 requirement-analysis 阶段创建，位置：`.claude/processes/{迭代目录名}/PROCESS.md`

### 更新规则

1. **阶段开始**：更新 code-review 状态为 `in_progress`，记录开始时间
2. **产出物完成**：更新 review 报告状态
3. **Checkpoint 检查**：记录检测轮次和结果
4. **发现问题**：添加到 Issue Pool（P0/P1 阻塞，P2/P3 记录）
5. **问题修复**：修复后重新审查，更新 Issue Pool 状态
6. **阶段完成**：更新状态为 `done`，记录完成时间

### 状态示例

```markdown
| 阶段 | 状态 | 开始时间 | 完成时间 | 检查轮次 |
|------|------|---------|---------|---------|
| ... | ... | ... | ... | ... |
| code-review | done | 2026-04-11 10:00 | 2026-04-11 11:00 | 1 |
| dev-handoff | pending | | | |
```

### Hook 触发条件

设置 `need_hook = true` 时，会话结束会触发 hook：
- 自动打开新 tmux pane 继续
- 读取 PROCESS.md 恢复状态
- 继续执行未完成的审查

## 修复验证闭环

**核心原则：评审不是终点，"评审问题的修复全部通过验证"才是终点。**

### 问题

当前流程中，code-review 发现问题后修复，但没有强制重跑验证。这导致：
- 修复本身可能引入新问题（最常见的回归来源）
- 评审提了 N 个问题，可能只修了 N-1 个，没人追踪
- 修复后直接进 dev-handoff，跳过了验证闭环

### 闭环流程

```
┌──────────────────────────────────────────────────────────────┐
│                     修复验证闭环                              │
│                                                              │
│  代码评审 → 发现 P0/P1 问题                                  │
│      │                                                       │
│      ▼                                                       │
│  ┌──────────────────────┐                                   │
│  │ 修复问题             │                                   │
│  │ • 逐条修复所有 P0/P1 │                                    │
│  │ • P2/P3 可选修复     │                                    │
│  └──────────┬───────────┘                                   │
│             │                                               │
│             ▼                                               │
│  ┌──────────────────────┐                                   │
│  │ 问题追踪表更新       │                                   │
│  │ • 标记每条修复状态   │                                    │
│  │ • 未修复项说明原因   │                                    │
│  └──────────┬───────────┘                                   │
│             │                                               │
│             ▼                                               │
│  ┌──────────────────────┐                                   │
│  │ 重跑 evaluator       │ ← 关键：修复后必须重新验证         │
│  │ • 跑追踪矩阵验证脚本 │                                    │
│  │ • 检查修复未引入回归 │                                    │
│  └──────────┬───────────┘                                   │
│             │                                               │
│             ▼                                               │
│  全部通过？ ────否───► 回到修复步骤                          │
│      │                                                       │
│     是                                                       │
│      │                                                       │
│      ▼                                                       │
│  修复验证闭环完成 → 进入 dev-handoff                         │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 问题追踪表

评审发现问题后，自动生成问题追踪表，修复过程中逐条更新：

```markdown
## 评审问题追踪表

| # | 等级 | 问题描述 | 位置 | 修复状态 | 验证结果 | 备注 |
|---|------|---------|------|---------|---------|------|
| 1 | P0 | {问题} | Xxx.java:120 | ✅ 已修复 | ✅ 验证通过 | |
| 2 | P1 | {问题} | Yyy.java:45 | ✅ 已修复 | ❌ 引入回归 | 需重新修复 |
| 3 | P2 | {问题} | Zzz.java:78 | ⏭️ 延后 | — | 不阻塞，下迭代处理 |
```

### 验证要求

1. **所有 P0/P1 必须修复**：不修复 = 评审不通过
2. **每条修复必须验证**：修复后跑对应的追踪矩阵验证脚本
3. **回归检查**：修复后重跑 evaluator，确认未引入新问题
4. **P2/P3 可延后**：标记"延后"并说明原因，不阻塞流程
5. **闭环标准**：所有 P0/P1 修复 + evaluator 全部通过 = 修复验证闭环完成

### 自动进入下一阶段

```
修复验证闭环完成 + checkpoint 通过 → 自动进入 dev-handoff 阶段
有 P0/P1 未修复 → 阻塞，回到修复步骤
```
