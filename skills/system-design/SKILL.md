## 定位与边界

本 skill 在迭代流程中的位置：

```
需求进来 → requirement-analysis → 【system-design】→ plan-work → 编码
            产出：原始需求 + 需求拆解    产出：技术方案 + 工时评估
```

**只管"怎么实现 + 多少工时"，不管：**
- 需求是什么（交给 `requirement-analysis`）
- 改哪些文件、什么顺序做（交给 `plan-work`）
- 代码怎么写（交给 `coding-standards` 等）

## Constitution 检查（自动执行）

在技术方案生成时自动检查 `constitution` 中的相关约束，**有问题才告警**。

### 自动检查项

| 检查项 | 通过条件 | 不通过处理 |
|--------|---------|-----------|
| 服务边界正确 | 不违反 Article I | 🚨 告警：服务边界违规 |
| 接口版本正确 | 符合 Article II | 🚨 告警：需要版本号 |
| 敏感数据处理 | 符合 Article V | 🚨 告警：缺少安全方案 |
| 数据层设计 | 符合 Article VI | 🚨 告警：事务/缓存问题 |

### 违反处理

```
┌─────────────────────────────────────────────────────────────┐
│  Constitution 检查流程：                                     │
│  ─────────────────────────────────────────────────────────  │
│  1. 自动检查所有条款                                         │
│  2. 无违反 → 自动继续                                        │
│  3. 有违反 → 记录到方案中 + 继续执行（不阻塞）               │
│                                                             │
│  只有 P0 级别违反才告警让人确认                              │
└─────────────────────────────────────────────────────────────┘
```

### 自动进入下一阶段

技术方案 + 工时评估 + 评估方案生成后，**自动调用 plan-work**，不需要人确认。

评估方案_DOC.md 的生成规则：
1. 从 需求拆解_DOC.md 提取验收标准 → 填入"功能正确性"维度
2. 从技术方案各子文档提取设计目标 → 填入对应维度（安全/性能/可观测性）
3. 从 coding-standards 提取通用规则 → 填入"可维护性"维度
4. 根据本次迭代特点决定哪些维度适用（小迭代只查功能正确性 + 可维护性）
5. 模板参见 `references/评估方案_DOC_模板.md`

> **兜底**：如果 evaluator 模板不可用，按以下最小结构生成评估方案：
> - 评估维度（功能正确性 + 可维护性，至少这两个）
> - 每个维度包含：检查项清单 + 通过条件 + 优先级
> - 生成失败不阻塞流程，记入 Issue Pool 作为 P2 警告

告警条件（才需要人介入）：
1. **🚨 Constitution 严重违反**：安全/数据层问题
2. **🚨 外部依赖不可用**：需要人协调
3. **🚨 技术选型存疑**：多个方案差异大，需要人决策

## 何时使用本 Skill

- 用户说"先出个技术方案""帮我设计一下""这个需求怎么实现比较好""评估下工时"。
- 需求涉及：跨服务调用、新接口定义、数据模型变更、技术选型、性能方案。
- 改动范围超过单个服务或单个模块。
- 需要和其他开发对齐技术方案再动手。

**不需要用的场景：** 改一个字段、修一个 bug、加一行日志这类明确的小需求，直接进 `plan-work` 或动手写。

## 输入要求

1. **需求拆解文档**：`需求拆解_DOC.md`（必须有，这是本 skill 的输入）。
2. **现有架构**：当前系统的服务拓扑、技术栈、关键依赖。
3. **约束条件**：性能要求、时间约束、兼容性、基础设施限制。
4. **团队信息**：参与开发的人员名单（用于工时评估中指定责任人）。

## 文档结构选择

| 条件 | 文档结构 |
|------|---------|
| 跨服务调用 / 新服务 / 新模块 | 完整版 |
| 涉及性能要求（QPS > 1000 / P99 < 100ms） | 完整版 |
| 涉及敏感数据 / 对外接口 | 完整版（含 05_安全设计.md） |
| 单服务 / ≤ 3 个接口 / 无特殊要求 | 简化版 |

**判断流程：**

```
1. 是否跨服务？
   ├─ 是 → 完整版
   └─ 否 ↓

2. 是否有性能要求（QPS > 1000 / P99 < 100ms）？
   ├─ 是 → 完整版（含 04_性能设计.md）
   └─ 否 ↓

3. 是否涉及敏感数据或对外接口？
   ├─ 是 → 完整版（含 05_安全设计.md）
   └─ 否 ↓

4. 接口数量 ≤ 3？
   ├─ 是 → 简化版
   └─ 否 → 完整版
```

## 技术方案设计流程

### 1) 判断文档结构

根据"文档结构选择"章节，判断使用完整版还是简化版。

### 2) 创建 README.md

先建索引，标明需要哪些文档，明确责任人和状态。

### 3) 读代码、画现有流程（不能跳过）

- 读仓库地图（`AGENTS.md`、`README.md`）搞清楚服务边界。
- **读涉及模块的代码**，找到关键类/方法/调用链路。
- 画出**现有**的调用关系和数据流（Mermaid）。
- 记录历史逻辑和技术债，评估对新方案的影响。

### 4) 按顺序产出各文档

```
完整版生成顺序：
1. README.md              ← 先建索引
2. 01_整体架构设计.md      ← 先画大图
3. 02_模块设计/           ← 再拆细节（按模块逐个）
4. 03_数据流设计.md       ← 数据怎么流转
5. 04_性能设计.md         ← 性能目标（如有要求）
6. 05_安全设计.md         ← 安全相关（如有敏感数据/对外接口）
7. 06_可观测性设计.md     ← 日志监控（必须有）
8. 07_运行管理控制设计.md ← 管理后台（如有）
9. 接口清单.md            ← 从模块设计中汇总
10. 表设计.md             ← 从模块设计中汇总

简化版生成顺序：
1. README.md
2. 01_整体设计.md         ← 合并版
3. 06_可观测性设计.md
4. 接口清单.md
```

### 5) 汇总检查

完成所有文档后，过一遍"设计检查清单"。

### 6) 生成评估方案_DOC.md

**此步骤不可跳过。** 按以下流程生成：

1. 读取 `references/评估方案_DOC_模板.md` 获取模板结构
2. 从 `需求拆解_DOC.md` 提取验收标准（Given-When-Then）→ 填入"功能正确性"维度
3. 从技术方案各子文档提取设计目标 → 填入对应维度（安全/性能/可观测性）
4. 从 `coding-standards` 提取通用规则 → 填入"可维护性"维度
5. 根据本次迭代特点决定维度适用范围：
   - 改一个字段/修 bug → 只含 功能正确性 + 可维护性
   - 新增接口 → 全维度
   - 性能优化 → 重点查 性能 + 可维护性
6. 将评估方案写入迭代目录：`{迭代目录}/评估方案_DOC.md`

> **兜底**：模板不可用时，按最小结构生成（功能正确性 + 可维护性 + 通过条件），不阻塞流程，记入 Issue Pool 作为 P2 警告。

## 工时评估流程

基于技术方案，按以下步骤评估：

1. **按场景拆任务** — 每个场景拆成具体的开发任务。
2. **到接口/字段级** — 每个任务明确涉及哪个接口、哪个字段。
3. **标注责任人** — 具体到人名（张三、李四）。
4. **估算小时数** — 每个任务估到小时。
5. **加联调时间** — 前后端联调、跨服务联调单独列。
6. **加自测提测** — 自测时间、提测准备时间。
7. **定里程碑** — 方案评审/开发完成/联调完成/提测的时间节点。
8. **加 buffer** — 开发工时的 15-20% 作为不可预见事项预留。

技术方案和工时评估完成后，过一遍：

**Constitution 合规：**
- [ ] 服务边界是否符合 constitution Article I？
- [ ] 接口版本是否符合 constitution Article II？
- [ ] 安全设计是否符合 constitution Article V？
- [ ] 数据层设计是否符合 constitution Article VI？
- [ ] 如有违反，是否已声明？

**架构设计：**
- [ ] 读过现有代码了吗？现有流程图画了吗？历史逻辑梳理了吗？
- [ ] 整体架构图（服务拓扑）画了吗？
- [ ] 技术选型有对比吗？理由充分吗？
- [ ] 依赖关系的 SLA 和降级方案确认了吗？

**模块设计：**
- [ ] 每个模块都有设计文档吗？
- [ ] 核心流程图（时序图）画了吗？
- [ ] 类/方法设计清晰吗？

**数据设计：**
- [ ] 数据流向图画了吗？
- [ ] 缓存设计是否覆盖了更新策略、过期策略、一致性保证？
- [ ] 消息设计是否覆盖了消费失败处理？
- [ ] 表设计是否完整（字段/索引/迁移）？遵循 table-design 规范吗？

**性能设计（如有要求）：**
- [ ] 性能目标明确吗（QPS/响应时间）？
- [ ] 瓶颈分析做了吗？
- [ ] 限流/降级/熔断方案设计了吗？

**安全设计（如有敏感数据/对外接口）：**
- [ ] 认证鉴权规则明确吗？
- [ ] 敏感数据的安全方案有了吗？
- [ ] 接口防护（防刷/防重放/参数校验）设计了吗？

**可观测性设计（必须有）：**
- [ ] 关键日志打点位置确定了吗？
- [ ] traceId 传递方案确定了吗？
- [ ] 监控指标和告警规则配置了吗？
- [ ] 排障手册写了吗？

**运行管理控制设计（如有需要）：**
- [ ] 运营需要看什么数据？看板设计了吗？
- [ ] 哪些参数需要动态配置？入口在哪里？
- [ ] 应急控制（熔断/降级）入口设计了吗？

**接口设计：**
- [ ] 接口契约是否完整（路径/方法/请求/响应/错误码/幂等/版本）？
- [ ] 客户端各端支持情况确认了吗？接口版本策略定了吗？
- [ ] 测试用例覆盖核心场景了吗？

**上线方案：**
- [ ] 上线步骤、灰度策略、回退方案都有吗？
- [ ] 影响范围列全了吗（避免遗漏联调方）？
- [ ] 开发和测试都能看懂这个方案吗？

**工时评估：**
- [ ] 是否到了接口/字段级别？
- [ ] 每个任务都有具体责任人吗？
- [ ] 联调时间是否单独列出？
- [ ] 里程碑时间节点是否合理？
- [ ] 是否预留了 buffer？

## Checkpoint 检查

技术方案完成后，**自动运行检查点验证产出物质量**：

### 执行检查

```bash
# 运行检查点

cat doc/需求迭代/{迭代目录}/.claude/checkpoint-result.json
```

### 检查结果处理

| 结果 | 处理方式 |
|------|---------|
| 全部通过 | 自动进入 plan-work 阶段 |
| 有警告 (warn) | 记录到问题池，继续执行 |
| 有阻塞 (block) | 必须修复后才能继续 |

## PROCESS.md 状态更新

> PROCESS.md 由 requirement-analysis 阶段创建，位置：`.claude/processes/{迭代目录名}/PROCESS.md`

### 更新规则

完成以下操作后更新 PROCESS.md：

1. **阶段开始**：更新 system-design 状态为 `in_progress`，记录开始时间
2. **产出物完成**：更新关键产出物状态（技术方案/、评估方案_DOC.md、工时评估_DOC.md）
3. **Checkpoint 检查**：记录检测轮次和结果
4. **发现问题**：添加到 Issue Pool
5. **问题修复**：更新 Issue Pool 状态
6. **阶段完成**：更新状态为 `done`，记录完成时间

### 状态示例

```markdown
| 阶段 | 状态 | 开始时间 | 完成时间 | 检查轮次 |
|------|------|---------|---------|---------|
| requirement-analysis | done | 2026-04-10 10:00 | 2026-04-10 12:00 | 1 |
| system-design | done | 2026-04-10 14:00 | 2026-04-10 16:00 | 1 |
```

### Hook 触发条件

设置 `need_hook = true` 时，会话结束会触发 hook：
- 自动打开新 tmux pane 继续
- 读取 PROCESS.md 恢复状态
- 继续执行未完成的检查

## 与其他 Skill 的关系

| Skill | 关系 |
|-------|------|
| `constitution` | 约束：技术方案必须符合项目宪法 |
| `requirement-analysis` | 上游：需求拆解文档是本 skill 的输入 |
| `evaluator` | 下游：产出评估方案_DOC.md，编码完由 evaluator 按方案验证 |
| `plan-work` | 下游：技术方案确定后，拆成实施步骤 |
| `table-design` | 协作：数据模型设计遵循其规范 |
| `coding-standards` | 约束：编码时按其规范落地（含外部调用、数据层、可观测性等） |
| `mermaid-visualizer` | 工具：流程图/时序图的画图能力 |
| `md-optimizer` | 约束：产出的 `*_DOC.md` 必须符合其 Markdown 规范（TOC/标点/结构/元信息） |
| `code-review` | 呼应：设计阶段提前考虑 review 关注的点 |

> 产出风格遵循 `work-spec`：大白话说明白、结构清晰、必要时用 Mermaid，一图胜千言。
