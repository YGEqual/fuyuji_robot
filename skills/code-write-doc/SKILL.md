## 定位

管"代码和文档之间的对齐"——代码改了，文档就得跟着改；新代码写了，文档就得跟着建。

## 何时触发

- 空项目/新项目要搭文档中心（`/api-doc`）。
- 代码改动后，需要同步更新对应 `*_DOC.md`。
- 需要为某个代码文件新写文档并接入文档中心。

## 统一约定

1. **结果只产出 Markdown 文件**（`*.md`），不强制依赖 Swagger/OpenAPI。
2. **文档与代码尽量一一对应**：Controller/Router/Handler/Service/Job/Script 都可以对应一份文档。
3. **命名规则**：`<代码文件基础名>_DOC.md`
   - `TrainAssistantController.java` → `TrainAssistantController_DOC.md`
   - `order_service.py` → `order_service_DOC.md`
4. **文档位置**（选一种并保持一致）：
   - A. 与代码文件同目录（最容易维护）。
   - B. 集中在 `doc/` 下，目录结构模拟代码结构。

`README.md` 是目录说明文件的固定例外，不使用 `*_DOC.md` 后缀。通用适用范围和内容要求以 `work-spec` 的“目录 README 规范”为准。

## 目录 README 管理

创建目录或显著调整目录职责时，执行以下步骤：

1. 先读父级 README、项目结构和目录内文件，确认职责边界；不要根据目录名猜用途。
2. 目录缺少说明且符合 `work-spec` 的适用条件时创建 `README.md`；已有 README 时直接补充，不创建 `DIRINFO.md`。
3. 按实际需要写入：用途、允许放入、禁止放入、目录结构或关键文件、常用命令、输入输出或产物位置。
4. 检查 README 中的路径和命令可以从声明的工作目录执行，测试目录还要与 `integration-test` 的 unit/integration/contract/e2e 边界一致。
5. 文件移动、改名或入口变化后，用搜索检查仓库内旧路径，并同步父级导航和相关文档引用。

推荐最小模板：

```markdown
# <目录名称>

## 用途

一句话说明该目录负责什么。

## 放置规则

- 可以放：……
- 不应放：……

## 关键内容

| 路径 | 说明 |
|------|------|

## 使用方式

写可直接执行的命令；没有运行入口时省略本节。

## 产物

说明输出位置和是否纳入 Git；没有产物时省略本节。
```

## 日常：代码改动后同步文档

每次代码有"对外可见行为"变化，走以下流程：

1. **明确变化点**（1-3 句话）：新增/删除接口、参数/字段变化、返回结构变化、错误码变化、核心规则变化。
2. **定位对应 `*_DOC.md`**：找不到就走"新建流程"。
3. **逐项核对**：路径/方法/命令、入参（必填/类型/默认值）、出参（字段含义/是否可空）、错误与异常、示例（成功+典型失败）。
4. **更新文档中心注册表/导航**。
5. **自查**：新同事 1-2 分钟能否看懂？字段名/错误码/示例是否与代码一致？

## 新建：为代码文件写文档

### 1) 定位代码单元

选最合适的"对外入口"：HTTP API (Controller) / 消息任务 (Consumer/Job) / 领域服务 / 脚本

### 2) 按模板写文档

推荐结构：

1. 元信息（作者/邮箱/创建时间/更新时间/**tags**）
2. 功能概述（大白话说明白）
3. 接口/命令基本信息（方法/路径/鉴权/限流等）
4. 输入参数（分组：Path/Query/Header/Body）
5. 输出/返回结构（字段说明 + 示例）
6. 错误与异常（错误码、触发条件、是否可重试、排障建议）
7. 业务规则与注意事项
8. **各环境 CURL 示例（必须）**（详见 `references/02-CURL示例与文档链接规范.md`）
9. 变更记录（可选）

### 3) 挂到文档中心

按文档中心方案执行注册（详见 `references/01-文档中心搭建方案.md`）。

## 文档 Tags 规范

**为什么**：快速表达文档主题、支持标签筛选和聚合、方便跨仓库发现相关文档。

**格式**：放在元信息区域，逗号分隔，3-6 个 tag，每个 2-8 个字。

**标准 tag 分类**：

| 分类 | 常用 tags |
|------|-----------|
| **业务领域** | 搜索、推荐、风控、支付、用户、订单、营销、行程、酒店、机票、火车票 |
| **业务场景** | B端、C端、内部工具、数据报表、运营后台 |
| **技术主题** | 缓存、异步、批量、签名、鉴权、限流、降级、重构、性能优化 |
| **架构组件** | Redis、MQ、ES、MySQL、配置中心、网关、MCP |
| **接口类型** | REST-API、RPC、MQ消费、定时任务、WebSocket |
| **文档类型** | 接口文档、设计文档、集成指南、运维手册、故障排查 |

**示例**：
```markdown
## 文档信息
- 作者：DeepTrip Team
- 负责人：按实际负责人填写
- 更新时间：2026-02-13 15:30:00
- tags：搜索, 行程, B端, 已上线
```

## 迭代文档补全（开发完成后必须执行）

开发任务完成后，需要按迭代 SOP 补全文档。目录位置：`doc/需求迭代/yyyyMMdd_迭代主题/`

### 命名规范（强约束，禁止变种）

> **铁律：迭代目录里所有文档命名必须严格用下面的标准名，不要自己起花名。** 变种命名（"编码规划" / "评审" / "测试" / "技术设计"）会让交接、检索、自动化检查全部失效。

**11 份标准命名（按 SOP 阶段排列，编号即 SOP 阶段流转顺序）**：

| 编号 | SOP 阶段 | 标准文件名 | 何时产出 | 必须 |
|------|---------|-----------|---------|------|
| `01` | 1 需求分析 | `01-原始需求_DOC.md` | 产品给 PRD 后存档原文 | ✅ |
| `02` | 1 需求分析 | `02-需求拆解_DOC.md` | 用户故事 + 场景矩阵 + 目标验证追踪矩阵 | ✅ |
| `03` | 1 辅助 | `03-现有体系梳理_DOC.md` | 基线调研（大需求才需要） | ⭕ 可选 |
| `04` | 2 技术方案 | `04-技术方案_DOC.md` 或 `04-技术方案/` 目录 | 单文件用 .md；多模块拆目录 | ✅ |
| `05` | 2 技术方案 | `05-评估方案_DOC.md` | 编码完后由 evaluator 验证的标准 | ✅ |
| `06` | 2 技术方案 | `06-工时评估_DOC.md` | 任务级工时 + 责任人 | ⭕ 可选 |
| `07` | 3 编码规划 | `07-编码实施计划_DOC.md` | Phase 拆步 + 文件 + 验证节点（**不是"编码规划"**） | ✅ |
| `08` | 5 业务验证 | `08-业务验证报告_DOC.md` | 追踪矩阵逐项 PASS/FAIL | ✅ |
| `09` | 6 代码评审 | `09-代码评审_DOC.md` | 评审结论 + 改造建议（**不是"评审"**） | ✅ |
| `10` | 7 交付 | `10-提测交付_DOC.md` | 变更清单 + 测试用例表 + 配置项 | ✅ |
| `11` | 7 交付 | `11-联调文档-{受众}_DOC.md` | 按受众细分，详见下方"联调文档受众细分" | ✅ |
| `12` | 9 回归测试 | `12-测试用例_DOC.md` | 详细测试用例清单（按需，可与测试报告合并） | ⭕ 可选 |
| `13` | 9 回归测试 | `13-测试报告_DOC.md` | 回归用例执行结果 | ✅ |

**编号规则（强约束）**：

- **必须加两位数字前缀 + 横杠**：`01-` `02-` … `13-`（不要写成 `1-` 或 `01_`）
- **编号固定，缺位跳号**：如果某份文档没产出，编号位置直接跳过（看到 `05-评估方案_DOC.md` 紧接 `07-编码实施计划_DOC.md`，能立刻看出 `06-工时评估` 没产出）。**不要把后面文档前移补位**，跳号本身就是一种信号。
- **README 不带编号**：`README.md` 作为迭代看板放在最前，靠 `R` 字母在排序上天然居首。
- **辅助调研用 03 号位**：基线/现状梳理类文档统一占 03 号位，标题用 `03-现有体系xxx_DOC.md` 或 `03-xxx调研_DOC.md`。

**辅助文档（不在标准编号内，命名要清晰）**：

| 文件名 | 用途 |
|--------|------|
| `README.md` | 迭代看板：状态表 + 文档清单 + 变更清单 + 阻塞项 |

### 联调文档受众细分（11 号位）

**铁律：联调文档必须按受众拆分，文件名带受众后缀。** 不同受众关注点完全不同，混在一份文档里要么前端嫌啰嗦，要么外部合作方看不到该看的。

| 受众 | 文件名 | 内容重点 |
|------|--------|---------|
| **前端** | `11-联调文档-前端_DOC.md` | 前端交互时序图、URL/Header 参数、SSE 字段格式、卡片渲染、埋点、UI 状态切换 |
| **外部** | `11-联调文档-外部_DOC.md` | 接口契约（HTTP/REST）、签名鉴权、限流策略、错误码清单、回调约定、SLA |
| **服务端** | `11-联调文档-服务端_DOC.md` | 内部 RPC/HTTP 协议、版本兼容、链路追踪 traceId 透传、降级开关、上下游依赖 |

**规则**：

- 涉及哪类联调就出哪份，**只有一类受众时也必须带后缀**（避免后续补另一份时改名）
- 文档头部固定写 `> 读者：xxx` 一行，再次明确受众
- 跨受众的公共信息（如 QA 环境地址、Token 获取方式）每份各自抄一份，**不要互相 include**——读者拿到一份就要能干活
- 想加新受众类型（如"测试团队联调"）先在本表登记，避免命名发散

**通用规则**：
- 所有迭代文档必须带 `_DOC.md` 后缀（`README.md` 除外）
- 中文文件名，不混拼音/英文（除约定俗成的 README）
- **文件名固定数字前缀 = SOP 阶段顺序（见上表）**，不要另起序号
- **联调文档必须带受众后缀**：`11-联调文档-前端_DOC.md` / `11-联调文档-外部_DOC.md` / `11-联调文档-服务端_DOC.md`
- 自定义辅助文档要选语义清晰的名字（"xxx体系梳理_DOC.md"、"xxx调研_DOC.md"），不要叫"补充_DOC.md"、"其他_DOC.md"

**违规如何处理**：发现已有的迭代目录命名不符合规范（少前缀/变种命名）时，用 `git mv` 改名（保留历史），同步修改文档内部互相引用。

### 必须文档清单（核心字段）

| 文档 | 必须包含 |
|------|---------|
| README.md | 迭代状态表 + 文档清单表 + 代码变更清单 + 测试结果 + 阻塞项 |
| 01-原始需求_DOC.md | 产品原文存档，不改写 |
| 02-需求拆解_DOC.md | 用户故事(验收条件) + 场景矩阵 + **用户交互流程图** |
| 04-技术方案_DOC.md | **整体架构图** + **请求处理流程图** + Redis/DB 设计 + 数据模型变更 + 核心服务 + **降级策略流程图** |
| 07-编码实施计划_DOC.md | Phase 分步 + 每步文件+验证节点 |
| 10-提测交付_DOC.md | 变更清单(含接口字段) + 测试用例表 + 配置项 |
| 11-联调文档-前端_DOC.md | **前端交互时序图** + **核心流程时序图** + 接口字段说明 + QA 测试地址 + 埋点 |
| 11-联调文档-外部_DOC.md | 接口契约 + 签名鉴权 + 限流策略 + 错误码 + 回调约定 + SLA |
| 11-联调文档-服务端_DOC.md | 内部 RPC/HTTP 协议 + 版本兼容 + traceId 透传 + 上下游依赖 |

### 必须包含的图（Mermaid）

**铁律：一图胜千言，每份文档的图要能独立看懂。**

技术方案至少 4 张图：
- 整体架构图（graph TB，模块+服务+存储+外部依赖）
- 请求处理流程图（flowchart TD，完整决策链路）
- 状态流转图（stateDiagram，状态机）
- Redis/DB 关系图（erDiagram）

联调文档至少 2 张图：
- 前端交互时序图（sequenceDiagram，用户→前端→API→存储）
- 核心流程时序图（sequenceDiagram，服务间调用链路）

需求拆解至少 1 张图：
- 用户交互流程图（flowchart 或 sequenceDiagram）

### 画图原则

- 每个节点/连线都要有业务语义标注
- 降级/异常路径必须画出（不能只画 happy path）
- 终端对话用 ASCII art，Markdown 文件里用 Mermaid

## 安全与发布约束

- 默认不在生产环境暴露 `/api-doc`：做环境开关或加鉴权/白名单。
- 文档里禁止明文写敏感信息（token/密码/密钥/真实手机号等）；示例用占位符代替。
