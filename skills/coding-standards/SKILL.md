## 定位

**只要碰代码，就按这个来。** 不管是写新代码、改老代码、还是重构，所有代码最终都要符合这套标准。

不用每次说"注意日志""注意性能""注意异常处理"——说一句"按代码规范来"或"按 coding-standards 检查"，以下全部维度自动覆盖。

## 对话启动规则（跨会话续传）

**如果当前工作目录或其父目录下存在 `.claude/processes/*/PROCESS.md`，或迭代目录下存在 `PROCESS.md`，必须在动手编码前先读取"当前上下文"章节。** 这保证新对话能精确续做，不需要人重新描述"上次做到哪了"。

读取后行为：
1. 了解当前目标、已完成、卡点、下一步
2. 继续从"下一步"开始，不重复已完成的工作
3. 如果发现 PROCESS.md 的上下文与当前任务不符，先问用户确认

## 何时生效

- 写新接口/新功能时
- 修改现有代码时（改到的地方按规范来）
- 重构老代码时（`refactor` 管怎么拆，本规范管拆完的代码质量）
- 代码评审时（`code-review` 的检查依据就是本规范）
- 用户说"按代码规范来""检查一下代码""规范一下"

## 编码自检清单

**写完代码、提交前，过一遍这个清单。** 不需要每条都适用，但每条都要想一下"跟我这次改动有没有关系"。

### 基础项（每次必过）

- [ ] **位置（铁律第一项）**：当前工作目录和分支是目标 worktree 吗？（`pwd` + `git branch --show-current`）同一仓库可能有多个 worktree，搞错了就白干。
- [ ] **分支命名**：新建业务分支统一使用 `vYYYYMMDDHHmm_<type>_<topic>`，例如 `v202609090227_feat_login_timeout`；时间使用上海时区的年月日时分，禁止出现 `/`，语义段使用小写字母、数字和 `_`。`main`、`master` 等既有约定分支不改名。
- [ ] **命名**：变量/方法/类名是否语义清晰，看名字就知道干嘛？
- [ ] **结构**：文件 ≤ 1000 行？方法 ≤ 150 行？职责单一？
- [ ] **分层**：代码放对层了吗？依赖方向正确吗？Controller 里没写业务逻辑吧？
- [ ] **可验收**：真实入口可调用吗？能按“分支 → 触发条件 → 预期日志”核对 QA/生产实际执行路径、数据和副作用吗？
- [ ] **注释**：复杂逻辑有导读注释？非直觉分支有解释？
- [ ] **日志（部署门禁）**：本次新增/修改的业务分支都有 INFO 及以上的决策日志吗？日志能看出 decision/result、reason、关键判断依据、业务标识和 traceId 吗？
- [ ] **异常**：没有吞异常？异常信息够定位问题？有合理的兜底？

### 外部调用（涉及 HTTP/RPC/DB/缓存/MQ/ES/MongoDB/S3 时必过）

- [ ] **隔离封装**：外部调用是否封装在独立类/方法中？
- [ ] **超时配置化**：超时参数是否从配置中心读取，有合理默认值？（存储 SDK 也算网络操作！）
- [ ] **耗时日志**：调用前后是否有日志，包含 costMs + bucket？
- [ ] **网络边界日志**：进来的请求打了 Header 关键字段吗？出去的调用打了入参/httpStatus/响应 Header 吗？
- [ ] **traceId 透传**：链路 ID 是否贯穿？异步线程是否传了 MDC？
- [ ] **截断**：请求/响应日志是否截断？大 JSON 是否用 safeKeyword 截断？
- [ ] **降级**：外部调用失败时有降级方案还是直接崩？（默认不重试，靠日志排障）

### 数据层（涉及 DB/缓存/MQ/ES/MongoDB/文件存储时必过）

- [ ] **N+1**：有没有循环里查数据库？能否批量？
- [ ] **索引**：新增查询是否走索引？是否有慢查询风险？
- [ ] **缓存一致性**：缓存和 DB 的更新顺序对吗？过期策略合理吗？
- [ ] **消息幂等**：消费端是否做了幂等？消费失败怎么处理？
- [ ] **容量预估**：新表/新索引/新 Collection 做了数据量预估吗？有拆分和清理策略吗？

### 质量兜底（核心链路/高风险改动必过）

- [ ] **事务边界**：事务范围是否清晰？有没有长事务？跨资源一致性？
- [ ] **并发安全**：同一资源并发修改怎么处理？线程池配置合理？
- [ ] **性能**：有无明显性能坑（大循环 IO、无界分页、全表扫描）？
- [ ] **安全**：输入校验了吗？权限校验了吗？有注入风险吗？
- [ ] **配置化**：关键参数（超时/阈值/开关）是否支持配置中心动态修改？
- [ ] **真实 E2E**：当前代码对应的应用已启动吗？新增/修改行为有可重复执行的脚本吗？脚本实际跑过并核对日志、数据和副作用了吗？（详见 `references/08-测试规范.md` 和 `integration-test`）

## 语言专项

通用规范适用于所有语言。遇到语言特定的规则时，参考对应章节：

- **Java**：`references/01-通用编码规范.md` 中的"Java 专项规则"章节
  - 配置中心用 `ConfigCenterUtil`，禁止 `@Value`
  - import 放文件顶部，类中不写全路径
  - 不为"看起来高级"强上设计模式

> 后续如有 Python、Go 等语言专项规则，在 references/ 中新增对应文档即可。

## Checkpoint 检查

编码阶段的自动化检查通过 `coding.yaml` 执行（由 workflow-engine 或 `run-checkpoint.sh` 触发）。

### 检查项清单

| 检查 ID | 描述 | 类型 | on_fail | 说明 |
|---------|------|------|---------|------|
| C01 | 代码静态检查通过 | script | warn | checkstyle / eslint |
| C02 | 新增/修改行为有真实 E2E 脚本 | ai_check | block | 脚本进入仓库且包含有效业务断言 |
| C03 | 当前代码已启动并实际跑过 E2E | ai_check | block | 有版本、命令、case、日志和数据证据 |
| C04 | 文件行数限制 (≤1000) | script | warn | 最近 10 次提交修改的文件 |
| C05 | 方法行数限制 (≤150) | script | warn | 简化检查，建议用 SonarQube |
| C06 | 新增/修改逻辑具备部署后分支可观测性 | ai_check | block | 每个影响业务结果的分支可通过 INFO 及以上日志判断 decision/result、reason 和关键依据 |
| C07 | 异常处理正确 | ai_check | warn | AI 按异常处理规范检查 |
| C08 | coding-standards 合规 | ai_check | warn | AI 按 8 维度逐项检查 |
| C09 | 未用 Mock/单测/覆盖率冒充验收 | ai_check | block | 辅助测试不能代替真实应用验证 |

> C01/C04/C05 是脚本检查，C02/C03/C06-C09 是 AI 语义检查。C02、C03、C06、C09 是编码与真实 E2E 验收门禁；其中 C06 不通过时禁止进入部署阶段。完整规范合规验证在 code-review 阶段通过 CR03 执行。
