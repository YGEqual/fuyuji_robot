# 01 — 通用编码规范

## 总体原则

- **代码是给人看的**，一切以人类易读、易理解为前提。
- 单一职责：函数/模块/文件只做一件事，觉得"有点多"就拆。
- 组合性：多写小而清晰的函数，用组合代替巨大的"上帝函数"。
- 简洁性：能用直观实现就不搞花活，避免过度设计。
- 透明性：关键分支和外部行为要能从代码和日志里看懂。
- 快速失败：遇到异常及时返回、打清晰日志，不带着错误继续跑。

## 命名规范

### 通用规则

- 变量/方法/类名必须**语义清晰**，看名字就大致知道干嘛。
- 避免过度缩写（除非是约定俗成：`id`、`url`、`dto`）。
- 布尔变量用 `is/has/can/should` 前缀：`isValid`、`hasPermission`。
- 集合变量用复数或加后缀：`userList`、`orderIds`、`nameSet`。
- 常量全大写下划线分隔：`MAX_RETRY_COUNT`、`DEFAULT_TIMEOUT_MS`。

### 方法命名

| 动词 | 含义 | 示例 |
|------|------|------|
| `get/find/query` | 查询，有返回值 | `getUserById` |
| `create/add/insert` | 新增 | `createOrder` |
| `update/modify` | 修改 | `updateStatus` |
| `delete/remove` | 删除 | `removeExpired` |
| `check/validate` | 校验 | `checkPermission` |
| `convert/transform` | 转换 | `convertToDTO` |
| `build/assemble` | 组装 | `buildResponse` |
| `parse` | 解析 | `parseConfig` |
| `handle/process` | 处理（入口方法） | `handleRequest` |
| `send/notify` | 发送/通知 | `sendMessage` |

## 结构规范

### 文件粒度

- 一个文件尽量不超过 **1000 行**。
- 超过就按业务边界拆分，每个文件聚焦一个清晰的职责。

### 方法粒度

- 一个方法尽量不超过 **150 行**。
- 方法太长时优先拆分：
  - 校验逻辑 → `validateXxx()`
  - 参数组装 → `buildXxxRequest()`
  - 外部调用 → `callXxxService()`
  - 结果处理 → `parseXxxResponse()`
- 拆出来的方法名必须能说明"做了什么"。

### 代码组织顺序

建议按以下顺序组织类内代码：

1. 常量 / 静态变量
2. 成员变量 / 依赖注入
3. 构造方法
4. 公开方法（按业务重要性排序）
5. 私有方法（紧跟调用它的公开方法后面）
6. 内部类

## 注释规范

### 原则

- **导读型注释**，不是翻译型注释。解释"为什么"，不是重复"是什么"。
- 中文注释为主，语气大白话，短句为主。

### 类级注释

```java
/**
 * 用户积分服务
 *
 * 主要职责：
 * - 积分的增加、扣减、查询
 * - 积分变动记录的落库
 * - 与营销系统的积分同步
 *
 * 注意：积分扣减需要校验余额，不支持负数
 */
public class UserPointService { }
```

### 方法级注释

对以下方法必须加注释：
- 核心入口方法（Controller/Service 的主方法）
- 有复杂业务逻辑的方法
- 有"非直觉"行为的方法（特殊 case、历史兼容）

```java
/**
 * 扣减用户积分
 *
 * 1. 校验余额是否足够（不足直接返回失败）
 * 2. 扣减积分并记录变动日志
 * 3. 异步通知营销系统
 *
 * @param userId 用户ID
 * @param amount 扣减数量（正数）
 * @return 扣减结果
 */
public DeductResult deductPoints(Long userId, int amount) { }
```

### 常量注释

配置 key、阈值、格式字符串等必须注释说明：

```java
/** 积分查询缓存过期时间，单位秒，调大会降低 DB 压力但数据延迟增加 */
private static final int POINT_CACHE_TTL_SEC = 300;

/** 配置中心 key：积分扣减开关，关闭后所有扣减请求直接返回失败 */
private static final String DEDUCT_ENABLED_KEY = "point.deduct.enabled";
```

### 不做的事

- 不在每行代码上加"翻译型注释"（`i++ // i加1` 这种）
- 不写过时不维护的注释（宁可不写也别写错的）
- 不在注释里写 TODO 然后永远不处理（TODO 要标人名和日期）

## Java 专项规则

### import 规范

- 所有类引用都放到文件顶部的 `import` 区域。
- 类中**禁止**出现全路径引用（`com.xxx.yyy.ClassName`）。
- review 时要检查是否有"中间突然出现的全路径"。

### 配置管理

- **禁止使用 `@Value` 或 Properties/yml 硬编码配置**。
- 必须使用配置中心 `ConfigCenterUtil`，支持动态修改、灰度发布。
- 必须提供合理的默认值。

```java
// ✅ 正确
String url = ConfigCenterUtil.getValue("xxx.downstream.url", "http://default.url");
int timeout = ConfigCenterUtil.getInteger("xxx.http.timeout.ms", 3000);
boolean enabled = ConfigCenterUtil.getBoolean("xxx.feature.enabled", false);

// ❌ 错误
@Value("${xxx.downstream.url}")
private String url;
```

配置 key 命名：`{业务标识}.{模块}.{属性}`，如 `deeptrip.point.deduct.enabled`。

### 设计模式

- 不为"看起来高级"强上设计模式。
- 优先按职责拆分，让类结构自然清晰。
- 需要引入模式时，要能解释引入后的阅读成本是否值得。

### 集合与资源

- 循环里避免频繁 new 对象或做 IO/网络调用。
- 使用连接池、线程池时注意配置和关闭。
- 选择合适的集合实现（随机访问用 ArrayList、去重用 Set、查找用 Map）。

## 解耦与模块化

### 通用原则（不分语言）

> 不管 Java、Python 还是前端，分层的核心目标只有一个：**让改一个地方不用动十个地方。**

**四条铁律：**

1. **依赖方向单向流动**：上层依赖下层，禁止反向。接入层 → 业务层 → 数据/基础设施层。
2. **面向接口编程**：业务层定义"要什么"（接口/抽象），基础设施层实现"怎么做"。换实现不用改业务代码。
3. **按业务域分包/分模块**：不按技术类型分（把所有 service 塞一起），而是按业务域分（用户域、订单域、文件域）。
4. **接入层薄、业务层厚**：Controller/Router/Handler 只做收参数→调业务→封装返回，不写业务逻辑。

**通用分层模型（三层，任何语言都适用）：**

```
接入层（Adapter/API）    ← 接收请求、返回响应、协议适配
    ↓
业务层（Domain/Service） ← 业务规则、流程编排、接口定义
    ↓
基础设施层（Infra）      ← DB/缓存/外部 API/文件存储的具体实现
```

各项目可以根据复杂度增加层级（如 common 层、framework 层），但这三层是最小集。

### Java 项目分层（以 dt_robot 为例）

dt_robot 在三层基础上扩展为 5 个 Maven 模块：

```
arsenal-service-ai-dt-robot-api             ← 接入层：Controller、拦截器、MQ Listener、配置
arsenal-service-ai-dt-robot-domain          ← 领域层：业务接口定义、领域模型、业务规则
arsenal-service-ai-dt-robot-infrastructure  ← 基础设施层：DB/Redis/ES/MongoDB/S3 的具体实现
arsenal-service-ai-dt-robot-framework       ← 框架层：通用工具、SDK 封装、基础组件
arsenal-service-ai-dt-robot-common          ← 公共层：DTO、枚举、常量、通用异常
```

**这不是唯一正解**，项目可根据实际需要增减模块（比如加一个 `gateway` 模块、加一个 `job` 模块）。关键是依赖方向不能乱。

#### 依赖方向

```
api → domain → common
         ↑（禁止反向！）
infrastructure → domain → common
framework → common
```

| 规则 | 说明 | 违反示例 |
|------|------|---------|
| domain **禁止**依赖 infrastructure | 领域层定义接口，基础设施层实现 | domain 里 import 了 MyBatis Mapper |
| domain **禁止**依赖 api | 领域层不知道谁在调自己 | domain 里 import 了 Controller 的 DTO |
| domain **禁止**依赖 framework | 领域层不绑定具体框架 | domain 里直接用了 OkHttpClient |
| api **禁止**绕过 domain 直接调 infrastructure | 必须经过领域层编排 | Controller 直接调了 Mapper |
| common **禁止**依赖任何其他模块 | 公共层是最底层 | common 里 import 了 domain 的类 |

**正确的姿势——接口在 domain，实现在 infrastructure：**

```java
// domain 层：定义接口
package com.ly.arsenal.ai.robot.domain.file;
public interface FileUploadService {
    String uploadToPavo(String filename, InputStream inputStream, boolean watermark);
}

// infrastructure 层：实现接口
package com.ly.arsenal.ai.robot.infrastructure.file;
@Service
public class PavoFileUploadService implements FileUploadService {
    // 具体实现
}
```

#### 各层职责

| 层 | 该放 | 不该放 |
|----|------|--------|
| **api** | Controller（收参数→调 domain→封装返回）、拦截器、MQ Listener、配置、入口日志 | 业务逻辑、DB/缓存操作、调外部系统 |
| **domain** | 业务接口定义、业务规则和校验、领域模型、领域事件 | 框架注解（@Mapper/@Cacheable）、第三方 SDK 直接调用 |
| **infrastructure** | domain 接口的实现、DB/Redis/ES/MongoDB/S3 操作、BoundService | 业务规则判断、Controller、流程编排 |
| **framework** | 通用工具（JSON/日期/加密）、SDK 封装、基础组件 | 业务逻辑、业务 DTO |
| **common** | 跨模块 DTO/VO、通用枚举/常量、通用异常 | 业务逻辑、Spring Bean、依赖其他模块 |

#### 包结构（按业务域分包）

```
// ✅ 按业务域
domain/
├── metrics/    infrastructure/
├── dochub/     ├── metrics/
├── file/       ├── dochub/
├── auth/       ├── cache/
├── audit/      ├── file/
└── task/       └── redis/

// ❌ 按技术类型
domain/
├── service/    ← 所有 service 塞一起
├── model/      ← 所有模型塞一起
└── repository/ ← 所有 repository 塞一起
```

**新功能往哪放：** 确定业务域 → domain 下找/建对应包 → 接口放 domain → 实现放 infrastructure。

#### 模块间通信

| 方式 | 适用场景 |
|------|---------|
| 接口注入（domain 接口 + infrastructure 实现） | 同步调用、需要返回值 |
| Spring Event / 领域事件 | 解耦非核心链路、异步通知 |
| MQ 消息 | 跨服务通信、削峰 |

```java
// ✅ 注入接口
@Resource
private FileUploadService fileUploadService;

// ❌ 注入实现类（绑死了实现）
@Resource
private PavoFileUploadService pavoFileUploadService;
```

### 前端项目分层

#### Vue/React 项目（以 ai-booking 为例）

```
src/
├── views/              ← 页面组件（按路由/功能域分目录）
│   ├── dashboard/
│   ├── chat/
│   └── settings/
├── components/         ← 通用 UI 组件（不含业务逻辑）
│   ├── common/         ← 全局通用（Button、Modal、Table）
│   └── business/       ← 业务通用（UserAvatar、ChatBubble）
├── composables/        ← 业务逻辑（Vue3 Composable / React Hook）
│   ├── useChat.ts
│   └── useAuth.ts
├── services/           ← API 调用层（封装所有 HTTP 请求）
│   ├── chat.ts
│   ├── user.ts
│   └── request.ts      ← Axios 封装（拦截器、超时、鉴权）
├── stores/             ← 状态管理（Pinia / Zustand / Redux）
│   ├── chat.ts
│   └── user.ts
├── types/              ← TypeScript 类型定义
├── utils/              ← 纯工具函数（不依赖框架）
├── constants/          ← 常量、枚举
├── router/             ← 路由配置
└── assets/             ← 静态资源
```

#### 依赖方向

```
views → composables/stores → services → (HTTP → 后端)
  ↓
components（只接收 props，不调 API）
```

| 规则 | 说明 |
|------|------|
| **views**（页面）调 composables/stores，不直接调 services | 页面只关心"用什么数据"，不关心"数据从哪来" |
| **components** 只接收 props + emit 事件，不调 API 不操作 store | 保证组件可复用、可测试 |
| **composables/hooks** 封装业务逻辑，调 services 和 stores | 业务逻辑集中在这里，页面保持简洁 |
| **services** 只做 HTTP 请求封装，不含业务判断 | 和后端接口一一对应 |
| **stores** 管跨组件共享状态，不直接调 API | 由 composables 触发更新 |

```typescript
// ✅ service 只做请求封装
// services/chat.ts
export function sendMessage(params: SendMessageRequest) {
  return request.post<ChatResponse>('/api/chat/send', params);
}

// ✅ composable 封装业务逻辑
// composables/useChat.ts
export function useChat() {
  const chatStore = useChatStore();

  async function send(content: string) {
    const result = await sendMessage({ content, traceId: genTraceId() });
    chatStore.addMessage(result.data);
    return result;
  }

  return { send, messages: chatStore.messages };
}

// ✅ 页面只做展示和交互
// views/chat/index.vue
const { send, messages } = useChat();

// ❌ 页面里直接调 API
// views/chat/index.vue
import axios from 'axios';
const res = await axios.post('/api/chat/send', { content });  // 不该在页面出现
```

### 循环依赖防控

| 语言 | 检测方式 |
|------|---------|
| Java | Maven/Gradle 模块依赖天然防护（编译不过）；类级靠 code-review |
| Python | 运行时 ImportError 或 `import` 时用类型注解延迟导入；用 `importlib` 检查 |
| 前端 | ESLint 插件（`eslint-plugin-import` 的 `no-cycle` 规则） |

**通用解法：** 提取公共逻辑到独立模块/文件、用事件/回调解耦、引入中间层。

### 解耦检查清单（通用）

- [ ] 新代码放在了正确的层和包/目录下（按业务域分，不按技术类型分）
- [ ] 依赖方向正确（业务层不依赖基础设施层/接入层的具体实现）
- [ ] 业务接口/抽象定义在业务层，具体实现在基础设施层
- [ ] 接入层（Controller/Router/页面）只做编排，不写业务逻辑
- [ ] 通过接口/依赖注入/props 通信，不直接 new 实现类/不直接调 API
- [ ] 没有循环依赖
- [ ] 新增业务域时，各层目录结构对应
