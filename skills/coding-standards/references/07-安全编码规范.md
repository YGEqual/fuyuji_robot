# 07 — 安全编码规范

## 总则

- 安全不是额外的工作，是编码时**顺手就该做的事**。
- 不信任任何外部输入（用户输入、第三方接口返回、配置值）。
- 敏感操作要有审计日志。

## 一、输入校验

### 所有外部输入必须校验

```java
// ✅ 入口处校验
public Response<Void> createOrder(@RequestBody @Valid CreateOrderRequest request) {
    // @Valid + 自定义校验
}

// 对于不能用注解的场景，手动校验
if (StringUtils.isBlank(request.getUserId())) {
    throw new BusinessException(ErrorCode.PARAM_ERROR, "userId不能为空");
}
if (request.getAmount() <= 0 || request.getAmount() > 100000) {
    throw new BusinessException(ErrorCode.PARAM_ERROR, "金额不合法");
}
```

### 校验维度

| 维度 | 检查项 |
|------|--------|
| **非空** | 必填字段不能为空/空串 |
| **格式** | 手机号、邮箱、日期等格式校验 |
| **范围** | 数值上下限、字符串长度、枚举范围 |
| **逻辑** | 开始时间 < 结束时间、金额 > 0 |
| **长度** | 防止超长字符串打爆数据库 |

### 不要只依赖前端校验

前端校验是用户体验，**后端校验是安全底线**。前端校验可以被绕过。

## 二、鉴权

### 接口权限

- 所有接口必须有**鉴权**（除明确标记为公开的接口）。
- 鉴权失败返回统一错误码，不暴露内部信息。
- 管理后台接口和用户接口的权限体系必须隔离。

### 数据权限

- 用户只能访问**自己的数据**，不能通过修改参数访问别人的。
- 查询和修改都要校验数据归属。

```java
// ❌ 只凭前端传的 userId 查询
Order order = orderDao.getById(orderId);

// ✅ 校验数据归属
Order order = orderDao.getById(orderId);
if (!order.getUserId().equals(currentUserId)) {
    throw new BusinessException(ErrorCode.NO_PERMISSION, "无权访问");
}
```

## 三、注入防护

### SQL 注入

- **禁止拼接 SQL**，必须使用参数化查询。

```java
// ❌ SQL 注入风险
String sql = "SELECT * FROM user WHERE name = '" + name + "'";

// ✅ 参数化查询
@Select("SELECT * FROM user WHERE name = #{name}")
User getByName(@Param("name") String name);
```

### XSS 防护

- 用户输入展示前做 HTML 转义。
- 富文本内容使用白名单过滤。

### SSRF 防护

- 用户提交的 URL 不能直接用于服务端请求。
- 需要校验：协议（只允许 http/https）、域名（白名单）、端口、内网地址过滤。

### 路径穿越

- 文件操作时校验路径，防止 `../../etc/passwd` 类攻击。
- 使用白名单目录 + 规范化路径。

## 四、敏感操作审计

以下操作必须有审计日志：

- 用户登录/登出
- 权限变更
- 数据删除（尤其是物理删除）
- 配置修改
- 金额/积分变动
- 导出敏感数据

审计日志格式：
```java
log.info("审计-{} operator={} target={} action={} detail={} traceId={}",
        "积分调整", operatorId, targetUserId, "DEDUCT", "amount=100", traceId);
```

## 检查清单

- [ ] 外部输入都校验了（非空/格式/范围/长度）？
- [ ] 后端有独立的校验逻辑，不只依赖前端？
- [ ] 接口有鉴权？数据有归属校验？
- [ ] 没有 SQL 拼接？用的参数化查询？
- [ ] 用户提交的 URL/路径有校验？
- [ ] 敏感操作有审计日志？
