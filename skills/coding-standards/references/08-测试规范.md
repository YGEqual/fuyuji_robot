# 08 - 真实端到端测试规范

> 测试的目标是证明真实应用中的业务行为正确，不是证明测试代码本身能运行。

## 完成标准

新增、修改、修复或重构代码后，编码工作只有同时满足以下条件才算完成：

- 使用项目官方方式启动了当前 worktree/分支对应的应用；
- 已从用户视角梳理受影响的真实使用链路，并建立“链路 -> 接口/服务 -> 状态与副作用 -> 条件 -> 断言与证据”追踪矩阵；
- 创建或更新了纳入业务仓库、长期保留的可重复执行 E2E 脚本；
- 脚本实际运行，适用的正常、边界、失败和回归 case 全部通过；
- 核对了用户可见结果、业务数据/副作用和本次测试链路日志；
- 留下了可复现的命令、版本、case 结果、日志与数据证据；
- 失败时完成“定位 -> 修复 -> 重启 -> 重跑 -> 再核对”的闭环。

详细执行流程统一使用 `integration-test` Skill，本文件只保留编码阶段必须遵守的规则。

## 不接受的替代品

以下内容不能作为编码完成或功能正确的证据：

- Mock 测试或把关键依赖替换成假的实现；
- 单元测试、覆盖率数字、快照测试；
- 只编译通过、静态检查通过或代码阅读；
- 只请求一次接口，或脚本放在临时目录、测试通过后删除，没有形成长期回归资产；
- 只断言 HTTP 200、`code=0`、响应非空或服务没崩；
- 只看接口返回，不查落库、缓存、消息、文件、异步任务等适用副作用；
- 扫全量日志没看到 ERROR，却没有按时间窗/traceId 确认关键分支真实执行；
- 服务起不来时改用 Mock/单测并宣称功能验证通过。

已有 Mock/单元测试可以运行作补充，但默认不花编码时间新增，也不能替代真实 E2E。用户明确要求时再单独处理。

## 编码过程

### 开始实现前

从需求验收标准、目标验证追踪矩阵、技术方案和缺陷复现步骤中梳理真实用户链路。每条链路识别：

- 用户角色、真实入口、前置状态、操作步骤、业务分支和最终可见结果；
- 受影响的接口、服务和状态迁移；
- DB、Redis、ES、MQ、文件、任务或第三方副作用；
- 能定位单次测试的 run_id、traceId、sid 或业务键；
- 需要启动的应用和依赖服务。

先形成用户链路清单，再建立“用户链路 -> 接口/服务 -> 状态与副作用 -> 测试条件 -> 断言与证据”追踪矩阵。测试设计不能从接口清单或代码分支直接开始；P0/P1 链路和高风险分支必须映射到可执行 case。

### 实现每个子目标时

1. 按用户链路及分支确定本次子目标的 case，并更新追踪矩阵。
2. 优先扩展现有 E2E 框架；没有时在目标仓库 `tests/e2e/<domain>/` 等稳定目录创建并长期保留脚本。
3. 写完业务代码后立即补对应 case，不把脚本拖到交付前。
4. 用官方启动脚本重启应用，确认端口上的进程加载当前 Git SHA。
5. 运行新增 case，核对响应、日志、数据和副作用。
6. case 失败就定位并修复，然后重启并重跑。
7. 子目标完成后再进入下一项；最后跑所有受影响 case 做回归。

### 脚本要求

脚本语言优先沿用仓库现有成熟 E2E 技术栈。没有约定时，Web HTTP/SSE/WebSocket、跨服务流程和数据核对默认使用 Python 3 + pytest；浏览器流程使用 TypeScript + Playwright；并发压测使用 k6 或 Locust；Shell 只做启停和薄编排，不用字符串命令解析复杂响应或承载业务断言。已有可维护的自研 Runner 或 Java/Go 测试框架不强制迁移。

脚本及 case 文件必须保留在业务仓库，跟随业务规则维护。case 较多时使用 YAML/JSON 管理输入与期望，用户步骤、协议处理和断言逻辑集中在 Python 中，不把 YAML 变成流程引擎。依赖复用目标仓库包管理和锁文件，不依赖开发机全局环境。

case 较多时，必须支持按用户链路、优先级和功能标签选择执行。无共享状态且测试数据可按 `run_id` 隔离的 case 可以限流并行；共享账号、商户、订单、库存、会话或顺序状态的 case 必须串行、分组隔离或加资源锁。pytest 可按项目依赖使用 `pytest-xdist` 或受控异步客户端，worker 数必须可配置并服从环境容量和下游限流。全量回归可后台执行，但交付前必须完成所有受影响链路；压测使用 k6/Locust，不靠无限增加 pytest worker。

无论使用哪种语言，脚本都必须：

- 可一条命令重复运行，环境和地址可配置；
- 默认只写本地/测试环境，不默认改生产；
- 自动准备前置数据并清理，或明确记录保留数据；
- 每次运行生成唯一标识并透传到请求和日志；
- case 级输出 PASS/FAIL，关键断言失败时非零退出；
- 对请求超时、协议不完整、解析失败和依赖异常明确失败；
- 不吞异常、不无限重试、不把失败改成 warning；
- 不把凭据和敏感数据写进代码或报告。

### 断言要求

按本次改动涉及的层次组合断言：

| 层次 | 断言示例 |
|------|----------|
| 传输 | HTTP 状态、SSE 结束事件、WebSocket 消息序列、超时 |
| 业务 | 业务码、字段值、金额、数量、排序、权限、状态迁移 |
| 数据 | DB 行、缓存值、ES 文档、MQ 消息、文件、任务终态 |
| 链路 | 预期代码分支、下游调用次数/结果、trace/span、耗时 |
| 用户 | 页面状态、最终消息、通知或其他用户可见结果 |

只断言状态码或业务码不合格。接口返回成功但数据没写对、异步任务失败、日志走了降级分支，都应判为失败。

## case 最低覆盖

以用户链路为主轴，在每条链路内按风险选择适用条件，并优先覆盖 P0/P1。不要把边界条件集中成与用户链路脱节的独立用例池：

| case | 要求 |
|------|------|
| Happy path | 完整真实链路必须有 |
| 关键边界 | 空值、临界值、长文本、特殊字符、组合参数按需覆盖 |
| 失败路径 | 非法输入、无权限、真实可构造的依赖失败按需覆盖 |
| 状态与幂等 | 有写操作、回调、消费或任务时必须覆盖 |
| 并发 | 涉及同资源竞争、库存、金额、计数或去重时必须覆盖 |
| 兼容回归 | 修改老行为时覆盖原有入口、数据和关键渠道 |

不适用项说明原因，不能静默遗漏。无法穷举所有组合时，按业务风险、状态迁移、历史故障和等价类取舍，不得笼统声称“覆盖所有条件”。

## 运行证据

测试记录至少包含：

- worktree、分支、Git SHA；
- 用户链路追踪矩阵及覆盖结论；
- 启动命令、端口、PID、健康检查和日志路径；
- 测试脚本路径与完整执行命令；
- 每个 case 的输入摘要、关键断言、结果和耗时；
- 用例选择范围、分组/分片和 worker 配置；
- run_id/traceId/sid 和日志时间窗；
- 数据前值、后值、期望值以及清理结果；
- 失败定位、修复内容和重跑结果；
- 未覆盖项及原因。

没有运行证据时，只能说“脚本已写但未完成真实验证”。

## 阻塞原则

应用无法启动、真实依赖不可用、缺少安全的测试数据/凭据、无法确认版本或无法读取关键副作用时，明确标记 E2E 未完成并说明缺失条件。不得降低测试层级后给出通过结论。

## 编码自检

- [ ] 当前代码对应的应用确实启动，且不是遗留旧进程
- [ ] 已先梳理用户角色、真实入口、步骤、分支和最终结果，没有从接口清单直接开始
- [ ] 已建立用户链路到接口、状态、条件、断言和证据的追踪矩阵
- [ ] 新增/修改行为都有仓库内 E2E 脚本 case
- [ ] 脚本和 case 已长期保留在业务仓库，不是临时文件或一次性命令
- [ ] case 覆盖正常、关键边界和适用失败路径
- [ ] 断言不止状态码/业务码，覆盖实际业务结果
- [ ] 已按 run_id/traceId 核对关键日志和下游调用
- [ ] 已核对适用的数据变化和外部副作用
- [ ] 测试失败后已重启并重跑受影响用例
- [ ] 已清理测试数据并留下可复现证据
- [ ] 没有用 Mock、单测或覆盖率冒充真实验收
