# 03 — 数据层规范

> 涉及数据库、缓存、消息队列、搜索引擎、文档存储、文件存储的代码都按这个来。

---

## 零、容量与性能红线（所有存储通用）

**写代码前先想清楚数据量级。** 下面是各组件的"安全水位线"和"危险水位线"，超过安全线就要提前规划，碰到危险线就是生产事故的前兆。

### MySQL

| 指标 | 安全水位 | 危险水位 | 到了该怎么办 |
|------|---------|---------|-------------|
| 单表行数 | < 500 万 | > 2000 万 | 分表（按时间/按 ID 取模）、归档历史数据 |
| 单次查询耗时 | < 200ms | > 1s | 检查索引、优化 SQL、加缓存 |
| 单次查询返回行数 | < 1000 行 | > 10000 行 | 分页、流式处理、异步导出 |
| 单事务持续时间 | < 500ms | > 3s | 缩小事务范围、异步化非核心操作 |
| 连接池活跃连接数 | < 池大小 60% | > 池大小 80% | 排查慢查询、扩容连接池、拆分读写 |
| 批量写入单批 | 200-500 条 | > 2000 条 | 减小 batch size、分批+sleep |

**连接池配置必须配置化：**

```java
int maxActive = ConfigCenterUtil.getInteger("db.pool.max.active", 20);
int minIdle = ConfigCenterUtil.getInteger("db.pool.min.idle", 5);
int maxWaitMs = ConfigCenterUtil.getInteger("db.pool.max.wait.ms", 3000);
```

### Redis

| 指标 | 安全水位 | 危险水位 | 到了该怎么办 |
|------|---------|---------|-------------|
| 单个 Value | < 64 KB | > 512 KB | 拆分（只缓存 ID 列表、构建精简 DTO） |
| 单次 Pipeline/批量命令 | < 200 条 | > 1000 条 | 分批执行 |
| 单个 List/Set/ZSet 元素数 | < 5000 | > 10 万 | 拆分 key（按时间/分段） |
| 连接池活跃连接 | < 池大小 60% | > 池大小 80% | 排查阻塞命令、扩容 |
| 单条命令耗时 | < 5ms | > 50ms | 排查大 key、慢命令（KEYS/SMEMBERS 大集合） |
| Lua 脚本执行时间 | < 50ms | > 200ms | 简化逻辑、拆分操作 |

**绝对禁止的操作：**
- 生产环境使用 `KEYS *`（用 `SCAN` 替代）
- 对大集合做 `SMEMBERS`/`HGETALL`（用 `SSCAN`/`HSCAN`）
- 无 TTL 的缓存 key（除非是明确的永久数据）

### Elasticsearch

| 指标 | 安全水位 | 危险水位 | 到了该怎么办 |
|------|---------|---------|-------------|
| 单个分片大小 | 10-30 GB | > 50 GB | 增加分片数、按时间滚动索引 |
| 单索引分片数 | 1-5 个 | > 20 个 | 合并小分片、重新规划索引策略 |
| 单次查询耗时 | < 200ms | > 2s | 优化查询（减少聚合层级/缩小范围）、加缓存 |
| 单次查询返回文档数 | < 1000 | > 10000 | 用 scroll/search_after、异步导出 |
| 批量写入单批 | 500-2000 条 | > 5000 条 | 减小 batch、控制写入频率 |
| 集群状态 | green | yellow/red | 立即排查（副本丢失/磁盘满/节点挂了） |

**写入性能关注点：**
- 高频写入场景先攒批再 bulk，不要逐条写。
- 写入密集时考虑**关闭 refresh**（`refresh_interval: -1`），批量完成后手动 refresh。
- 索引不需要的字段设置 `"index": false`，减少索引体积。

### MongoDB

| 指标 | 安全水位 | 危险水位 | 到了该怎么办 |
|------|---------|---------|-------------|
| 单 Collection 文档数 | < 500 万 | > 2000 万 | 按时间拆分 Collection、Sharding |
| 单 Document 大小 | < 1 MB | > 5 MB | 拆分嵌套数组、外部存储大字段 |
| 嵌套数组元素数 | < 500 | > 5000 | 拆成独立 Collection 关联 |
| 单次查询耗时 | < 200ms | > 1s | 检查索引（explain）、缩小返回字段 |
| Working Set | < 可用内存 60% | > 可用内存 80% | 扩内存、归档冷数据、加缓存层 |
| 批量操作单批 | 500-2000 条 | > 5000 条 | 减小 batch |

**Working Set 是 MongoDB 的命门：** 常被访问的数据（热数据）应当能放进内存。如果 Working Set 超过内存，查询会频繁读磁盘，性能急剧下降。

### 文件/对象存储

| 指标 | 安全水位 | 危险水位 | 到了该怎么办 |
|------|---------|---------|-------------|
| 单文件上传大小（图片/Pavo） | < 5 MB | > 10 MB | 前端压缩、拒绝上传 |
| 单文件上传大小（视频/S3） | < 200 MB | > 500 MB | 分片上传（Multipart Upload） |
| 并发上传数 | < 10/实例 | > 50/实例 | 队列化、限流 |
| 临时文件残留 | 0 | > 0 | 检查 finally 清理逻辑 |

## 一、数据库操作规范

### SQL 编写

- **禁止 `SELECT *`**：明确列出需要的字段，减少网络传输和内存占用。
- **禁止无 WHERE 的 UPDATE/DELETE**：必须有条件限制，防止全表误操作。
- **分页必须有上限**：`LIMIT` 值必须配置化，禁止无界分页。
- **批量操作有 batch size**：批量插入/更新控制在 200-500 条/批，避免大事务。

### N+1 问题

**循环里查数据库是最常见的性能杀手**：

```java
// ❌ N+1：循环里查数据库
for (Long userId : userIds) {
    User user = userDao.getById(userId);  // 每次一条 SQL
}

// ✅ 批量查询 + Map 映射
List<User> users = userDao.listByIds(userIds);
Map<Long, User> userMap = users.stream()
    .collect(Collectors.toMap(User::getId, Function.identity()));
```

### 索引规范

- 新增查询前先确认**走不走索引**（`EXPLAIN` 验证）。
- WHERE 条件中的字段优先建索引。
- 联合索引遵循最左匹配原则。
- 避免在索引字段上做函数运算（`WHERE DATE(create_time) = ...`）。
- 表设计索引规范详见 `table-design` skill。

### 事务规范

- 事务范围尽量小，**不要在事务里做外部调用**（HTTP/RPC/MQ）。
- 明确标注事务边界（`@Transactional` 加在 Service 方法上，不要加在 Controller）。
- 需要跨表一致性时，评估是否需要本地消息表或补偿机制。
- 只读查询加 `@Transactional(readOnly = true)`。

## 二、缓存使用规范

### 缓存 Key 设计

```
{业务标识}:{实体类型}:{唯一标识}
```

示例：
```
deeptrip:user:12345
deeptrip:poi:detail:67890
deeptrip:config:homepage:v2
```

### 过期策略

| 场景 | 建议 TTL | 说明 |
|------|---------|------|
| 配置类（变化少） | 5-30 分钟 | 配合主动失效 |
| 详情类（变化适中） | 1-5 分钟 | 容忍短暂不一致 |
| 列表/聚合类（变化频繁） | 30 秒-2 分钟 | 或不缓存 |
| 热点数据 | 按需 | 本地缓存 + Redis 二级缓存 |

TTL 必须从配置中心读取，支持动态调整。

### 缓存与 DB 一致性

**默认策略：先更新 DB，再删除缓存**（Cache Aside Pattern）。

```java
// ✅ 推荐
userDao.update(user);           // 1. 先更新 DB
redisTemplate.delete(cacheKey); // 2. 再删除缓存（下次读时回源）

// ❌ 不推荐：先删缓存再更新 DB（并发下会脏读）
```

对于一致性要求高的场景，考虑延迟双删或消息驱动缓存更新。

### 缓存穿透/击穿/雪崩

| 问题 | 现象 | 应对 |
|------|------|------|
| **穿透** | 查不存在的 key，每次都打 DB | 缓存空值（短 TTL）或布隆过滤器 |
| **击穿** | 热点 key 过期瞬间大量请求打 DB | 互斥锁（setnx）或热点 key 不过期 |
| **雪崩** | 大量 key 同时过期 | TTL 加随机偏移量 |

### 大 Value 防护

Redis value 过大会导致网络阻塞、慢查询、甚至 OOM。**写入缓存时主动检测并告警：**

```java
// ✅ 写缓存前检测 value 大小
String json = JsonUtil.toJson(data);
int sizeKb = json.getBytes(StandardCharsets.UTF_8).length / 1024;
int warnThresholdKb = ConfigCenterUtil.getInteger("cache.big.value.warn.kb", 64);
int blockThresholdKb = ConfigCenterUtil.getInteger("cache.big.value.block.kb", 512);

if (sizeKb >= blockThresholdKb) {
    log.error("缓存写入阻断-value过大 key={} sizeKb={} threshold={}kb", cacheKey, sizeKb, blockThresholdKb);
    // 不写入缓存，走降级（直接查 DB 或返回精简数据）
    return;
}
if (sizeKb >= warnThresholdKb) {
    log.warn("缓存大value告警 key={} sizeKb={} threshold={}kb，请排查是否可以精简", cacheKey, sizeKb, warnThresholdKb);
}
redisTemplate.opsForValue().set(cacheKey, json, ttl, TimeUnit.SECONDS);
```

**阈值建议：**

| 阈值 | 默认值 | 行为 |
|------|--------|------|
| warn | 64 KB | 打 WARN 日志，提醒开发排查 |
| block | 512 KB | 打 ERROR 日志，**阻断写入**，走降级 |

**大 value 的常见原因和处理方式：**

| 原因 | 处理 |
|------|------|
| 缓存了整个列表/大对象 | 只缓存 ID 列表，详情按需查 |
| 字段冗余（缓存了不需要的字段） | 构建专用的缓存 DTO，只存需要的字段 |
| 嵌套对象过深 | 扁平化或分层缓存 |
| 历史数据堆积（如聊天记录） | 分页缓存 or 只缓存最近 N 条 |

### 本地缓存（Caffeine）

Redis 之前加一层 Caffeine 本地缓存，减少网络 IO，适合**读多写少、对一致性容忍短暂延迟**的场景。

#### 适用场景

| 适合 | 不适合 |
|------|--------|
| 配置信息、枚举映射、城市/POI 基础数据 | 用户私有数据（多实例不一致） |
| 变化频率低（分钟级） | 变化频率高（秒级） |
| 单条数据量小（< 1KB） | 单条数据量大 |

#### 代码模板

```java
// ✅ Caffeine 本地缓存，参数配置化
private final Cache<String, Object> localCache = Caffeine.newBuilder()
    .maximumSize(ConfigCenterUtil.getInteger("local.cache.max.size", 1000))
    .expireAfterWrite(ConfigCenterUtil.getInteger("local.cache.expire.seconds", 300), TimeUnit.SECONDS)
    .recordStats()  // 开启统计，用于监控命中率
    .build();
```

#### 二级缓存模式

```java
// ✅ 先查本地 → 再查 Redis → 最后查 DB
public PoiDetail getPoiDetail(String poiId) {
    String cacheKey = "deeptrip:poi:detail:" + poiId;

    // L1：本地缓存
    PoiDetail result = (PoiDetail) localCache.getIfPresent(cacheKey);
    if (result != null) {
        return result;
    }

    // L2：Redis
    String json = redisTemplate.opsForValue().get(cacheKey);
    if (json != null) {
        result = JsonUtil.parse(json, PoiDetail.class);
        localCache.put(cacheKey, result);  // 回填本地缓存
        return result;
    }

    // L3：DB
    result = poiDao.getById(poiId);
    if (result != null) {
        redisTemplate.opsForValue().set(cacheKey, JsonUtil.toJson(result), ttl, TimeUnit.SECONDS);
        localCache.put(cacheKey, result);
    }
    return result;
}
```

#### 失效策略

- **本地缓存 TTL 必须短于 Redis TTL**（如本地 5 分钟，Redis 30 分钟），避免本地缓存比 Redis 还旧。
- 主动失效时**同时清除本地缓存和 Redis**。
- 多实例部署时，本地缓存靠 TTL 过期兜底（接受短暂不一致），强一致性场景通过 MQ 广播清除。

#### Caffeine 监控

```java
// ✅ 定期输出缓存命中率（排查缓存是否有效）
@Scheduled(fixedRate = 60_000)
public void logCacheStats() {
    CacheStats stats = localCache.stats();
    log.info("本地缓存统计 hitRate={} hitCount={} missCount={} evictionCount={} size={}",
            String.format("%.2f%%", stats.hitRate() * 100),
            stats.hitCount(),
            stats.missCount(),
            stats.evictionCount(),
            localCache.estimatedSize());
}
```

**关注指标：**

| 指标 | 含义 | 异常信号 |
|------|------|---------|
| `hitRate` | 命中率 | < 50% 说明缓存可能没用，检查 key 设计或 TTL |
| `evictionCount` | 淘汰次数 | 持续很高说明 maximumSize 太小 |
| `size` | 当前缓存条目数 | 持续接近 maximumSize 考虑扩容 |

### 缓存检查清单

- [ ] Key 命名清晰、有前缀、不冲突
- [ ] TTL 配置化、有合理默认值
- [ ] 更新/删除策略明确（先 DB 后缓存）
- [ ] 考虑了穿透/击穿/雪崩
- [ ] 大 value 有检测和告警（warn 64KB / block 512KB）
- [ ] 本地缓存 TTL 短于 Redis TTL
- [ ] 本地缓存开启了 `recordStats()`，有命中率监控

## 三、消息队列规范

### 生产者

- 发送前记录日志：topic、key、消息摘要。
- 发送结果（成功/失败）必须有日志。
- 关键消息考虑**本地消息表**保证可靠投递。
- 消息体尽量精简，带上 traceId。

```java
log.info("MQ发送开始 topic={} key={} traceId={} body={}",
        topic, msgKey, traceId, briefBody);
SendResult result = producer.send(msg);
log.info("MQ发送结束 topic={} key={} traceId={} result={}",
        topic, msgKey, traceId, result.getSendStatus());
```

### 消费者

- **幂等必做**：用业务唯一键（订单号/请求ID）去重。
- 消费失败有明确策略：重试次数、重试间隔、死信队列。
- 消费日志必须包含：消息 key、traceId、处理结果、耗时。
- 批量消费有并发控制和 batch size 限制。

```java
log.info("MQ消费开始 topic={} key={} traceId={}",
        topic, msg.getKeys(), traceId);
try {
    // 1. 幂等校验
    if (isDuplicate(msg.getKeys())) {
        log.info("MQ消费跳过-重复消息 key={}", msg.getKeys());
        return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
    }
    // 2. 业务处理
    processMessage(msg);
    log.info("MQ消费成功 key={} costMs={}", msg.getKeys(), costMs);
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
} catch (Exception e) {
    log.error("MQ消费异常 key={} err={}", msg.getKeys(), e.toString(), e);
    return ConsumeConcurrentlyStatus.RECONSUME_LATER;
}
```

### 消息检查清单

- [ ] 生产者有发送前后日志
- [ ] 消费者做了幂等
- [ ] 消费失败有重试策略和死信处理
- [ ] 消息体带了 traceId
- [ ] 消费有耗时日志

## 四、Elasticsearch 规范

### 索引设计

- **索引命名**：`{业务标识}_{数据类型}_{时间粒度}`，全小写、下划线分隔。
  - 示例：`deeptrip_chat_log_202603`、`deeptrip_poi_detail`
- **Mapping 必须显式定义**：禁止依赖动态 Mapping，字段类型、分词器、是否索引都要明确声明。
- **字段类型选择**：
  - 精确匹配用 `keyword`（渠道、状态、ID）
  - 全文检索用 `text` + 合适的分词器
  - 时间用 `date`（指定 format）
  - 数值用 `long`/`double`，不要用 `text` 存数字

### 数据量大时必须拆分

**按时间滚动索引（推荐）**：

```
# 索引命名：{前缀}_{yyyyMM} 或 {前缀}_{yyyyMMdd}
deeptrip_chat_log_202603      ← 按月
deeptrip_event_raw_20260309   ← 按天（数据量特别大时）
```

**拆分策略选择：**

| 日数据量 | 拆分粒度 | 保留策略 |
|---------|---------|---------|
| < 100 万条 | 按月 | 保留 6-12 个月 |
| 100 万 ~ 1000 万条 | 按月，考虑按天 | 保留 3-6 个月 |
| > 1000 万条 | 按天 | 保留 30-90 天 |

**自动管理：**
- 推荐使用 **ILM（Index Lifecycle Management）** 自动管理索引生命周期（热→温→冷→删除）。
- 没有 ILM 条件的，用定时任务清理过期索引。

### 分片（Shard）规范

- **单个分片大小控制在 10-50 GB**，超过则增加分片数。
- 分片数 = 预估索引总大小 / 30GB（取整）。
- **副本数**：生产至少 1 个副本，开发/测试可以 0。

### 查询规范

- **禁止深分页**：`from + size` 总量不超过 10000（ES 默认限制）。大数据量翻页用 `search_after` 或 `scroll`。
- **查询必须有超时**：设置 `timeout` 参数，防止慢查询拖垮集群。
- 批量写入用 **Bulk API**，单次 batch 500-2000 条。
- **禁止 `match_all` + 大 size**：等于全表扫描。

### 日志与监控

- 写入/查询都要有耗时日志（costMs + bucket）。
- 关注集群健康状态（green/yellow/red）、索引大小、分片分布。

### ES 检查清单

- [ ] Mapping 显式定义，没有依赖动态 Mapping
- [ ] 大数据量索引按时间拆分（按月/按天）
- [ ] 有索引生命周期管理（ILM 或定时清理）
- [ ] 单分片大小在 10-50 GB 范围内
- [ ] 查询有超时设置，无深分页
- [ ] 批量写入用 Bulk API
- [ ] 写入/查询有耗时日志

## 五、MongoDB 规范

### Collection 设计

- **命名规范**：`{业务标识}_{数据类型}`，全小写、下划线分隔。
  - 示例：`chat_history`、`user_preference`、`poi_raw_data`
- **Document 结构要提前设计**：虽然 MongoDB 是 Schema-free，但团队内部必须有明确的字段约定文档，不能随意往 Document 里塞字段。
- **通用字段**：每个 Document 都应包含 `created_on`、`updated_on`、`env`（与 MySQL 规范对齐）。

### 数据量大时必须拆分

**按时间分 Collection（推荐）**：

```
# Collection 命名：{前缀}_{yyyyMM} 或 {前缀}_{yyyyMMdd}
chat_history_202603      ← 按月
event_detail_20260309    ← 按天
```

**拆分策略选择：**

| 日数据量 | 拆分粒度 | 保留策略 |
|---------|---------|---------|
| < 50 万条 | 按月 | 保留 6-12 个月 |
| 50 万 ~ 500 万条 | 按月，考虑按天 | 保留 3-6 个月 |
| > 500 万条 | 按天 | 保留 30-90 天 |

**大规模场景**：数据量特别大时考虑 MongoDB **Sharding**（分片集群），按业务 key 做 shard key。

### 索引规范

- **查询字段必须建索引**：MongoDB 没索引的查询就是全表扫描。
- 复合索引遵循**最左匹配**原则（和 MySQL 一样）。
- 用 `explain()` 验证查询是否走索引。
- **TTL 索引**：日志类、临时数据用 TTL 索引自动过期删除。

```javascript
// ✅ TTL 索引：30 天后自动删除
db.chat_history.createIndex(
  { "created_on": 1 },
  { expireAfterSeconds: 2592000 }  // 30 天
)
```

### 查询规范

- **禁止无条件全量查询**：必须有查询条件 + limit。
- **分页**：大数据量用 `_id` 游标分页，不要用 `skip` + `limit`（skip 大偏移量性能极差）。
- 投影（Projection）只返回需要的字段，不要返回整个 Document。
- 批量写入用 **bulkWrite**，单次 500-2000 条。

```java
// ❌ skip 深分页，性能差
db.collection.find().skip(100000).limit(20);

// ✅ 游标分页
db.collection.find({ "_id": { "$gt": lastId } }).limit(20);
```

### 大 Document 防护

- **单个 Document 不超过 1 MB**（MongoDB 限制 16 MB，但实际应控制在 1 MB 以内）。
- 嵌套数组不要无限增长（如聊天记录不要全塞一个 Document，按时间窗口拆分）。
- 超大字段考虑用 GridFS 或外部存储。

### MongoDB 检查清单

- [ ] Collection 命名规范，有字段约定文档
- [ ] 大数据量 Collection 按时间拆分
- [ ] 查询字段有索引，用 `explain()` 验证过
- [ ] 日志/临时数据用 TTL 索引自动清理
- [ ] 无深分页（用游标分页替代 skip）
- [ ] 批量操作用 bulkWrite
- [ ] 单个 Document 大小可控（< 1 MB）

## 六、文件/对象存储规范

DeepTrip 使用两种文件上传通道：**Pavo**（图片/小文件）和 **Ceph S3**（大文件/视频）。

### 上传通道选择

| 场景 | 通道 | 说明 |
|------|------|------|
| 图片（头像、旅行照片、POI 图片） | Pavo | 支持水印，有 CDN |
| 小文件（PDF、文档） | Pavo | < 10 MB |
| 大文件（视频、音频） | Ceph S3（PublicRead） | 无大小限制 |
| 模型生成的图片/文件 | Ceph S3 | 先落临时文件再上传 |

### 文件命名规范

```java
// ✅ 用 UUID 避免冲突，保留原始扩展名
String newFileName = UUID.randomUUID().toString().replace("-", "") + "." + ext;
```

- 禁止用原始文件名直接上传（可能冲突、含特殊字符）。
- 保留原始扩展名，方便下游识别文件类型。

### 安全规范

- **上传前校验**：
  - 文件大小限制（配置化，如图片 ≤ 10 MB，视频 ≤ 500 MB）
  - 文件类型白名单（只允许 png/jpg/gif/webp/pdf/mp4 等）
  - **禁止上传可执行文件**（.exe/.sh/.bat/.jar 等）
- **Token/凭证**：从配置中心读取，禁止硬编码。
- **返回 URL 统一 HTTPS**。

### 临时文件清理

从外部 URL 下载后转存的场景，**必须在 finally 中清理临时文件**：

```java
// ✅ finally 中清理
try {
    // 下载 → 上传
} finally {
    Files.deleteIfExists(tmpFile);
}
```

### 日志规范

- 上传成功：记录 `key`（或返回 URL）、文件大小、耗时。
- 上传失败：记录 `key`、原始文件名、错误原因。
- **禁止在日志中打印文件内容/Base64**。

### 文件存储检查清单

- [ ] 根据文件类型和大小选择了正确的上传通道
- [ ] 文件名用 UUID 生成，保留扩展名
- [ ] 上传前有大小限制和类型白名单校验
- [ ] Token/凭证从配置中心读取，未硬编码
- [ ] 临时文件在 finally 中清理
- [ ] 上传成功/失败都有日志
- [ ] 返回 URL 统一 HTTPS
