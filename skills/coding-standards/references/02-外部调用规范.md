# 02 — 外部调用规范

> 只要涉及网络 IO（HTTP/RPC/第三方 SDK），都按这个来。

## 核心原则

1. **独立封装**：外部接口调用必须封装到独立的 `*BoundService` 类中。
2. **统一目录**：BoundService 类放在 `application/bound/` 目录下。
3. **可观测性**：调用开始/结束/异常必须有完整日志，包含 costMs + bucket。
4. **超时配置化**：超时参数必须支持配置中心动态调整。
5. **traceId 透传**：链路 ID 必须贯穿整个调用链。
6. **网络边界必打日志**：数据进来要打、出去要打，关键字段不能少（详见下方铁律）。

## 网络边界日志铁律

> **凡是跨网络的数据交换，进和出都必须有日志，且必须包含关键业务字段。**
>
> 这不是建议，是铁律。因为网络另一端不是你能控制的——对方说"我传了"、你说"我没收到"，没日志就是死无对证。开发时觉得"这个不用打"，排障时就是"这个要是打了就好了"。

### 两个方向，四个日志点

```
外部请求进来（Controller / MQ Consumer）          我方调用出去（BoundService / SDK）
        │                                                    │
   ┌────▼────┐                                          ┌────▼────┐
   │ 入口日志 │ ← 打印收到了什么                         │ 请求日志 │ ← 打印发出去什么
   └────┬────┘                                          └────┬────┘
        │ 处理...                                            │ 等响应...
   ┌────▼────┐                                          ┌────▼────┐
   │ 出口日志 │ ← 打印返回了什么                         │ 响应日志 │ ← 打印收到了什么
   └─────────┘                                          └─────────┘
```

### 每个日志点必须包含的字段

#### 请求进来（Controller 入口）

```java
// ✅ 入口：打印收到了什么（含请求 Header 关键信息）
log.info("[Xxx接口] 收到请求 traceId={} 来源={} "
        + "headers=[Content-Type={}, User-Agent={}, X-Forwarded-For={}] "
        + "关键字段=[userId={}, cityCode={}, dateRange={}]",
        traceId, request.getChannel(),
        httpRequest.getHeader("Content-Type"),
        httpRequest.getHeader("User-Agent"),
        httpRequest.getHeader("X-Forwarded-For"),
        request.getUserId(), request.getCityCode(), request.getDateRange());
```

| 必打字段 | 说明 |
|---------|------|
| traceId | 串联全链路 |
| 来源/渠道 | 谁调的（channel/appId/IP） |
| **请求 Header 关键项** | Content-Type、鉴权标识、X-Forwarded-For（真实 IP）、自定义业务 Header |
| **业务关键字段** | 能定位这次请求是"干什么的"（userId、orderId、cityCode 等） |

**请求 Header 该打哪些：**

| Header | 为什么要打 |
|--------|-----------|
| `Content-Type` | 确认格式对不对（json/form/xml），格式不对直接解析失败 |
| `X-Forwarded-For` / `X-Real-IP` | 真实客户端 IP，定位来源、排查 IP 维度问题 |
| `User-Agent` | 区分渠道（App/小程序/H5/爬虫） |
| `Authorization` / `token` | 确认有没有传、传的是哪个 |
| 自定义业务 Header（如 `X-Channel`、`X-App-Version`） | 业务路由/灰度/版本判断依据 |

#### 请求进来（Controller 出口）

```java
// ✅ 出口：打印返回了什么（含响应状态）
long costMs = System.currentTimeMillis() - startTime;
log.info("[Xxx接口] 返回响应 traceId={} bucket={} costMs={} "
        + "httpStatus={} resultCode={} 关键结果=[命中数={}, 首条={}]",
        traceId, LatencyBucketUtil.bucketLabel(costMs), costMs,
        httpStatus, response.getCode(), response.getTotal(),
        LatencyBucketUtil.safeKeyword(firstItemBrief, 200));
```

| 必打字段 | 说明 |
|---------|------|
| traceId + costMs + bucket | 标配 |
| **httpStatus** | HTTP 状态码（200/400/401/500 等，网关/前端会看这个） |
| resultCode | 业务状态码（成功/失败/降级） |
| **结果关键字段** | 能判断"返回对不对"（条数、首条摘要、状态等） |

#### 调用出去（BoundService 请求）

```java
// ✅ 出去：打印发出去什么（含请求 Header）
log.info("Xxx-下游调用开始 traceId={} method={} url={} "
        + "reqHeaders=[Content-Type={}, Authorization={}***] "
        + "关键入参=[query={}, page={}, size={}] timeout=[connect={}ms, read={}ms]",
        traceId, "POST", url,
        contentType, tokenPrefix,
        query, page, size, connectMs, readMs);
```

| 必打字段 | 说明 |
|---------|------|
| traceId | 串联 |
| **method** | GET/POST/PUT/DELETE（同一个 url 不同 method 行为完全不同） |
| url/目标 | 调的谁 |
| **请求 Header 关键项** | Content-Type + 鉴权信息 + 自定义 Header |
| **关键入参** | 传了什么过去（不是全量 dump，是关键业务字段） |
| 超时配置 | 当前生效的超时值（排障时确认是不是超时设太短） |

#### 调用出去（BoundService 响应）

```java
// ✅ 回来：打印收到了什么（含响应 Header 和状态码）
long costMs = System.currentTimeMillis() - startMs;
String bucket = LatencyBucketUtil.bucketLabel(costMs);
log.info("Xxx-下游调用结束 traceId={} bucket={} costMs={} "
        + "httpStatus={} respHeaders=[Content-Type={}, X-Request-Id={}] "
        + "关键响应=[code={}, total={}, 首条={}]",
        traceId, bucket, costMs,
        response.code(),
        response.header("Content-Type"),
        response.header("X-Request-Id"),
        resp.getCode(), resp.getTotal(),
        LatencyBucketUtil.safeKeyword(firstItemBrief, 300));
```

| 必打字段 | 说明 |
|---------|------|
| traceId + costMs + bucket | 标配 |
| **httpStatus** | HTTP 状态码（最重要！200/301/400/401/403/404/429/500/502/503/504 各有不同含义） |
| **响应 Header 关键项** | Content-Type（确认返回格式）、X-Request-Id（对方链路 ID，对数据用）、Rate-Limit 相关 |
| **关键响应字段** | 对方返回了什么（code、条数、首条摘要） |

**响应 Header 该打哪些：**

| Header | 为什么要打 |
|--------|-----------|
| `Content-Type` | 确认返回格式（有时对方返回 HTML 错误页但你当 JSON 解析，不打这个根本看不出来） |
| 对方的请求 ID（`X-Request-Id` / `X-Trace-Id`） | 找对方排障时，给这个 ID 对方能直接定位 |
| `Retry-After` / `X-RateLimit-*` | 被限流时需要知道 |
| `Location` | 3xx 重定向时目标地址 |

**HTTP 状态码速查（排障常用）：**

| 状态码 | 含义 | 常见原因 |
|--------|------|---------|
| 200 | 成功 | 正常（但业务 code 可能不是成功，要继续看 body） |
| 301/302 | 重定向 | URL 换了、没跟随重定向 |
| 400 | 请求格式错误 | 参数类型不对、JSON 格式错误、缺必填字段 |
| 401 | 未认证 | Token 过期/没传/格式不对 |
| 403 | 无权限 | 有 Token 但权限不够、IP 白名单没加 |
| 404 | 不存在 | URL 写错、接口已下线 |
| 429 | 限流 | 请求太频繁，看 Retry-After |
| 500 | 对方服务端错误 | 对方的 bug，拿着 X-Request-Id 找对方 |
| 502/503 | 网关/服务不可用 | 对方在发版、扩容、挂了 |
| 504 | 网关超时 | 对方处理太慢，网关先超时了 |

### "关键字段"怎么选

**不是全量打印请求/响应体**（那样日志太大、可能泄敏感信息），而是选几个能回答排障核心问题的字段：

| 排障问题 | 需要的字段 |
|---------|-----------|
| 这次请求是谁的？ | userId / channel / appId |
| 请求想干什么？ | 接口名 / 查询条件（城市/日期/关键词） |
| 对方收到了吗？传对了吗？ | 关键入参（和对方对数据用） |
| 返回的对不对？ | 结果 code + 条数 + 首条摘要 |
| 为什么慢/为什么失败？ | costMs + bucket + 异常类型 |

**选字段的原则：** 想象你凌晨三点被叫起来排障，只能看日志，你最想看到什么——那就是该打的字段。

### 存储组件 SDK 也一样

Redis/ES/MongoDB/S3/MQ 虽然不是 HTTP 调用，但一样是跨网络，一样要打"发了什么、收到什么"：

```java
// ✅ Redis：打印 key + 操作 + 结果
log.info("Redis-GET traceId={} key={} hit={} costMs={}", traceId, key, result != null, costMs);
log.info("Redis-SET traceId={} key={} valueSize={}B ttl={}s costMs={}", traceId, key, valueBytes, ttlSeconds, costMs);

// ✅ ES：打印索引 + 查询条件 + 命中数
log.info("ES-Search traceId={} index={} query={} hits={} costMs={} bucket={}",
        traceId, indexName, queryBrief, totalHits, costMs, bucket);

// ✅ MongoDB：打印 collection + 条件 + 结果数
log.info("Mongo-Find traceId={} collection={} filter={} resultCount={} costMs={} bucket={}",
        traceId, collectionName, filterBrief, resultCount, costMs, bucket);

// ✅ S3：打印 bucket + key + 文件大小
log.info("S3-Upload traceId={} bucket={} key={} fileSize={}KB costMs={} bucket={}",
        traceId, s3Bucket, objectKey, fileSizeKB, costMs, latencyBucket);

// ✅ MQ：打印 topic + key + 消息摘要
log.info("MQ-Send traceId={} topic={} msgKey={} bodySize={}B costMs={}",
        traceId, topic, msgKey, bodySize, costMs);
```

### 日志打印的边界

- **截断**：大 JSON 用 `LatencyBucketUtil.safeKeyword(json, 300)` 截断，不要全量 dump。
- **禁止打印文件内容/Base64**：只打元信息（文件名、大小、类型）。
- **批量操作打摘要**：`batchSize=50, 首条key=xxx, 末条key=yyy`，不逐条打。

### 网络边界日志检查清单

- [ ] Controller 入口打印了 traceId + 请求 Header 关键项（Content-Type/X-Forwarded-For/鉴权标识）+ 业务关键字段
- [ ] Controller 出口打印了 traceId + httpStatus + costMs + resultCode + 结果关键字段
- [ ] BoundService 请求打印了 traceId + method + url + 请求 Header（Content-Type/鉴权）+ 关键入参 + 超时配置
- [ ] BoundService 响应打印了 traceId + httpStatus + 响应 Header（Content-Type/对方 Request-Id）+ costMs + 关键响应字段
- [ ] 存储 SDK 操作打印了 traceId + 操作类型 + key/索引 + 结果/大小 + costMs
- [ ] 大 JSON 已截断
- [ ] 异常日志包含完整排障信息（httpStatus + 异常类型 + 消息 + 堆栈）

## BoundService 代码模板

```java
@Service
@CustomLog
public class XxxBoundService {

    private static final String DEFAULT_URL = "http://xxx.17usoft.com/api";

    /**
     * 调用 Xxx 下游接口
     */
    public XxxResponse callXxx(String param, String traceId) {
        String url = ConfigCenterUtil.getValue("xxx.url", DEFAULT_URL);

        // 1. 超时配置（毫秒）
        long connectMs = ConfigCenterUtil.getLong("xxx.http.connect.ms", 3000L);
        long writeMs = ConfigCenterUtil.getLong("xxx.http.write.ms", 3000L);
        long readMs = ConfigCenterUtil.getLong("xxx.http.read.ms", 10000L);

        // 2. 调用开始日志
        long startMs = System.currentTimeMillis();
        String reqBrief = LatencyBucketUtil.safeKeyword(reqJson, 300);
        log.info("Xxx-下游调用开始 traceId={} url={} connect超时ms={} read超时ms={} req={}",
                traceId, url, connectMs, readMs, reqBrief);

        try {
            // 3. 执行调用
            JSONObject resp = OkHttpClientUtil.postJson(url, reqJson, headers,
                    connectMs, writeMs, readMs, new TypeReference<JSONObject>() {});

            // 4. 调用结束日志（含耗时分桶）
            long costMs = System.currentTimeMillis() - startMs;
            String bucket = LatencyBucketUtil.bucketLabel(costMs);
            String respBrief = LatencyBucketUtil.safeKeyword(JSONUtil.toJsonStr(resp), 500);
            log.info("Xxx-下游调用结束 traceId={} bucket={} costMs={} resp={}",
                    traceId, bucket, costMs, respBrief);
            return resp;

        } catch (Exception e) {
            // 5. 异常日志（含耗时分桶）
            long costMs = System.currentTimeMillis() - startMs;
            String bucket = LatencyBucketUtil.bucketLabel(costMs);
            log.error("Xxx-下游调用异常 traceId={} bucket={} costMs={} err={}",
                    traceId, bucket, costMs, e.toString(), e);
            return buildErrorResponse("EXCEPTION", e.getMessage());
        }
    }
}
```

## Controller 接口日志模板

```java
@CustomLog
@RestController
@RequestMapping("/iopen/xxx")
public class XxxController {

    @PostMapping("/api")
    public Response<XxxResponse> doSomething(@RequestBody XxxRequest request) {
        long startTime = System.currentTimeMillis();

        // 1. 入口日志
        log.info("[Xxx接口] 开始处理, 关键参数={}",
                request.getParam1());

        // 2. 业务逻辑
        XxxResponse response = xxxService.doSomething(request);

        // 3. 出口日志（含耗时分桶）
        long costMs = System.currentTimeMillis() - startTime;
        log.info("[Xxx接口] 处理完成, bucket={}, costMs={}",
                LatencyBucketUtil.bucketLabel(costMs), costMs);

        return Response.success(response);
    }
}
```

## 超时配置规范

| 参数 | 默认值 | 说明 |
|------|--------|------|
| connect | 3000ms | 连接超时 |
| write | 3000ms | 写超时 |
| read | 8000-15000ms | 读超时，根据下游响应时间设置 |

所有超时必须从配置中心读取：
```java
long connectMs = ConfigCenterUtil.getLong("xxx.http.connect.ms", 3000L);
```

配置 key 命名：`{业务标识}.http.{connect|write|read}.ms`

## 耗时分桶

使用 `LatencyBucketUtil.bucketLabel(costMs)` 对耗时分桶，便于监控和告警：

`0-20ms` → `20-50ms` → `50-100ms` → `100-150ms` → `150-200ms` → `200-300ms` → `300-500ms` → `500-800ms` → `800-1000ms` → `1000-1500ms` → `1500-2000ms` → `2000-3000ms` → `3000-5000ms` → `5000-8000ms` → `8000-10000ms` → `>10000ms`

## 异步调用模板

适用于下游响应慢但非核心链路的场景：

```java
private static final ThreadPoolExecutor EXECUTOR = new ThreadPoolExecutor(
        4, 8, 60L, TimeUnit.SECONDS,
        new LinkedBlockingQueue<>(200),
        r -> { Thread t = new Thread(r); t.setName("xxx-bound-" + t.getId()); t.setDaemon(true); return t; },
        new ThreadPoolExecutor.AbortPolicy()
);

public XxxResponse call(String param, String traceId) {
    int discardWaitMs = ConfigCenterUtil.getInteger("xxx.discard.ms", 1500);
    Future<XxxResponse> future = EXECUTOR.submit(() -> doCall(param, traceId));
    try {
        return future.get(discardWaitMs, TimeUnit.MILLISECONDS);
    } catch (TimeoutException e) {
        future.cancel(true);
        return degraded("timeout", traceId);
    }
}
```

## 存储组件 SDK 的网络规范

> **核心认知：Redis/ES/MongoDB/S3/MQ 的 SDK 调用本质都是网络 IO，必须和 HTTP 外部调用一样对待——超时、耗时监控、异常处理，一个都不能少。**

### 统一原则

1. **所有网络操作必须有超时**：连接超时 + 读写超时，不允许无限等待。
2. **所有网络操作必须有耗时日志**：costMs + bucket，和 BoundService 同标准。
3. **所有网络操作必须有异常处理**：网络异常 ≠ 业务异常，要区分处理。
4. **超时参数配置化**：从配置中心读取，支持动态调整。

### 各组件超时配置

#### Redis

```java
// ✅ 连接池 + 超时配置化
int connectTimeoutMs = ConfigCenterUtil.getInteger("redis.connect.timeout.ms", 2000);
int readTimeoutMs = ConfigCenterUtil.getInteger("redis.read.timeout.ms", 2000);
int maxTotal = ConfigCenterUtil.getInteger("redis.pool.max.total", 50);
int maxIdle = ConfigCenterUtil.getInteger("redis.pool.max.idle", 20);
int maxWaitMs = ConfigCenterUtil.getInteger("redis.pool.max.wait.ms", 3000);
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| connect.timeout | 2000ms | 连接超时 |
| read.timeout | 2000ms | 读写超时 |
| pool.max.total | 50 | 最大连接数 |
| pool.max.idle | 20 | 最大空闲连接 |
| pool.max.wait | 3000ms | 获取连接最大等待时间 |

**关键风险点：**
- Redis 挂了或网络抖动时，如果没有超时，线程会被阻塞，连接池耗尽，拖垮整个服务。
- Pipeline/批量操作更要注意：批次越大，网络耗时越长。

#### Elasticsearch

```java
// ✅ RestClient 超时配置
RestClientBuilder builder = RestClient.builder(hosts)
    .setRequestConfigCallback(config -> config
        .setConnectTimeout(ConfigCenterUtil.getInteger("es.connect.timeout.ms", 3000))
        .setSocketTimeout(ConfigCenterUtil.getInteger("es.socket.timeout.ms", 10000))
        .setConnectionRequestTimeout(ConfigCenterUtil.getInteger("es.pool.timeout.ms", 3000))
    );
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| connect.timeout | 3000ms | TCP 连接超时 |
| socket.timeout | 10000ms | 读写超时（ES 查询可能较慢，给大一些） |
| pool.timeout | 3000ms | 从连接池获取连接超时 |

**关键风险点：**
- ES 慢查询（聚合/全文检索）可能耗时很长，socket.timeout 要按业务场景设置，不能一刀切太短。
- 但也不能不设——不设就是无限等待。

#### MongoDB

```java
// ✅ MongoClient 超时配置
MongoClientSettings settings = MongoClientSettings.builder()
    .applyConnectionString(connectionString)
    .applyToClusterSettings(cluster -> cluster
        .serverSelectionTimeout(
            ConfigCenterUtil.getInteger("mongo.server.selection.timeout.ms", 5000),
            TimeUnit.MILLISECONDS))
    .applyToSocketSettings(socket -> socket
        .connectTimeout(
            ConfigCenterUtil.getInteger("mongo.connect.timeout.ms", 3000),
            TimeUnit.MILLISECONDS)
        .readTimeout(
            ConfigCenterUtil.getInteger("mongo.read.timeout.ms", 10000),
            TimeUnit.MILLISECONDS))
    .applyToConnectionPoolSettings(pool -> pool
        .maxSize(ConfigCenterUtil.getInteger("mongo.pool.max.size", 50))
        .maxWaitTime(
            ConfigCenterUtil.getInteger("mongo.pool.max.wait.ms", 3000),
            TimeUnit.MILLISECONDS))
    .build();
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| server.selection.timeout | 5000ms | 选择可用节点超时 |
| connect.timeout | 3000ms | TCP 连接超时 |
| read.timeout | 10000ms | 读写超时 |
| pool.max.size | 50 | 最大连接数 |
| pool.max.wait | 3000ms | 获取连接最大等待时间 |

**关键风险点：**
- MongoDB 主从切换时 `serverSelectionTimeout` 是关键——太短会大量报错，太长会阻塞线程。
- Working Set 不在内存时，查询走磁盘，读超时可能不够。

#### S3/对象存储

```java
// ✅ S3 Client 超时配置
ClientConfiguration clientConfig = new ClientConfiguration();
clientConfig.setConnectionTimeout(
    ConfigCenterUtil.getInteger("s3.connect.timeout.ms", 5000));
clientConfig.setSocketTimeout(
    ConfigCenterUtil.getInteger("s3.socket.timeout.ms", 30000));  // 大文件上传需要更长
clientConfig.setMaxConnections(
    ConfigCenterUtil.getInteger("s3.pool.max.connections", 50));
clientConfig.setConnectionMaxIdleMillis(
    ConfigCenterUtil.getLong("s3.pool.max.idle.ms", 60000L));
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| connect.timeout | 5000ms | TCP 连接超时 |
| socket.timeout | 30000ms | 读写超时（大文件上传要给足） |
| pool.max.connections | 50 | 最大连接数 |

**关键风险点：**
- 上传大文件时网络中断，如果没有超时，线程会长时间阻塞。
- 外部图片 URL 下载后转存场景，下载那一步也要有超时（OkHttp 的 read timeout）。

#### MQ 生产者

```java
// ✅ 生产者超时配置
producer.setSendMsgTimeout(
    ConfigCenterUtil.getInteger("mq.send.timeout.ms", 3000));
```

| 参数 | 默认值 | 说明 |
|------|--------|------|
| send.timeout | 3000ms | 消息发送超时 |

### 耗时监控统一模板

**所有存储组件操作都要按这个模板记录耗时：**

```java
// ✅ 存储操作耗时监控模板
long startMs = System.currentTimeMillis();
try {
    // 执行存储操作（Redis/ES/MongoDB/S3/MQ）
    result = doStorageOperation();

    long costMs = System.currentTimeMillis() - startMs;
    String bucket = LatencyBucketUtil.bucketLabel(costMs);
    log.info("{}-操作完成 traceId={} bucket={} costMs={} key={}",
            storageType, traceId, bucket, costMs, operationKey);
    return result;

} catch (Exception e) {
    long costMs = System.currentTimeMillis() - startMs;
    String bucket = LatencyBucketUtil.bucketLabel(costMs);
    log.error("{}-操作异常 traceId={} bucket={} costMs={} key={} err={}",
            storageType, traceId, bucket, costMs, operationKey, e.toString(), e);
    // 降级处理
    return fallback();
}
```

**耗时告警阈值建议：**

| 组件 | P99 目标 | warn 阈值 | error 阈值 |
|------|---------|----------|-----------|
| Redis 单次读写 | < 10ms | > 50ms | > 200ms |
| Redis Pipeline | < 50ms | > 200ms | > 1s |
| ES 简单查询 | < 100ms | > 500ms | > 2s |
| ES 聚合查询 | < 500ms | > 2s | > 5s |
| MongoDB 单次查询 | < 50ms | > 200ms | > 1s |
| MongoDB 聚合 | < 500ms | > 2s | > 5s |
| S3 上传（小文件 < 5MB） | < 1s | > 3s | > 10s |
| S3 上传（大文件 > 50MB） | < 30s | > 60s | > 120s |
| MQ 发送 | < 50ms | > 200ms | > 1s |

**超过 warn 阈值时自动降级日志级别：**

```java
long costMs = System.currentTimeMillis() - startMs;
String bucket = LatencyBucketUtil.bucketLabel(costMs);
if (costMs > errorThresholdMs) {
    log.error("{}-操作耗时过长 traceId={} bucket={} costMs={} key={}",
            storageType, traceId, bucket, costMs, operationKey);
} else if (costMs > warnThresholdMs) {
    log.warn("{}-操作偏慢 traceId={} bucket={} costMs={} key={}",
            storageType, traceId, bucket, costMs, operationKey);
} else {
    log.info("{}-操作完成 traceId={} bucket={} costMs={} key={}",
            storageType, traceId, bucket, costMs, operationKey);
}
```

### 网络故障处理策略

网络操作都可能失败。**默认不重试，靠日志排障 + 降级兜底。**

> **铁律：不要自动重试。** 重试 = 重复执行，非幂等操作重试一次就是多扣一次钱、多发一条消息、多插一条数据。出了问题靠日志定位，靠人工或补偿机制处理。

#### 失败时必须打印的信息

```java
// ✅ 失败日志必须包含完整排障信息
log.error("{}-操作失败 traceId={} bucket={} costMs={} "
        + "操作类型={} key={} 入参摘要={} 异常类型={} err={}",
        storageType, traceId, bucket, costMs,
        operationType, operationKey, paramBrief,
        e.getClass().getSimpleName(), e.getMessage(), e);
```

**日志必须包含以下字段，缺一个都不利于排障：**

| 字段 | 说明 | 示例 |
|------|------|------|
| storageType | 哪个组件 | Redis / ES / MongoDB / S3 / MQ |
| traceId | 链路 ID | 串联上下游 |
| costMs + bucket | 耗时 + 分桶 | 判断是超时还是秒失败 |
| 操作类型 | 读/写/删除/查询 | get / set / bulk / upload |
| key | 操作的 key/索引/Collection | 定位具体数据 |
| 入参摘要 | 关键入参（截断） | 知道当时传了什么 |
| 异常类型 + 消息 | 根因 | TimeoutException / ConnectionRefused |

#### 降级策略

| 组件 | 降级策略 |
|------|---------|
| Redis 读失败 | 回源数据库查询（Cache Aside 兜底） |
| Redis 写失败 | 允许跳过（下次请求会重新缓存），记 warn 日志 |
| ES 查询失败 | 降级到 MySQL 查询（功能降级），或返回空结果 + 提示 |
| MongoDB 查询失败 | 降级到缓存/MySQL（如果有冗余），或返回空 + 提示 |
| S3 上传失败 | 记录完整日志（文件名/大小/目标 bucket），人工介入或走补偿任务 |
| MQ 发送失败 | 落本地消息表（含完整消息体），由补偿任务定期扫描重发 |

### 连接池健康监控

**所有使用连接池的组件都必须有健康监控：**

```java
// ✅ 定期打印连接池状态（通用模板）
@Scheduled(fixedRate = 60000)
public void logPoolMetrics() {
    // Redis 连接池
    log.info("Redis连接池 active={} idle={} waiters={}",
            pool.getNumActive(), pool.getNumIdle(), pool.getNumWaiters());

    // MySQL 连接池
    log.info("DB连接池 active={} idle={} maxActive={} waitCount={}",
            dataSource.getActiveCount(), dataSource.getPoolingCount(),
            dataSource.getMaxActive(), dataSource.getWaitThreadCount());
}
```

**连接池告警条件：**
- 活跃连接 > 池大小 80%
- 等待线程 > 0 持续 1 分钟
- 获取连接超时次数 > 0
