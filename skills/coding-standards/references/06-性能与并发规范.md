# 06 — 性能与并发规范

## 一、性能规范

### 写代码时主动思考

每写一段涉及 IO/网络/计算的代码，问自己：

1. 能否**批量处理**，减少频繁调用？
2. 是否可以用**缓存**降低重复查询？
3. 是否存在**阻塞点**，需要异步/队列？
4. 是否需要**限流/超时/降级**？
5. 资源是否正确释放（连接、文件句柄、流）？

### 常见性能坑

#### N+1 查询

```java
// ❌ 循环里查数据库
for (Order order : orders) {
    User user = userDao.getById(order.getUserId());
}

// ✅ 批量查询 + Map
Set<Long> userIds = orders.stream().map(Order::getUserId).collect(Collectors.toSet());
Map<Long, User> userMap = userDao.listByIds(userIds).stream()
    .collect(Collectors.toMap(User::getId, Function.identity()));
```

#### 无界分页

```java
// ❌ 不限制分页大小
List<User> users = userDao.list(pageNum, pageSize);  // pageSize 可以传 999999

// ✅ 限制最大分页
int maxPageSize = ConfigCenterUtil.getInteger("query.max.page.size", 100);
int safePageSize = Math.min(pageSize, maxPageSize);
```

#### 循环内 IO

```java
// ❌ 循环里发 HTTP
for (String city : cities) {
    weatherService.query(city);  // 每个城市一次 HTTP
}

// ✅ 批量接口 或 并行调用
List<WeatherInfo> results = weatherService.batchQuery(cities);
```

#### 大对象序列化

```java
// ❌ 把整个大对象序列化到日志/缓存
log.info("result={}", JSONUtil.toJsonStr(hugeObject));

// ✅ 只打摘要
log.info("result size={} firstItem={}", list.size(), list.get(0));
```

### 批处理规范

- batch size 必须配置化，建议默认 200-500。
- 批处理必须有汇总日志（total/success/fail/costMs）。
- 大批量任务考虑分批+sleep，避免打满数据库连接。

## 二、并发规范

### 线程池

#### 必须隔离

不同业务使用**独立的线程池**，不共用一个：

```java
// ✅ 独立线程池，命名清晰
private static final ThreadPoolExecutor WEATHER_POOL = new ThreadPoolExecutor(
    4, 8, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(200),
    r -> { Thread t = new Thread(r); t.setName("weather-query-" + t.getId()); t.setDaemon(true); return t; },
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

#### 参数配置化

```java
int coreSize = ConfigCenterUtil.getInteger("xxx.pool.core", 4);
int maxSize = ConfigCenterUtil.getInteger("xxx.pool.max", 8);
int queueSize = ConfigCenterUtil.getInteger("xxx.pool.queue", 200);
```

#### 拒绝策略必须明确

| 策略 | 适用场景 |
|------|---------|
| `CallerRunsPolicy` | 不能丢弃，降速处理 |
| `AbortPolicy` | 超出直接拒绝，适合有降级方案的场景 |
| `DiscardOldestPolicy` | 可以丢弃旧任务（慎用） |

#### 异步异常处理

```java
// ❌ 异步任务异常被吞掉
executor.submit(() -> doWork());

// ✅ 捕获异常并记录
executor.submit(() -> {
    try {
        doWork();
    } catch (Exception e) {
        log.error("异步任务异常 err={}", e.toString(), e);
    }
});
```

#### 异步任务超时兜底

异步任务必须有超时机制，防止任务卡住占满线程池：

```java
// ✅ CompletableFuture 带超时
CompletableFuture<Result> future = CompletableFuture.supplyAsync(() -> doWork(), WEATHER_POOL);
try {
    int timeoutMs = ConfigCenterUtil.getInteger("xxx.async.timeout.ms", 5000);
    Result result = future.get(timeoutMs, TimeUnit.MILLISECONDS);
} catch (TimeoutException e) {
    future.cancel(true);
    log.error("异步任务超时 timeoutMs={} err={}", timeoutMs, e.toString());
    // 走降级逻辑
}
```

**要求：**
- 超时时间必须配置化，有合理默认值。
- 超时后主动 `cancel` + 记录日志 + 走降级。
- 禁止无超时的 `future.get()`（会永远阻塞）。

#### 线程池监控

线程池是"看不见的后台执行者"，必须暴露运行状态到监控：

```java
// ✅ 定期打印线程池状态（或注册到监控指标）
@Scheduled(fixedRate = 60_000)
public void logPoolMetrics() {
    log.info("线程池状态 pool={} active={} queue={} completed={} rejected={}",
            "WEATHER_POOL",
            WEATHER_POOL.getActiveCount(),
            WEATHER_POOL.getQueue().size(),
            WEATHER_POOL.getCompletedTaskCount(),
            getRejectedCount());  // 自行维护拒绝计数
}
```

**必须监控的指标：**

| 指标 | 含义 | 告警阈值建议 |
|------|------|-------------|
| `activeCount` | 当前活跃线程数 | 持续 >= maxPoolSize 的 80% |
| `queue.size` | 等待队列积压数 | 持续 >= queueCapacity 的 50% |
| `completedTaskCount` | 已完成任务总数 | 用于趋势观察 |
| `rejectedCount` | 被拒绝的任务数 | > 0 就告警 |

**原则：线程池不能是黑盒。** 如果队列积压、拒绝增多、活跃线程打满——必须能从监控/日志里看到，而不是等业务出问题了才发现。

#### 线程池优雅关闭

应用停机时必须正确关闭线程池，避免任务丢失：

```java
@PreDestroy
public void shutdown() {
    log.info("线程池关闭开始 pool=WEATHER_POOL queue={}", WEATHER_POOL.getQueue().size());
    WEATHER_POOL.shutdown();  // 不再接受新任务
    try {
        // 等待已提交任务完成
        int waitSeconds = ConfigCenterUtil.getInteger("xxx.pool.shutdown.wait.seconds", 30);
        if (!WEATHER_POOL.awaitTermination(waitSeconds, TimeUnit.SECONDS)) {
            log.warn("线程池等待超时，强制关闭 pool=WEATHER_POOL droppedTasks={}",
                    WEATHER_POOL.shutdownNow().size());
        }
    } catch (InterruptedException e) {
        WEATHER_POOL.shutdownNow();
        Thread.currentThread().interrupt();
    }
    log.info("线程池关闭完成 pool=WEATHER_POOL");
}
```

**要求：**
- 先 `shutdown()`（温和），等待一段时间后再 `shutdownNow()`（强制）。
- 等待时间配置化，默认 30 秒。
- 关闭前后都有日志，记录队列剩余任务数。
- 强制关闭时记录丢弃的任务数量。

### 并发写保护

同一资源并发修改时需要保护：

| 方案 | 适用场景 | 示例 |
|------|---------|------|
| **乐观锁** | 冲突少，读多写少 | `UPDATE ... SET version=version+1 WHERE id=? AND version=?` |
| **分布式锁** | 跨实例互斥 | Redis setnx + 过期时间 |
| **幂等设计** | 重复请求不产生副作用 | 唯一键去重 |

### 跨线程可见性

多线程场景下，**JMM（Java 内存模型）不保证非 volatile 字段的跨线程可见性**。ConcurrentHashMap 保证桶操作原子性，但**不保证 Value 对象内部字段的可见性**。

#### 规则：共享对象的字段必须 volatile

当一个对象被多个线程读写时，其可变字段必须加 `volatile`：

```java
// ❌ ConcurrentHashMap 保证了 map 操作原子，但 Entry 字段对其他线程不可见
class RiskEntry {
    String llmResult;       // 线程 A 写入后，线程 B 可能读到 null（CPU 缓存未刷新）
    String riskCenterResult;
}

ConcurrentHashMap<String, RiskEntry> map = new ConcurrentHashMap<>();
map.computeIfAbsent(traceId, k -> new RiskEntry());
entry.llmResult = "risk";  // 线程 A 写
// 线程 B 读 entry.llmResult → 可能是 null！

// ✅ volatile 保证跨线程可见
class RiskEntry {
    volatile String llmResult;
    volatile String riskCenterResult;
}
```

#### 规则：ConcurrentHashMap 的 Value 不能整体替换覆盖

`ConcurrentHashMap.put(key, newValue)` 会**替换整个 Value**，导致其他线程之前写入的内部字段丢失：

```java
// ❌ 输入侧检测结果写入
entry.reqLlmResult = "risk";

// 输出侧检测同时触发，put 创建全新 Entry，丢失输入侧结果
map.put(traceId, new Entry("risk", now));  // reqLlmResult 被丢失！

// ✅ 只更新需要修改的字段，不替换整个 Entry
Entry entry = map.get(traceId);
if (entry != null) {
    entry.outPutResult = "risk";   // volatile 写，其他线程立即可见
} else {
    map.put(traceId, new Entry("risk", now));
}
```

#### 规则：复合操作不是原子的

`get → 判断 → put` 序列不是原子的，高并发下会出问题：

```java
// ❌ 两个线程可能同时读到 null，各自创建新 Entry，后写的覆盖先写的
Entry entry = map.get(traceId);
if (entry == null) {
    map.put(traceId, new Entry(...));  // 竞态：另一个线程可能同时 put
}

// ✅ 用 computeIfAbsent 保证原子创建
Entry entry = map.computeIfAbsent(traceId, k -> new Entry(...));
entry.someField = "value";  // volatile 写
```

#### 检查场景

以下场景必须审查跨线程可见性：

| 场景 | 典型例子 | 检查点 |
|------|---------|--------|
| 异步回调写共享状态 | Dubbo/Future 回调写结果 | 字段是否 volatile |
| 轮询等待结果 | 主线程轮询检测结果 | 读到的字段是否可能 stale |
| 多路检测聚合 | 输入侧/输出侧同时写同一个 traceId | put 是否覆盖整个 Entry |
| 本地缓存 + 远程缓存 | Caffeine + Redis 两级缓存 | 是否存在 remove 和 write 之间的竞态窗口 |
| RequestContext 跨线程 | 异步线程读写 ctx | 复合操作（get→modify→put）是否原子 |

### 上下文传递

异步/跨线程时注意传递：
- traceId（MDC）
- 用户信息
- 租户信息

参见 `04-可观测性规范.md` 中的 traceId 异步传递章节。

## 三、资源管理

### 连接池

- 数据库连接池、Redis 连接池、HTTP 连接池都必须有合理配置。
- 参数配置化，支持动态调整。
- 监控连接池使用率，设置告警。

### 资源释放

```java
// ✅ try-with-resources
try (InputStream is = new FileInputStream(file)) {
    // 处理
}

// ❌ 手动关闭容易遗漏
InputStream is = new FileInputStream(file);
// ... 如果中间抛异常，is 就泄漏了
is.close();
```

## 检查清单

- [ ] 有没有 N+1 查询、循环内 IO？
- [ ] 分页有上限限制？
- [ ] 批处理有 batch size 控制？
- [ ] 线程池独立、命名清晰、参数配置化？
- [ ] 拒绝策略明确？异步异常有处理？
- [ ] 异步任务有超时兜底？禁止无超时的 `future.get()`？
- [ ] 线程池运行状态暴露到监控/日志（active/queue/rejected）？
- [ ] 应用停机时线程池优雅关闭（shutdown → awaitTermination → shutdownNow）？
- [ ] 并发写有保护（乐观锁/分布式锁/幂等）？
- [ ] 资源正确释放（连接、流、文件句柄）？
- [ ] 关键参数（超时/阈值/开关）配置化？
