# 05 — 异常与错误处理规范

## 总则

- **不吞异常**：catch 了必须有日志或处理，禁止空 catch。
- **快速失败**：能在入口校验就校验，不要带着错误数据跑到最后才炸。
- **统一出口**：异常信息通过统一的错误响应格式返回，不要每个接口自己搞一套。

## 异常分类

| 类型 | 特征 | 处理方式 |
|------|------|---------|
| **业务异常** | 预期内的业务错误（参数非法、余额不足、状态不允许） | 返回明确错误码 + 错误信息，不打 ERROR 日志（WARN 即可） |
| **系统异常** | 非预期错误（NPE、DB 超时、OOM） | 打 ERROR 日志，返回通用错误码，触发告警 |
| **外部异常** | 外部系统返回错误或超时 | 打 WARN/ERROR 日志，根据策略重试或降级 |

## 异常处理规范

### 不要吞异常

```java
// ❌ 空 catch，出了问题完全无法排查
try {
    doSomething();
} catch (Exception e) {
    // nothing
}

// ✅ 至少记录日志
try {
    doSomething();
} catch (Exception e) {
    log.error("处理失败 traceId={} param={} err={}", traceId, param, e.toString(), e);
    throw new BusinessException(ErrorCode.SYSTEM_ERROR, "处理失败");
}
```

### 异常信息要够定位

```java
// ❌ 信息不够
log.error("调用失败", e);

// ✅ 带上关键上下文
log.error("用户积分扣减失败 userId={} amount={} traceId={} err={}",
        userId, amount, traceId, e.toString(), e);
```

### 区分可重试与不可重试

```java
// 可重试异常：超时、网络抖动 → 重试
if (e instanceof SocketTimeoutException) {
    // 重试逻辑
}

// 不可重试异常：参数错误、权限不足 → 直接返回错误
if (e instanceof IllegalArgumentException) {
    return Result.fail(ErrorCode.PARAM_ERROR, e.getMessage());
}
```

## 错误码规范

### 格式

```
{模块}.{子模块}.{错误类型}
```

示例：
- `POINT.DEDUCT.BALANCE_NOT_ENOUGH` — 积分扣减余额不足
- `USER.AUTH.TOKEN_EXPIRED` — 用户认证 token 过期
- `BOUND.WEATHER.TIMEOUT` — 天气接口超时

### 错误码原则

- 每个错误码对应一种明确的错误场景，不要用一个 `SYSTEM_ERROR` 包打天下。
- 错误码要能帮助**前端展示合理提示**和**后端快速定位**。
- 新增错误码必须在统一的错误码枚举中注册。

## 降级策略

外部调用失败时，不能直接让整个请求崩掉：

| 策略 | 适用场景 | 示例 |
|------|---------|------|
| **返回默认值** | 非核心数据缺失可接受 | 天气查询失败 → 返回"暂无天气信息" |
| **返回缓存数据** | 数据有时效但可接受短暂过期 | 配置查询失败 → 返回上次缓存 |
| **跳过非核心步骤** | 失败不影响主流程 | 埋点发送失败 → 跳过，不影响业务 |
| **返回错误** | 核心链路，必须告知用户 | 支付失败 → 明确提示用户 |

```java
try {
    WeatherInfo weather = weatherBoundService.query(city, traceId);
    return weather;
} catch (Exception e) {
    log.warn("天气查询降级 city={} traceId={} err={}", city, traceId, e.toString());
    return WeatherInfo.defaultEmpty();  // 降级：返回空天气
}
```

## 重试规范

- 只对**可重试异常**重试（超时、网络抖动），不对业务异常重试。
- 重试次数和间隔**配置化**。
- 重试必须有**上限**，不能无限重试。
- 重试日志要标明是第几次重试。

```java
int maxRetry = ConfigCenterUtil.getInteger("xxx.retry.max", 3);
for (int i = 1; i <= maxRetry; i++) {
    try {
        return doCall();
    } catch (SocketTimeoutException e) {
        log.warn("调用超时-重试 retry={}/{} traceId={}", i, maxRetry, traceId);
        if (i == maxRetry) {
            log.error("调用超时-重试耗尽 traceId={}", traceId);
            return degraded();
        }
    }
}
```

## 客户端请求校验规范

**面向客户端的接口，不要用 `@Size`、`@NotBlank` 等 JSR 校验注解直接拦截返回错误信息，改为 Service 层判断后静默返回空结果/默认值。**

原因：校验注解失败会直接把错误信息（如"关键词最大50字符"）暴露给客户端，体验差且有信息泄露风险。在 Service 层判断可以优雅降级，不影响用户核心流程。

```java
// ❌ 校验注解直接暴露错误给客户端
@NotBlank(message = "关键词不能为空")
@Size(max = 50, message = "关键词最大50字符")
private String keyword;

// ✅ Request 只做字段定义，Service 层判断后静默返回
@ApiModelProperty(value = "搜索关键词", example = "北京")
private String keyword;

// Service 中：
if (StringUtils.isBlank(keyword) || keyword.length() > MAX_INPUT_LENGTH) {
    return Collections.emptyList();  // 静默返回，不报错
}
```

**例外**：需要明确告知用户参数错误的场景（如登录、支付等核心链路），仍然使用校验注解 + 明确错误码。

## 检查清单

- [ ] 没有空 catch（吞异常）？
- [ ] 异常日志带了关键上下文（谁、什么参数、traceId）？
- [ ] 区分了业务异常和系统异常？日志级别正确？
- [ ] 错误码明确、有意义，不是笼统的 SYSTEM_ERROR？
- [ ] 外部调用失败有降级方案？
- [ ] 重试只针对可重试异常？有次数上限？
- [ ] 面向客户端的非核心接口，避免用校验注解直接暴露错误信息，改用 Service 层静默降级？
