# 04 — 可观测性规范

> 目标：代码发布到 QA 或生产后，不只在出问题时能排障，还能主动验证本次改动实际走了哪个逻辑分支、为什么走、结果是什么、花了多久。

## 自主部署阶段铁律

**可观测性是编码完成和允许部署的前置条件，不是上线后的补救项。** Codex 编写或修改的业务逻辑，必须能通过 QA/生产默认开启的日志还原真实执行路径；如果发布后无法仅凭 `traceId`、业务标识和稳定日志关键词判断改动是否按预期生效，代码不得进入部署阶段。

强制要求：

1. **新增或修改的业务分支必须可辨识**：会改变业务结果的开关、路由、策略选择、过滤/跳过、提前返回、兜底/降级、状态迁移等分支，都要留下分支决策日志。
2. **日志必须说明决策，不只说明位置**：至少包含 `decision/result`、`reason`、关键判断依据、业务标识和 `traceId`；禁止只写“进入 if”“执行 else”这类无法验收的日志。
3. **生产环境默认可见**：正常业务分支使用 `INFO`，异常或已兜底分支使用 `WARN/ERROR`，不得把验收所需日志写成默认关闭的 `DEBUG`。
4. **能按改动逐分支验收**：编码完成前列出“分支 → 触发条件 → 预期日志关键词/字段”，E2E 必须覆盖本次改动的主要分支，并核对实际日志。
5. **可观测不等于刷屏**：只记录会影响业务结果、且无法从入口/出口推断的决策点；循环和批处理用汇总日志，高频明细使用配置开关，敏感信息和大对象仍按安全、截断规则处理。

## 日志级别规范

### 禁止使用 DEBUG 级别

**生产代码中禁止使用 `log.debug`**，理由：

1. **线上默认不输出**：DEBUG 在生产环境通常关闭，写了也看不到，等于没有日志。
2. **要么删掉，要么升级**：如果日志有价值就改成 INFO/WARN；如果只是调试用的，不应该留在代码里。
3. **避免噪音**：DEBUG 改成 INFO 后如果太吵，说明这条日志本身就不该存在——直接删除。

**唯一例外**：专门用于日志转发/透传的接口（如前端日志上报），可以保留 DEBUG。

### 级别选择规则

| 级别 | 使用场景 | 示例 |
|------|---------|------|
| **ERROR** | 需要立即关注的故障，影响业务主流程 | 外部服务不可用、数据不一致 |
| **WARN** | 异常但已兜底处理，需关注但不影响主流程 | 限流触发、降级兜底、解析失败但已跳过 |
| **INFO** | 业务关键节点的正常流转 | 请求入口/出口、状态变更、外部调用前后 |

### 哪些日志不该存在

| 类型 | 为什么不该有 | 正确做法 |
|------|-------------|---------|
| Filter 逐 header 遍历 | 每个请求都打，刷屏 | 删除 |
| 内部遍历/匹配细节 | 纯调试信息，无业务含义 | 删除 |
| SSE 逐事件日志 | 流式数据量大，逐事件太吵 | 删除 |
| 不影响业务结果、可由出口直接推断的默认值分支 | 没有独立验收价值 | 合并到出口摘要；若默认值会改变业务结果，则保留分支决策日志 |
| 正常客户端断连 | HTTP 连接关闭是正常行为 | 删除 |
| 敏感信息（签名原文、密钥） | 安全风险 | 删除 |

## 日志总则

- 日志**全部使用中文**描述业务含义，字段名/结构体可以用英文。
- 一条日志能看懂：当前在做哪一步、用什么参数、结果如何、耗时多少。
- 正常路径少说话（少无意义输出），异常路径大声说话（日志清晰可查）。
- 控制日志量：不要无意义的 debug 噪音，但关键路径必须有。
- 新增或修改逻辑优先保证发布后可验证，再考虑精简日志；精简不能破坏分支可辨识性。
- **禁止使用 DEBUG 级别**，详见上方"日志级别规范"。

## 必须覆盖的日志节点

| 节点 | 日志级别 | 必须包含 |
|------|---------|---------|
| **入口** | INFO | 关键入参、requestId/traceId |
| **分支决策** | INFO/WARN | decision/result、reason、关键判断依据、业务标识、traceId |
| **重要步骤** | INFO | 状态变更、调用外部服务前后 |
| **异常与降级** | ERROR/WARN | 错误类型、关键上下文、是否重试/降级 |
| **出口** | INFO | 摘要结果、总耗时 |

## 分支决策日志

### 必须记录的分支

| 分支类型 | 需要看见的内容 |
|----------|----------------|
| 功能开关、灰度和配置分流 | 开关/配置键、生效值、最终走向 |
| 路由、策略、规则命中 | 候选策略、命中策略、命中原因 |
| 过滤、跳过、提前返回 | 被过滤/跳过的业务对象摘要、原因、返回结果 |
| 兜底、降级、重试或补偿 | 原路径失败原因、采用的兜底、最终结果 |
| 状态迁移和幂等判断 | 原状态、目标状态、执行/跳过决定及原因 |
| 外部结果驱动的业务判断 | 外部结果摘要、判断依据、后续动作 |

### 推荐格式

使用稳定的模块前缀和可检索字段，日志文案不要依赖临时调试描述：

```java
if (!featureEnabled) {
    log.info("[活动任务] 分支决策 decision=SKIP reason=SWITCH_OFF userId={} configKey={} traceId={}",
            userId, configKey, traceId);
    return TaskResult.skipped();
}

String strategy = selectStrategy(scene, userLevel);
log.info("[活动任务] 分支决策 decision=EXECUTE reason=STRATEGY_MATCH userId={} scene={} userLevel={} strategy={} traceId={}",
        userId, scene, userLevel, strategy, traceId);
```

错误示例：

```java
log.info("进入 if 分支");       // 不知道哪个业务、为何进入、处理谁
log.debug("命中方案 B");       // 生产默认不可见，无法作为部署后验收证据
log.info("request={}", request); // 全量对象可能包含敏感信息且无法直接表达决策
```

## traceId 规范

- traceId 必须贯穿整个请求链路，从 Controller 入口一路传到最底层。
- 异步线程必须传递 MDC（线程池提交任务时手动传递）。
- 跨服务调用时 traceId 放在 Header 中透传。

获取方式：
```java
String traceId = MDC.get("traceId");
// 或
String traceId = ApmTraceUtils.getTraceId();
```

异步场景传递：
```java
// 提交异步任务前
Map<String, String> contextMap = MDC.getCopyOfContextMap();
executor.submit(() -> {
    MDC.setContextMap(contextMap);  // 恢复上下文
    try {
        doWork();
    } finally {
        MDC.clear();
    }
});
```

## 耗时日志

所有涉及 IO 的操作（HTTP/RPC/DB/Redis/MQ）都要记录耗时：

```java
long startMs = System.currentTimeMillis();
// ... 执行操作 ...
long costMs = System.currentTimeMillis() - startMs;
String bucket = LatencyBucketUtil.bucketLabel(costMs);
log.info("操作描述 traceId={} bucket={} costMs={}", traceId, bucket, costMs);
```

**`bucket` 和 `costMs` 必须同时出现**，bucket 用于聚合统计，costMs 用于精确排查。

## 批处理日志

批处理不要逐条刷屏，用**汇总日志**：

```java
log.info("批量处理完成 total={} success={} fail={} costMs={} 失败原因汇总={}",
        total, successCount, failCount, costMs, failReasonSummary);
```

如需调试，用**详细日志开关**：
```java
boolean detailLog = ConfigCenterUtil.getBoolean("xxx.batch.detail.log", false);
if (detailLog) {
    log.info("批量处理明细 item={} result={}", item, result);
}
```

## 误导日志防范

常见坑：
- request/response 写反
- catch 后日志缺上下文（不知道是哪个请求出的错）
- 变量打错（打了另一个变量的值）
- 日志级别用错（异常用了 INFO）

## 模块前缀标识规范

多层架构中，日志前缀是快速定位"这行日志来自哪个模块"的关键。

### 前缀格式

```
[模块名] 中文描述 key=value
[模块名][子模块] 中文描述 key=value
```

### 命名规则

| 规则 | 正确示例 | 错误示例 |
|------|---------|---------|
| **无横线**，用中文全称 | `[V3模板渲染]` | `[V3-模板渲染]` |
| **最多两层嵌套**，不超过 `[A][B]` | `[推荐聚合][动态混合]` | `[dynamicRecommend][混合][V3-模板渲染][V2-向量库搜索]` |
| **每个模块一个固定前缀** | Controller 统一用 `[推荐问题]` | 有的带、有的不带 |
| **方法名不入前缀**，放在描述里 | `[推荐聚合] dynamicRecommend 开始` | `[dynamicRecommend][START]` |

### 前缀分配示例（推荐模块）

| 类 | 前缀 |
|----|------|
| RecommendQuestionController | `[推荐问题]` |
| RecommendDispatcher | `[推荐分发]` |
| AgentRecommendService | `[推荐聚合]` |
| RecommendSupportV3Service | `[V3模板渲染]` |
| RecommendSupportV2Service | `[V2向量搜索]` |
| SugByOrderTemplateV0Processor | `[V3模板渲染]`（从属于 V3 链路） |

### 结果 JSON 去重

同一份结果对象，**只在最终出口打印一次完整 JSON**，中间过程只打 `size`：

```java
// 中间步骤 — 只打 size
log.info("[推荐聚合][动态混合] 混合完成 mixedSize={}", mixed.size());

// 最终出口 — 打完整结果（如有必要，截断）
log.info("[推荐聚合] 完成 unionId={} resultSize={} costMs={} bucket={}", unionId, size, costMs, bucket);
```

**为什么**：同一份 JSON 在 V3 出口打一次、mix 出口打一次、dynamicRecommend 出口又打一次 → 日志体积翻 3 倍，排障时反而看花眼。

### 重复逻辑日志

如果同一段计算逻辑在多个层都会执行（如 scene count 计算在聚合层和模板层都有），**详细日志只在最上层打，下层只打汇总**：

```java
// 上层（AgentRecommendService.computeReturnCount）— 打详细配置查找过程
log.info("[推荐聚合] 返回数量计算 scene={} configKey={} count={}", scene, configKey, count);

// 下层（V3Service）— 只打一行汇总
log.info("[V3模板渲染] 返回数量计算 scene={} respItemCount={}", scene, respItemCount);
```

## 检查清单

- [ ] 入口/出口/异常都有日志？能从日志还原一次请求的完整链路？
- [ ] 本次新增/修改的业务分支都有稳定、可检索的决策日志？
- [ ] 每条分支日志都包含 decision/result、reason、关键判断依据、业务标识和 traceId？
- [ ] 已列出“分支 → 触发条件 → 预期日志”，并在 E2E 中核对实际命中？
- [ ] traceId 贯穿？异步线程也传了？
- [ ] 耗时日志包含 costMs + bucket？
- [ ] 大字段截断？
- [ ] 批处理有汇总日志，不是逐条刷屏？
- [ ] 没有误导日志（request/response 没写反、变量没打错）？
- [ ] 模块前缀统一？同一个类的所有日志都带同一个 `[前缀]`？
- [ ] 前缀层级不超过两层？没有方法名混入前缀？
- [ ] 同一份结果 JSON 只在最终出口打一次，中间只打 size？
- [ ] 没有 `log.debug`？有业务含义的改 INFO/WARN，纯调试的直接删除？
