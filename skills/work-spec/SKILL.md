## 定位

本 skill 管**非编码部分**的工作规范：沟通风格、文档格式、开发流程。

**编码规范（命名/结构/日志/性能/安全等）已全部移至 `coding-standards`。**

## 一、沟通与语气

- 回复时默认使用中文。
- 自称保持助理/同事视角，称呼使用"用户"、"负责人"、"维护人"，或直接省略称呼。
- 语气轻松一点可以，但对问题的检查和结论要严谨。
- 尽量自己先做决策和取舍，避免频繁把选择题抛回用户。
- 代码是给人看的，不是给机器看的，说明白比看起来高级重要。

## 二、开发流程

- **干活前先确认目录和分支（铁律，第一优先级）**：
  - 项目经常有多个 git worktree 并行开发，同一个仓库可能存在 3~4 个工作目录。**搞错目录 = 代码白写 + 回滚成本极高。**
  - **AI 工具**：接到任务后，第一步用 `git worktree list` 查看所有工作目录，然后**主动问用户要在哪个目录/分支工作**，确认后再动手。不要假设"当前目录就是对的"。
  - **人工开发**：切目录/切分支后，养成习惯先跑 `pwd && git branch --show-current`，肉眼确认再开工。
  - **找不到文件/代码时，先查 worktree**：当前目录找不到预期的文件或改动，**第一反应是 `git worktree list`**——很可能代码在另一个 worktree 目录里。去对应的 worktree 找，不要直接说"文件不存在"。
  - **永远不在主分支开发**：main / master 只做 `pull` 和 `merge`，任何开发必须通过 worktree 创建独立分支。AI 工具接到开发任务时，如果当前在主分支，必须先创建 worktree。
  - **分支命名（强约束）**：新建业务分支统一使用 `vYYYYMMDDHHmm_<type>_<topic>`，其中时间使用上海时区的年月日时分，示例：`v202609090227_feat_unified_login`。分支名禁止出现 `/`，语义段使用小写字母、数字和 `_`，避免部署系统解析歧义。已有 `main`、`master`、固定汇总分支等约定分支保持原名，不为此规则改名。
  - 详见 `git-worktree-starter` skill（含中间产物清理机制、分支同步机制）。
- **设计先行**：编码前先想清楚方案；必要时在 `doc/` 目录下按日期新建设计文档。
- **迭代文档命名严格约束**：每个迭代目录 `doc/需求迭代/yyyyMMdd_迭代主题/` 下的文档**必须用标准命名 + 两位数字前缀**（`01-原始需求_DOC.md`、`02-需求拆解_DOC.md`、`04-技术方案_DOC.md`、`05-评估方案_DOC.md`、`06-工时评估_DOC.md`、`07-编码实施计划_DOC.md`、`08-业务验证报告_DOC.md`、`09-代码评审_DOC.md`、`10-提测交付_DOC.md`、`11-联调文档-{受众}_DOC.md`、`12-测试用例_DOC.md`、`13-测试报告_DOC.md`，统一 `_DOC.md` 后缀）。**编号即 SOP 阶段顺序**，缺位跳号不补位。**联调文档必须按受众细分**（前端/外部/服务端），即使只有一类受众也带后缀。禁止变种命名（如"编码规划"、"评审"）。完整清单和编号约定见 `code-write-doc` skill 的"命名规范"章节，权威以那边为准。
- **命令行编译与测试（默认谨慎）**：
  - 默认不主动在命令行执行编译/构建来"碰碰运气"。
  - 只有任务本身需要、用户明确要求、或项目有稳定的本地验证方式时才执行。
  - 其他情况优先给出"建议在 IDE/目标环境如何验证"的检查点与命令清单。

## 三、Markdown 文档处理规范

适用于项目内 Markdown：

- 文字：
  - 使用正确的中文标点，保证语句通顺、逻辑清晰。
  - 修正错别字，但语气保持"大白话"，不要变成官话。
- 结构：
  - 尽量在文档前面加 TOC（如 `[TOC]`）和手写目录列表。
  - 合理使用标题层级，避免过深嵌套。
  - 需要时使用 Mermaid 画图，一图胜千言。
- 元信息：
  - 可以在文档里标明作者、负责人、创建/更新时间（`yyyy-MM-dd HH:mm:ss`）。
  - 团队文档优先写具体负责人或 `DeepTrip Team`，不要附加 AI 工具后缀。
- 高亮：
  - 对关键句可以用 `<mark style="background: #FFB86CA6;">内容</mark>` 做强调，适度使用。

## 四、目录 README 规范

- 目录说明统一使用 `README.md`，不新增 `DIRINFO.md` 或其他同义文件名。Git 平台、IDE 和新成员都能按惯例直接找到它。
- 仓库根目录、职责明确的一级目录、包含多个入口或子目录的独立模块、测试套件和工程工具目录应有 `README.md`。
- 纯包结构、只有一两个自解释文件的叶子目录可以复用上级 README；生成目录、日志、缓存、构建产物、第三方代码和空目录不添加 README。
- README 至少说明：目录用途、允许放什么、禁止放什么、关键结构或文件、常用命令、输入输出或产物位置。没有对应内容的章节不要为凑格式而保留。
- README 只描述当前有效状态，不记录迁移流水账；文件移动、入口命令或目录职责变化时必须同步更新相关 README 和上级导航。
- 若目录已有产品或模块 README，在同一个 `README.md` 中补充“目录职责”，不要再创建第二份目录说明文件。
- 具体创建和维护步骤使用 `code-write-doc`；测试目录的边界和层级以 `integration-test` 为准。
