# Fix Bug

用于定位和修复缺陷。修复时必须遵循最小改动原则，禁止无关重构。

## When to use

Apply this skill when the user wants to:

- Fix a bug, defect, or regression
- Debug errors, crashes, or unexpected behavior
- Resolve CI/test failures caused by application code
- Investigate and repair a reported issue

## Core principles

1. **最小改动**：只改修复问题所必需的文件和代码。
2. **禁止无关重构**：不顺手优化、不重命名、不调整格式、不迁移结构。
3. **先定位根因**：禁止只压错误、吞异常、加空判断来掩盖问题。
4. **共享代码优先保守**：公共方法、共享模块、被多个组件引用的代码，默认避免行为变更。

## Workflow

```
Task Progress:
- [ ] 1. 理解问题（现象、复现、期望行为）
- [ ] 2. 定位根因（日志、调用链、相关代码）
- [ ] 3. 评估影响范围与风险等级
- [ ] 4. 制定最小修复方案
- [ ] 5. 实施修复
- [ ] 6. 本地验证（测试 / build / 基本回归）
- [ ] 7. 输出修复报告（含人工确认事项）
```

### Step 1: 理解问题

收集并确认：

- 问题现象与报错信息
- 复现步骤或触发条件
- 期望行为 vs 实际行为
- 影响范围（单页面 / 单模块 / 全局）

信息不足时，先追问或基于现有证据做最小假设，并在报告中标注不确定性。

### Step 2: 定位根因

- 从报错栈、日志、最近改动入手
- 追踪到具体文件、函数、条件分支
- 区分根因与表象，避免只修表面症状

### Step 3: 评估影响范围与风险等级

**高风险**（满足任一即视为高风险）：

- 公共 / 导出方法、共享 `utils` / `common` / `shared` 模块
- 被 2 个及以上组件 / 模块 / 页面引用的代码
- 基础类型、全局状态、鉴权、支付、数据持久化
- 修改公共 API 签名或对外契约

**中风险**：

- 单模块内多处调用，但影响面局限在一个业务域
- 需要改配置、环境变量、构建脚本

**低风险**：

- 仅影响单一组件 / 页面 / 函数的局部逻辑
- 调用方唯一且边界清晰

### Step 4: 制定最小修复方案

| 风险等级 | 策略 |
|----------|------|
| 低风险 | 可直接修复，保持改动最小 |
| 中风险 | 优先局部修复；评估所有调用方是否受影响 |
| 高风险 | 优先在不改公共行为的前提下修复；若必须改公共代码，先说明影响面并规划验证 |

**高风险改动约束**：

- 必须先评估影响范围并避免行为变更
- 如确需修改，必须先完成本地验证（测试 / build / 基本回归）
- 结果中必须明确标注「需要人工介入验证」
- 移动端需注明真机测试项

### Step 5: 实施修复

- 只提交与根因直接相关的改动
- 不改无关文件；不扩大 diff
- 高风险场景下，优先兼容性修复（如加参数默认值、保留旧行为分支）而非破坏性修改
- 若存在更安全的替代方案，优先采用

### Step 6: 本地验证

按项目实际情况执行，至少包括：

1. **针对性验证**：验证 bug 已修复（复现路径、相关单测）
2. **构建检查**：`build` / `lint` / 类型检查（若项目有）
3. **基本回归**：检查直接调用方和相邻功能未被破坏

| 风险等级 | 最低验证要求 |
|----------|--------------|
| 低风险 | 复现路径 + 相关检查 |
| 中风险 | 上述 + 调用方抽样验证 |
| 高风险 | 上述 + 全量相关测试 / build；标注人工验证项 |

验证失败时，继续修复或回退方案，不要带着失败结果声称已修复。

### Step 7: 输出修复报告

每次修复结束，**必须**使用以下模板输出：

```markdown
## 修复报告

### 根因
[一句话说明根本原因，附关键代码位置]

### 修改范围
- 文件：`path/to/file` — [改了什么]
- （列出所有改动文件）

### 风险评估
- 风险等级：低 / 中 / 高
- 影响面：[哪些模块 / 组件 / 调用方可能受影响]
- 行为变更：有 / 无 — [如有，说明变更内容]

### 验证结果
- [ ] 问题复现路径验证通过
- [ ] 相关测试通过（注明命令与结果）
- [ ] Build / lint 通过（注明命令与结果）
- [ ] 基本回归通过（说明验证了哪些场景）

### 待人工确认事项
- [ ] 无 — 低风险且本地验证充分
- [ ] **需要人工介入验证** — [具体说明]
  - 移动端真机测试：[测试项 1]、[测试项 2]
  - 其他人工验证：[staging 验证 / 跨端验证 / 性能验证 等]
```

「待人工确认事项」不能为空。高风险改动必须包含「需要人工介入验证」。

## Prohibited actions

- 不顺手重构、不批量改风格、不升级依赖（除非与 bug 直接相关）
- 不通过注释掉错误、空 `catch`、静默降级来掩盖问题
- 不无说明地修改公共接口签名或共享模块行为
- 不在未完成本地验证时声称已修复
- 不跳过影响评估直接改共享代码

## Escalation

以下情况停止自动推进，向用户说明并请求决策：

- 根因不确定，存在多种可能且证据不足
- 修复需要破坏性变更或大范围改动
- 涉及安全、隐私、支付、数据一致性且无法安全验证
- 本地无法运行测试 / build，或缺少真机 / 测试环境

## Quick reference

**用户原话约束（必须遵守）**：

> 修复时必须遵循最小改动原则，禁止无关重构。若改动涉及公共方法、共享模块或被多个组件引用的代码，必须先评估影响范围并避免行为变更；如确需修改，必须先完成本地验证（测试/build/基本回归），并在结果中明确标注「需要人工介入验证」，移动端需注明真机测试项。最终输出需包含：根因、修改范围、风险评估、验证结果、待人工确认事项。
