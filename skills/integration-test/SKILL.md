# 真实应用端到端测试

## 定位

把测试当作编码的一部分，而不是代码写完后的形式检查。测试结论必须来自正在运行的真实应用和可核对的运行证据。

本 Skill 只认可以下闭环：

```text
梳理用户真实使用链路
  -> 建立链路到接口、状态、条件和证据的追踪矩阵
  -> 当前代码启动成功
  -> 写入仓库的可执行 E2E 脚本
  -> 多类 case 真实运行
  -> 核对响应与业务语义
  -> 核对日志/trace
  -> 核对数据库、缓存、消息或其他副作用
  -> 失败则修复、重启、重跑
```

## 硬性门禁

未同时满足以下条件，不得声称“测试通过”“验证完成”或“可以交付”：

1. **用户链路完整**：先按用户角色、真实入口、前置状态、操作步骤、业务分支和最终可见结果梳理受影响链路；禁止从接口清单或代码分支直接开始凑 case。
2. **链路可追踪**：建立“用户链路 -> 接口/服务 -> 状态与副作用 -> 测试条件 -> 断言与证据”追踪矩阵；P0/P1 链路和高风险分支不得遗漏。
3. **应用真实运行**：用目标仓库官方启动脚本启动当前 worktree/分支代码；确认 Git SHA、进程、端口和健康状态，排除旧进程。
4. **脚本长期保留**：为本次新增或修改的行为创建或更新可重复执行的测试脚本，纳入目标仓库并作为后续回归资产维护。放在 `/tmp`、对话临时目录、命令历史里，或测试通过后删除都不合格；一次性 `curl` 和手工点页面不算测试产物。
5. **case 覆盖风险**：在每条用户链路内至少覆盖正常流程、关键边界和明确失败路径；按改动风险补充鉴权、幂等、重复提交、状态迁移、超时、重试、并发或多轮交互。
6. **断言覆盖结果**：不能只断言 HTTP 状态码、`code=0`、返回非空或进程未崩溃；必须断言用户可感知结果和适用的后台状态变化。
7. **日志与数据真实核对**：只检查本次测试时间窗、唯一测试 ID、traceId 或 sid 对应日志，确认关键分支和下游调用确实执行，并解释相关 ERROR/WARN；对适用的 DB、Redis、ES、MQ、文件、任务状态或第三方副作用做前后对比。
8. **证据可复现**：保留链路覆盖、运行命令、环境、Git SHA、case 结果、关键日志位置、数据查询结果和清理结果。

Mock、单元测试、覆盖率和静态检查可以作为补充信息，但在本 Skill 中不得新写、不得作为主要工作、不得替代上述任一门禁。用户明确要求这些测试时，另行执行，结论仍不能冒充 E2E 验收。

## 执行流程

### 1. 梳理用户链路与验证范围

先读取并交叉核对：

- 当前 worktree、分支、Git SHA 和 diff；
- 需求验收标准、目标验证追踪矩阵、技术方案和缺陷复现步骤；
- 用户角色、真实入口、前置状态、操作步骤、业务分支和最终可见结果；
- 受影响接口、下游服务、数据存储、异步任务和外部副作用；
- 目标仓库的 `AGENTS.md`、启动文档、现有 E2E 框架和脚本风格。

先形成用户链路清单，再映射实现链路。不要从接口清单、Controller 方法或代码分支直接开始设计 case。每条链路至少说明“谁在什么状态下，从哪个入口做什么，经过哪些业务分支，最终看到什么结果”。

建立并持续更新以下追踪矩阵；需求已有目标验证追踪矩阵时，在原矩阵扩展这些字段，不重复造文档：

| 链路 ID | 用户角色/入口 | 前置状态 | 用户步骤与分支 | 接口/服务 | 状态与副作用 | 测试条件 | 断言与证据 | 优先级 |
|---------|---------------|----------|----------------|-----------|--------------|----------|------------|--------|
| J01 | 示例 | 示例 | 示例 | 示例 | 示例 | 正常/边界/失败 | 响应/数据/日志/用户结果 | P0/P1/P2 |

每个可观察行为至少对应一个断言，每个 P0/P1 链路和高风险分支至少对应一个 case。无法确认用户真实入口或最终结果时，先补齐需求分析，不得用接口调用顺序代替用户链路。

### 2. 设计 case 矩阵

以用户链路为主轴，在每条链路内展开适用条件，不要先测 Happy path、最后再建一个与链路脱节的边界用例池：

| 维度 | 必查问题 |
|------|----------|
| 正常流程 | 用户从真实入口能否完成完整操作，结果是否正确？ |
| 输入边界 | 空值、临界值、长文本、特殊字符、组合参数是否正确？ |
| 权限与归属 | 未登录、无权限、跨用户/跨商户访问是否被拒绝且无脏数据？ |
| 状态迁移 | 前置状态、操作后状态、重复操作后的状态是否符合规则？ |
| 幂等与重复 | 同一业务键、requestId、消息或回调重复执行会不会重复写入？ |
| 失败与恢复 | 真实可构造的下游失败、超时、非法响应或中断是否按设计处理？ |
| 并发 | 同一资源并发修改时是否超卖、重复、丢更新或状态错乱？ |
| 兼容与回归 | 老入口、老数据、不同渠道/语言/版本是否仍然正常？ |

P0/P1 链路必须覆盖；不适用项写明原因，不能静默跳过。测试无法穷举所有输入组合时，按业务风险、状态迁移、历史故障和等价类选择用例，不得笼统声称“覆盖所有条件”。

### 3. 编写可重复执行的脚本

优先扩展仓库已有 E2E 框架。没有现成框架时，在目标仓库使用清晰、稳定的位置，例如：

```text
tests/e2e/<domain>/
  README.md
  conftest.py
  test_<feature>_journeys.py
  cases/
    <journey>.yaml
```

#### 测试资产目录规则

所有用于判断功能是否正确的资产统一放在业务仓库 `tests/`，不得放在 `scripts/` 或单独的顶层 `e2e/`：

```text
tests/
  unit/                  # 用户明确要求时编写；可使用 Mock
  integration/           # 多模块与真实中间件/真实依赖，禁止替代依赖
  contract/              # 协议、Schema、字段映射和兼容性
  smoke/<domain>/        # 运行中应用的入口连通性和基础协议，不代表业务验收
  e2e/<domain>/          # 通过真实入口驱动已运行应用，不替换业务依赖
```

- 目录按测试边界分类，不按运行框架分类；使用 pytest 的黑盒测试仍放 `tests/e2e/`，可独立执行的 Python runner 也不能因此放进 `scripts/`。
- 文件只要包含业务断言、PASS/FAIL 判定、回归 case 或测试专用 fixture/runner，就属于测试资产。
- `scripts/` 只放通用项目或工程脚本，例如启停、构建、代码生成、数据迁移、环境检查和通用诊断工具。
- integration 必须连接其声明范围内的真实数据库、Redis、MQ、外部服务或其他真实依赖；替换了关键依赖就没有集成验收意义。
- 不新增或保留以 Mock、桩数据、固定样本、`redis_override` 或纯内部模块拼接为核心的 integration 回归资产；触及这类历史文件时优先删除。用户明确要求隔离验证时只能作为 unit 测试处理，且不得替代真实 E2E。
- 只检查状态码、连接、Content-Type 或基础响应结构的运行中应用测试归入 `tests/smoke/`；smoke 通过不能替代 E2E 业务验收。
- 测试专用 case、fixture 和样本放在对应测试目录；通用数据导出、环境准备工具可以留在 `scripts/`，由测试调用。
- 运行证据统一写入项目忽略的 `logs/`、`test_logs/` 或项目约定的证据目录，不与可执行测试资产混放。
- 迁移既有测试文件时同步修改 import、运行命令、CI 配置和文档引用；历史目录可分批治理，但新增和本次触及的文件必须立即合规。

脚本和 case 文件必须提交到业务代码仓库，跟随接口和业务规则持续演进。运行日志、数据快照和包含敏感信息的证据按项目规则保存或忽略，不与可执行脚本混在一起。

#### 语言选择

先沿用目标仓库成熟的 E2E 技术栈；没有现成约定时按以下顺序选择：

| 场景 | 推荐 | 原因 |
|------|------|------|
| Web HTTP API、SSE、WebSocket、跨服务流程、数据核对 | **Python 3 + pytest（新建默认）** | HTTP/JSON/协议/数据库客户端成熟；fixture、参数化、断言、超时、报告和退出码可直接复用 |
| 浏览器页面、前端交互 | **TypeScript + Playwright** | 能驱动真实浏览器，适合页面状态、网络请求和用户流程断言 |
| 高并发、吞吐、稳定性 | **k6 JavaScript 或 Locust Python** | 有明确并发模型和指标，不用手写压测调度器 |
| 启停服务、串联已有命令 | **Shell** | 只做薄编排，简单直接 |
| 仓库已有成熟自研 Runner 或 Java/Go 测试工具 | **沿用现有框架** | 减少迁移和新依赖，复用鉴权、模型和基础设施 |

没有成熟框架时，服务端 Web E2E 默认使用 Python 3 + pytest：fixture 管理环境、鉴权、前置数据和清理，参数化管理同一链路的多组条件，测试函数表达用户步骤与断言。已有可维护的 Python CLI Runner、RestAssured 或 Go 测试框架时直接扩展，不为统一形式强制迁移。

case 多于少量固定场景时，将输入与期望放进 YAML/JSON，用户步骤、协议处理和断言逻辑放进 Python；不要把 YAML 变成包含条件分支的流程引擎。优先使用结构化 HTTP/JSON、数据库和协议客户端，不用 `grep`、`sed` 或字符串包含关系解析复杂响应。Shell 不承载业务断言，只负责启动、传参和调用测试程序。依赖使用目标仓库现有包管理方式锁定，不能依赖开发机上碰巧全局安装的包。

#### 大用例集执行策略

case 较多时，不要把所有用例无差别串行执行，也不要用无限加 worker 掩盖套件设计问题：

- 为 case 标记 `journey_id`、优先级和功能标签，支持按受影响链路、P0/P1、功能域和全量回归选择执行；交付前跑完所有受影响链路，全量回归按项目周期后台执行。
- 无共享状态、数据由 `run_id` 隔离的 case 可以限流并行；共用账号、商户、订单、库存、会话或顺序状态的 case 必须串行、分组隔离或加资源锁。
- pytest 同步用例可按项目依赖使用 `pytest-xdist`，大量网络等待场景可使用受控异步客户端；worker 数必须可配置，并依据测试环境容量、下游限流和数据隔离能力设置保守默认值。
- 并行运行仍须保证每个 case 的日志、trace、数据快照和清理动作能按唯一标识归属；无法归属证据时降低并发，不得牺牲可诊断性换速度。
- 高并发、吞吐和稳定性目标使用 k6/Locust 单独验证，不通过堆叠 pytest worker 代替压测。

无论选择哪种语言，脚本必须：

- 默认连接本地或明确的测试环境，禁止默认写生产；
- 支持通过参数或环境变量配置 base URL、端口和必要凭据；
- 为每次运行生成唯一 `run_id`，并透传 traceId/sid/requestId；
- 自动准备前置数据，记录变更前快照，结束后清理或说明保留原因；
- 设置明确超时，异常时输出请求、响应摘要和定位标识；
- 对每个 case 输出 PASS/FAIL，任一关键断言失败时返回非零退出码；
- 避免吞异常、无限重试和把失败降级为 warning；
- 把密钥放在环境变量或本地忽略配置中，不写入脚本和报告；
- 在功能后续修改时同步更新，不能写完一次后变成失效脚本。

每个 case 的断言按实际链路覆盖以下层次：

```text
传输层：状态码、协议/SSE/WebSocket 完整性
业务层：业务码、关键字段、状态迁移、排序/数量/金额/文案
数据层：DB/缓存/ES/MQ/文件/任务记录的新增、修改、删除和一致性
链路层：关键分支日志、下游请求结果、trace/span、错误与耗时
用户层：最终页面、消息、通知或可见业务结果
```

只断言其中一层通常不够；覆盖所有与本次改动有关的层。

### 4. 启动当前代码

1. 使用项目官方启动 Skill 或启动脚本，禁止绕过项目约定手工 `java -jar`、`uvicorn` 等。
2. 对旧进程执行项目支持的 stop/restart，确认监听端口对应新进程。
3. 等待明确的就绪条件，不用固定 `sleep` 代替健康检查。
4. 记录 Git SHA、启动命令、端口、PID、启动时间和日志路径。
5. 如果是多服务链路，启动所有本次验证必需的真实服务，并记录各自版本。

若只能访问共享 QA，必须确认部署版本包含目标提交；无法确认时不得把结果归到当前代码。

### 5. 运行并观测

先记录日志文件偏移、时间戳或查询起点，再运行脚本。执行过程中同步保存：

- 完整命令和参数；
- 每个 case 的唯一 ID、耗时和断言结果；
- 用例选择范围、分组/分片和 worker 配置；
- 失败请求的必要上下文；
- 应用日志、下游调用日志和 trace 链接/标识；
- 数据前后快照及查询命令；
- 异步任务最终状态，而不是只看“已受理”。

日志核对不能只跑 `grep ERROR`：还要确认预期代码分支、下游调用次数和关键状态日志出现。发现 ERROR/WARN 时逐条判断是否由本次 case 触发、是否影响结果、是否需要修复。

### 6. 失败闭环

测试失败时先判断是产品代码、测试脚本、环境还是测试数据问题，再处理：

1. 用 run_id/traceId 和数据快照定位根因；
2. 修复产品代码或脚本；
3. 按项目方式重启应用，确认新进程加载新代码；
4. 先重跑失败 case，再重跑所有受影响 case；
5. 重新检查日志和数据，不能只看脚本退出码。

不要通过放宽断言、吞异常、增加无界重试、删除失败 case 或改期望值让测试“变绿”。

### 7. 清理与报告

清理测试创建的数据、临时文件和本次启动且不再需要的进程。不得停止用户原本运行的无关服务。

在迭代流程中按项目文档规范写测试报告；普通编码任务至少在最终答复中给出同等信息：

```markdown
## 用户链路覆盖
| 链路 ID | 用户场景 | 接口/服务 | 测试条件 | Case | 覆盖结论 |

## 环境与版本
- 仓库 / worktree / 分支 / Git SHA
- 启动命令 / 端口 / PID / 日志路径

## 测试脚本
- 脚本路径
- 执行命令

## 测试结果
| Case | 场景 | 关键断言 | 结果 | 耗时 |

## 日志核对
- run_id / traceId / 时间窗
- 关键路径与异常结论

## 数据核对
- 数据源、前值、后值、期望值、清理结果

## 问题列表
- 已修复、遗留问题、未覆盖项及原因

## 证据索引
- 原始输出、日志、trace、数据快照的位置
```

## 阻塞处理

遇到以下情况，明确结论为“未完成真实 E2E 验证”，说明已完成的检查、缺失条件和可直接继续的命令：

- 应用无法构建或启动；
- 必要依赖、凭据、测试账号或环境不可用；
- 无法确认运行版本对应当前提交；
- 真实数据状态无法读取或副作用无法核对；
- 测试会不可控地影响生产数据。

不得为了给出 PASS 而改用 Mock、单元测试、静态阅读或伪造结果。

## 与其他 Skill 的关系

| Skill | 关系 |
|-------|------|
| `coding-standards` | 编码时必须同步产出并运行真实 E2E 脚本；本 Skill 定义完成门槛 |
| `local-start` | 按目标链路决定并启动所需本地服务 |
| `requirement-analysis` | 从验收标准和目标验证追踪矩阵获取基础 case |
| `code-review` | 评审脚本质量、断言有效性和未覆盖风险，不用“有测试文件”代替执行证据 |
| `skynet-log` / `deeptrip-trace-query` / `langfuse-session-query` | 按环境核对真实日志和链路证据 |
