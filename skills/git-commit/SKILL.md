## 何时使用本 Skill

- 当需要在任意项目里 **git 提交 / push** 时，尤其是：
  - 我已经改了代码或文档，用户说“提交一下”“推一下”；
  - 需要确认是否要顺带更新接口/结构文档；
  - 需要考虑是否跑测试或至少检查测试是否合理覆盖。
- 只要涉及 `git add` / `git commit` / `git push`，都应该按本 skill 的流程来，而 **不要使用 rebase**。

## 总体原则

- **禁止 rebase**：不要使用 `git pull --rebase` 或任何 rebase 相关操作。
- **push 冲突时停下**：若 push 失败（远端有更新），立即停止并让用户人工介入，不要自动 pull 或解决冲突。
- **只提交该提交的东西**：保证这次 commit 里只有与当前任务直接相关的文件。
- **对话范围内提交**：当由 Codex 协助提交代码时，默认只提交“本次对话中由 Codex 修改或新建的文件”，不把其他本地改动顺带一起提交。
- **新建分支命名**：统一使用 `vYYYYMMDDHHmm_<type>_<topic>`，例如 `v202609090227_feat_robot_qa`；时间使用上海时区的年月日时分，禁止使用 `/`。已有主分支或团队固定分支保持原名。
- **提交前想清楚两件事**：
  1. 有没有需要更新/补充的文档（尤其是 *_DOC.md、mapping 文档等）；
  2. 现有测试是否需要更新或至少用来验证一下改动。
- **提交后保持分支干净**：push 前先 pull（非 rebase），避免把脏历史推给别人。
- **push 前强制规范检查（铁律）**：所有代码在 push 到远程之前，**必须**检查是否符合项目全部规范（`coding-standards`、文档同步、测试覆盖等）。不检查就 push = 把风险直接推给团队，后果极其严重。哪怕用户说"快点推"，也要至少过一遍核心检查项，不能跳过。

## 提交流程（一步步来）

> 以下流程假设当前已经在目标仓库的工作目录下。

### 1. 检查当前改动范围

1. 运行 `git status`，看清楚：
   - 哪些文件是 `modified`；
   - 哪些文件是 `untracked`。
2. 思考这次任务的边界，只允许以下几类文件进本次 commit：
   - 当前任务直接修改的代码文件；
   - 与这些代码逻辑强相关的文档文件（如 `*_DOC.md`、`doc/*.md`）；
   - 必要的配置/脚本更新（如果本次任务确实要求）。
3. 如有与本次任务无关的改动：
   - 优先使用 `git restore <file>` 恢复；
   - 或记下，等以后专门为这些改动单开一个 commit。

### 2. 检查是否需要更新文档

在准备 `git add` 之前，先做一轮“文档对齐思考”：

- 如果你改动了：
  - 请求 / 响应 DTO（例如新增字段、修改含义）；
  - Service 行为（例如过滤逻辑、排序规则）；
  - 出参结构里新增了字段（比如这次的 `TrainTransferInfo` 补字段）；
- 那就要检查相应文档：
  - API 文档：如 `*_Controller_DOC.md`；
  - 映射 / 设计文档：如 `doc/2026-01-05_dt2_train_assistant_mapping.md`；
  - 其他使用方依赖的结构说明文档。

对于每一处行为/字段变更：

1. 问自己：**如果我是调用方，看文档能不能看出来这次的变化？**
2. 若答案是否定的，就补文档：
   - 把新增字段列出来（字段名 + 含义 + 取值范围/示例）；
   - 若有行为变化（比如排序/过滤规则收紧），补一两句说明；
   - 保持用语清晰直接，和项目现有文档风格一致。
3. 补完文档后，再跑一次 `git diff` 确认文档改动集中且描述准确。

### 3. 检查测试是否需要/可以验证

> 不要求每次都一定要跑全量测试，但在提交前必须主动思考一次。

对于当前改动，问自己三件事：

1. **有没有相关测试存在？**
   - 查找是否有对应模块的测试文件（例如单元测试、接口测试）；
   - 如果有，看看是否需要调整断言或补新 case。
2. **这次改动风险高不高？**
   - 风险高（核心逻辑、过滤/排序条件、金额/库存/安全相关）：**优先考虑跑测试**；
   - 风险相对可控，可以先在逻辑上自证，再视情况决定是否立即跑测试。
3. **当前环境适不适合跑测试？**
   - 若仓库已有清晰的测试命令（如 `mvn test`、`npm test` 等），记录下建议命令；
   - 在当前 `approval_policy` 允许且不会拖慢节奏太多时，可以实际执行；
   - 若不方便执行（时间过长或环境不稳），在最终回复中明确告诉用户“建议跑哪类测试”。
   - 同时遵循 `work-spec`：默认不主动跑编译/构建，除非任务本身需要或用户明确要求。

Skill 层面的默认动作：

- 若当前任务本身就是修测试 / 补测试，则可以直接运行对应测试命令；
- 其他情况优先给出“要不要跑、跑什么”的判断，再由用户决定是否让你实际跑。

### 4. 组织提交内容（git add）

1. 用 `git diff` 再看一眼改动，确认逻辑和文档都是你认可的状态。
2. 使用 `git add <file1> <file2> ...` 精确添加文件，不用 `git add .`：
   - 只加本次任务相关文件；
   - 不要顺带把未规划的文件加进去。
3. 再次执行 `git status`，确保：
   - `Changes to be committed` 中只有你期望的文件；
   - `Changes not staged for commit` 中没有遗漏的关键改动。

### 5. 编写 commit message

写 commit message 时遵循：

- **必须使用中文描述**，不要再写英文的 message；
- 简短、清晰、说明这次做了什么：
  - 比如：`fix: 修复郑州站匹配规则`；
  - 或：`feat: 补充中转方案站点信息`。
- 不要在 message 里写长篇解释，长解释应该放在文档或代码注释里。

步骤：

1. 执行 `git commit -m "<简明中文说明>"`。
2. 若 commit 失败（例如 pre-commit hook），按错误提示修复后再重试。

### 6. 同步远程（禁止 rebase）

> 团队约定：**不要 rebase**。

1. 在 push 之前，先同步远程分支，但**只用普通方式**：
   - 使用 `git pull`（默认 merge 模式）；
   - 或者 `git fetch origin` + `git merge origin/<branch>`；
   - **不要**使用 `git pull --rebase`，也不要手动执行 `git rebase`。
2. 如遇合并冲突：
   - 先解决冲突、确认行为正确；
   - 再 `git add` 冲突文件并 `git commit` 完成 merge；
   - 然后继续后面的 push。

### 7. push 前强制规范检查（铁律）

> **不检查就 push = 把风险直接推给团队。** 这一步不可跳过。

在同步远程完成后、push 之前，必须完成以下检查：

1. **代码规范**：所有改动是否符合 `coding-standards`（命名、结构、日志、异常处理、安全等）；
2. **文档同步**：涉及接口/行为/字段变更的，对应 `*_DOC.md` 是否已更新；
3. **测试覆盖**：核心逻辑改动是否有测试保障，至少要有"我确认过不需要"的判断记录；
4. **敏感文件**：确认没有误提交 `.env`、密钥、临时调试代码等；
5. **编译/语法**：代码能通过基本的编译或 lint 检查（如果项目有的话）。

如果任何一项不通过：**停下来先修，修完再 push。** 不要抱着"先推上去再说"的心态。

### 8. push 到远端

1. 使用 `git push` 将本地分支推送到远程：
   - 确认当前分支名称是否正确（新建业务分支示例：`v202609090227_feat_robot_qa`）。
2. **若 push 失败（远端有新提交导致冲突）**：
   - **立即停下来，不要自动尝试解决**；
   - 告知用户："push 遇到冲突，需要人工介入"；
   - 说明冲突原因（例如"远端有新的提交，需要先 pull 合并"）；
   - 等待用户的指示，不要自作主张执行 `git pull` 或其他操作。
3. 若远端有保护或提示（例如需要使用 token、SSH），按提示完成。
4. push 成功后，可以在最终回复里带上：
   - 最新的 commit id；
   - 以及是否需要创建 / 更新 Merge Request 的简要说明。

## 使用本 Skill 时的注意事项

- 若其他 Skill（比如某个项目专用 Skill）对提交流程有更细的指引：
  - 应先遵循项目专用 Skill 的特殊要求；
  - 然后再叠加本 Skill 中的“禁止 rebase + 文档/测试检查”通用规则。
- 若用户在对话中明确给出特殊指令（例如“这次就改这个文件，直接 push 就行”）：
  - 可以适当简化流程，但仍要：
    - 确认不要使用 rebase；
    - 思考一次文档与测试是否需要调整，并在回复里说清楚你的判断。

| `code-review` | 协作：提交前可先 review 一轮 |
| `work-spec` | 遵循：commit message 用中文、提交前检查边界清晰 |
