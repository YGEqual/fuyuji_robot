## 定位与边界

本 skill 在迭代流程中的位置：

```
需求进来 → 【requirement-analysis】→ system-design → plan-work → 编码
            产出：原始需求 + 需求拆解      产出：技术方案 + 工时评估
```

**只管"需求是什么"，不管：**
- 怎么实现（交给 `system-design`）
- 改哪些文件（交给 `plan-work`）

## 自动化原则

**默认自动执行，有问题才告警让人介入。**

```
┌─────────────────────────────────────────────────────────────┐
│  需求分析完成后：                                            │
│  ─────────────────────────────────────────────────────────  │
│  1. 自动检查：伪需求判断、价值评估、优先级、确认项            │
│  2. 无问题 → 自动进入 system-design 阶段                     │
│  3. 有问题 → 告警，等待人处理                                │
└─────────────────────────────────────────────────────────────┘
```

### 自动检查清单

| 检查项 | 通过条件 | 不通过处理 |
|--------|---------|-----------|
| 需求拆解文档完整 | 所有章节已填写 | 🚨 告警：补全缺失章节 |
| 伪需求判断完成 | 所有功能点已判断 | 🚨 告警：完成伪需求判断 |
| 优先级已排定 | MVP 范围明确 | 🚨 告警：排定优先级 |
| 待确认项已确认 | 无 [NEEDS CLARIFICATION] | 🚨 告警：确认待办项 |

### 告警规则

只有以下情况才需要人介入：

1. **🚨 发现伪需求**：建议砍掉，等待人确认
2. **🚨 待确认项未确认**：需要产品/业务方补充信息
3. **🚨 价值评估不明确**：需要人判断是否值得做

### 自动进入下一阶段

以上检查全部通过后，**自动调用 system-design**，不需要人确认。

```
检查通过 → 自动进入 system-design
检查不通过 → 告警，等待人处理 → 处理后自动进入下一阶段
```

## 何时使用本 Skill

- 用户说"先别写代码，先把需求搞清楚""帮我分析下这个产品需求/PRD/原型""把业务逻辑全部拆出来"。
- 需求看起来简单，但其实容易埋雷：涉及状态流转、权限、金额、库存、并发、幂等、跨系统联动、审核流等。
- 开发前需要把内容同步给：研发/测试/产品/运营（避免口头对齐反复扯皮）。

## 输入要求

尽量一次性拿到这些；缺少会导致结论不稳（只问"阻塞性"问题，其他先按合理默认值继续推进）：

1. 需求来源：PRD 文本 / 会议纪要 / 飞书卡片 / 原型链接 / 截图。
2. 目标用户：谁用？在什么场景用？频率如何？
3. 业务目标：为什么做？要提升什么指标？（转化/留存/效率/成本/风险）
4. 约束条件：上线时间/兼容性/数据口径/权限要求/依赖系统。
5. 现状：现在怎么做？痛点是什么？现有接口/表/流程是什么？

## 输出交付物（2 份文档）

### 文档 1：原始需求_DOC.md

> 模板：`references/原始需求_DOC_模板.md`

**定位**：产品原文存档 + AI 整理的统一格式版。

- **AI 整理版**（第一部分）：把产品给的内容整理成结构化 Markdown，补全缺失信息，标注待确认项。
- **产品原文**（第二部分/附录）：原文不做修改，仅供留底对照。

### 文档 2：需求拆解_DOC.md

> 模板：`references/需求拆解_DOC_模板.md`

**定位**：从用户视角逻辑拆解，每个场景讲清楚用户做什么、看到什么、得到什么。

核心内容：
1. **需求概述**：一句话说清楚。
2. **场景拆解**：每个场景包含用户角色/前置条件/操作/响应/成功结果/异常。
3. **状态与规则**：状态流转图 + 业务规则清单。
4. **边界与异常**：异常情况 + 用户看到什么 + 处理方式。
5. **非功能要求**：性能/安全/兼容。
6. **范围边界**：本次做 / 本次不做。
7. **验收标准**：Given-When-Then。
8. **未决问题**：需要谁拍板 + 当前假设。

## 分析流程

按下面顺序走，别上来就画接口（容易把错误需求实现得很漂亮）：

1. **需求分类**（第一步，必填）：
   - 需求来源：产品需求 / Bug修复 / 技术需求 / 运营需求 / 测试反馈 / 用户反馈
   - 需求规模：大需求（>5人日）/ 中需求（2-5人日）/ 小需求（<2人日）
   - 紧急程度：🔴 紧急修复 / 🟡 计划迭代 / ⚪ 长期优化
   - 提出方：产品/开发/测试/运营/用户/领导
   - 影响范围：单端/多端/跨系统/全渠道
   - **为什么要分类**：不同来源/规模/紧急度的需求，处理流程和标准不同。分类清楚了，后续流程才能对症下药。
2. **一句话复述需求**：用大白话复述给用户确认（不超过 3 句）。
3. **价值与优先级**：
   - 这功能做成后，谁得利？解决哪类痛点？
   - 不做会怎样？做一半能不能先上线？
4. **范围边界**（最关键）：
   - 这次"必须做"的最小闭环是什么？
   - 明确"不做什么"（避免 scope creep）。
5. **按场景拆用户路径**：
   - 正常主路径（happy path）先跑通；
   - 再补关键分支（权限/状态/异常/并发）。
6. **抽象出业务对象与状态**：
   - 先定实体（谁是主角），再定状态机（怎么变），再定规则（什么时候能变）。
7. **规则落到"可判定条件"**：
   - 每条规则都要写成"条件 → 结果"，避免模糊词（尽量/适当/可能）。
8. **验收标准**：
   - 每条需求至少 1 条可验证验收（别让测试靠猜）。
9. **非功能与风险兜底**：
   - 性能、并发、幂等、权限、安全、日志、可观测性。

## 逻辑拆解清单（强制覆盖）

不管需求是什么，至少把下面这些点过一遍（否则代码一定会漏）：

1. **角色与权限** — 谁能看？谁能改？谁能删？管理员/普通用户差异？
2. **状态与流转** — 有哪些状态？允许的迁移路径？禁止的跳转？
3. **输入与校验** — 必填字段、格式、长度、枚举、默认值、空值处理。
4. **核心计算规则** — 优先级、冲突规则、排序/过滤口径、精度（如涉及金额）。
5. **幂等与重复提交** — 重复请求怎么处理？幂等键是什么？
6. **并发与一致性** — 同一资源并发修改怎么处理？
7. **失败与降级** — 失败提示什么？是否重试？是否需要人工兜底？
8. **日志与可观测性** — 关键节点日志？traceId？
9. **数据口径** — 字段含义、来源、是否持久化、是否缓存、历史数据兼容。

## 验收标准写法

统一用 Given-When-Then：

- Given：前置条件（用户角色/数据状态/配置开关/依赖系统返回）
- When：触发动作（点击/提交/调用接口/定时任务）
- Then：期望结果（页面/返回体/落库/MQ/状态变化/日志关键字）

每条 Then 至少包含一个"可检查"的点：返回码、状态变化、数据库记录变化、关键字段取值。

### 测试用例输出要求

需求分析阶段必须输出**功能测试用例清单**，作为测试阶段的输入。

每个验收标准对应一条测试用例，格式如下：

```markdown
## 测试用例清单

| 编号 | 场景 | Given | When | Then | 优先级 |
|------|------|-------|------|------|--------|
| TC01 | 用户登录成功 | 用户已注册 | 输入正确账号密码 | 返回 token | P0 |
| TC02 | 密码错误 | 用户已注册 | 输入错误密码 | 提示"密码错误" | P0 |
| TC03 | 账号锁定 | 连续错误5次 | 再次尝试登录 | 提示"账号已锁定" | P1 |
```

**优先级定义：**
- P0：核心功能，必须通过才能上线
- P1：重要功能，应该通过
- P2：边界场景，可以做

## 风险与非功能

至少写清楚下面这些"上线后最常炸"的点：

- 性能：QPS 预估、是否分页、是否批量、是否缓存。
- 安全：权限校验、输入校验。
- 可靠性：超时、重试、降级、幂等；外部依赖不可用怎么办。
- 可观测性：关键链路日志、耗时、traceId、告警指标。
- 兼容性：老数据/老客户端/灰度开关/回滚方案。

## Checkpoint 检查

需求分析完成后，**自动运行检查点验证产出物质量**：

### 检查项清单

| 检查 ID | 描述 | 类型 | on_fail | 说明 |
|---------|------|------|---------|------|
| R01 | 原始需求文档结构完整 | structure | auto_fix | 自动补全缺失章节 |
| R02 | 文档格式规范 | format | auto_fix | 自动修复格式问题 |
| R03 | 需求拆解核心章节完整 | structure | warn | 需手动补充 |
| R04 | 验收标准格式正确 (Given-When-Then) | content | warn | 需手动修正 |
| R05 | 测试用例数量匹配验收标准 | content+script | warn | 建议补充测试用例 |
| R06 | 包含边界与异常场景 | structure | warn | 建议补充 |
| R07 | 场景覆盖完整（含异常场景） | ai_check | warn | AI 验证 |
| R08 | 包含隐藏需求排查 | structure | warn | 建议补充 |
| R09 | 迭代看板存在且结构完整 | structure | warn | 可选检查 |

### 执行检查

```bash
# 运行检查点
scripts/checkpoint/run-checkpoint.sh requirement-analysis doc/需求迭代/{迭代目录}

# 查看检查结果
cat doc/需求迭代/{迭代目录}/.claude/checkpoint-result.json

# 查看问题池
scripts/checkpoint/issue-pool.sh list --status open
```

### 检查结果处理

| 结果 | 处理方式 |
|------|---------|
| 全部通过 | 自动进入 system-design 阶段 |
| 有警告 (warn) | 记录到问题池，继续执行 |
| 有阻塞 (block) | 必须修复后才能继续 |

## PROCESS.md 状态记录

需求分析阶段开始时，创建/更新 PROCESS.md：

```bash
# 创建 PROCESS.md
mkdir -p .claude/processes/{迭代目录}
cp scripts/checkpoint/templates/PROCESS_TEMPLATE.md .claude/processes/{迭代目录}/PROCESS.md
```

### 更新规则

完成以下操作后更新 PROCESS.md：

1. **阶段开始**：更新阶段状态为 `in_progress`
2. **产出物完成**：更新产出物状态
3. **Checkpoint 检查**：记录检测轮次和结果
4. **发现问题**：添加到 Issue Pool
5. **问题修复**：更新 Issue Pool 状态
6. **阶段完成**：更新阶段状态为 `done`

### PROCESS.md 关键字段

```markdown
| 字段 | 值 |
|------|-----|
| 当前状态 | `in_progress` |
| need_hook | `true` / `false` |
| max_check_rounds | `5` |

| 阶段 | 状态 | 开始时间 | 完成时间 |
|------|------|---------|---------|
| requirement-analysis | in_progress | 2026-04-10 10:00 | |
```

### Hook 触发条件

设置 `need_hook = true` 时，会话结束会触发 hook：

- 自动打开新 tmux pane 继续
- 读取 PROCESS.md 恢复状态
- 继续执行未完成的检查
